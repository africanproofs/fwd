# fwd — Flare Wallet Daemon

> Policy-gated signing service for African Proofs' EVM backend keys. Custody-first; substrate-minimal; Anthropic agents are first-class callers. The redesign of `keosd` for autonomous agents on Flare in 2026.

## Identity

`fwd` holds AP's automation private keys AES-256-GCM-sealed under a 32-byte master key kept in a mode-0600 host file (loaded once at startup; v1.0.0a1 retired the HashiCorp Vault backend — see `decisions.md` D1); decryption and signing happen in `fwd`'s own process, gated by declarative policy and recorded in an append-only audit log. Every `.env PRIVATE_KEY` line in AP backends — `ftso-fee-claimer`, `apregister/`, `apcli`, future `fics` write paths, future Claude agents — calls `fwd` instead of holding keys directly.

The custody property `fwd` rests on: **the Vault Transit master encryption key is `exportable=false` and cannot be extracted via the API; private keys are envelope-encrypted at rest and exist as plaintext in `fwd`'s process memory only during the bounded signing operation, after which the buffer is zeroized (Core invariant #16).** This is a deliberate trade-off documented in `decisions.md` D1: the originally-intended design (Vault Transit signing of `ecdsa-p256k1` keys) was infeasible because Vault does not support secp256k1.

The workflow doctrine below is settled — transferred verbatim from FICSM (`../ficsm/CLAUDE.md` § Development workflow), where it was earned through FICS' five-month design cycle and the S0+S1+S2 hardware sealing on 2026-04-25. `fwd` inherits the operating discipline, not the substrate; the substrate (single-purpose signing service vs multi-stratum control plane) is fwd's own.

Wrapper requirements (in § Development workflow / Reviewer obligations): (1) name the canonical prompt file path explicitly; (2) instruct Sonnet to read the file in full before doing anything else; (3) tell Sonnet that the HAND-OFF fenced block is the authoritative spec (material outside the fences is Reviewer-internal context); (4) restate the no-commit / no-version-bump / no-doctrine-edit operating rules; (5) require deviation surfacing per the canonical prompt's final-report format; (6) end with "Begin by reading the canonical prompt file." The wrapper is the seam: operator copies the wrapper verbatim, Sonnet reads the file, finds the fence, implements what's inside. Symmetric pattern to v0.3.0a5's hand-off-demarcation doctrine, which codified the fence requirement; this ship codifies what the operator pastes to point Sonnet AT the fence. ## What FWD Deliberately IS NOT

These are not in scope until a real consumer or proven need surfaces. Re-introducing any requires explicit operator authorization tied to a concrete consumer:

- **Not a user wallet.** Frontends (`apregister-web`, `proofs-website`) keep thirdweb v5. fwd is for *backend automation*, not user flows.
- **Not multi-chain beyond EVM Flare-family.** Flare, Songbird, Coston2 only. No Bitcoin, Solana, Cosmos, Antelope.
- **Not clustered, not HA, not horizontally scalable.** A signer is a coherence boundary, not a scaling unit. One container, one wallet set, one nonce manager per (wallet, chain).
- **No K8s, no Pulumi, no Helm.** `docker-compose.yml` is the deployment artifact. K3s exists in AP infra but `fwd` does not run on it.
- **No public network exposure in v1.** Bind to `127.0.0.1` on the host; callers reach fwd via the Docker bridge network only. No `signer.proofs.africa` DNS.
- **No autonomous policy.** Every rule is declarative YAML. The LLM never decides whether to sign.
- **No web UI.** HTTP API + a thin CLI for admin operations. No dashboard.
- **No multi-signer / threshold / MPC in v1.** Single Vault, single key per wallet.
- **No HSM hardware in v1.** YubiHSM 2 is a Phase 10 option.
- **No `web3.py`.** `eth-account` + `httpx` cover the signing path with a fraction of the dependency tree.
- **No raw-digest signing.** The structured-signing endpoints `/sign-message` and `/sign-typed-data` are deferred (Phase 9/10 — NOT mounted in v0.5.x; `src/fwd/main.py` mounts only `/v1/sign-and-send` among signing routes); arbitrary `eth_sign`-style raw-digest endpoints will never exist. (The prior "exist" wording was Core #18 drift; reconciled v0.5.5.)
- **No long-lived caller credentials issued by humans.** Caller API keys are minted by `fwd` itself, scoped per policy, rotatable from the CLI.

## Core invariants

1. **Keys never persist plaintext.** Each wallet's secp256k1 private key is generated externally (secure RNG), envelope-encrypted with AES-256-GCM under a 32-byte master key held in a mode-0600 host file (`SealedMaster`, `src/fwd/infra/sealed_master.py`; v1.0.0a1 retired Vault Transit — `decisions.md` D1), and stored as `seal:v1:<ciphertext>` in SQLite. Plaintext keys exist in `fwd`'s process memory only during the bounded signing operation and are zeroized in-place on the mutable `bytearray` after each signature. **Process memory is locked against swap via `mlockall(MCL_CURRENT | MCL_FUTURE)` at lifespan startup (`src/fwd/main.py::lifespan`).** Because the `fwd` container runs as non-root user `fwd` (uid 1000) per the Dockerfile, the actual mechanism that allows `mlockall` to succeed is `ulimits.memlock: -1` (unlimited `RLIMIT_MEMLOCK`) in `docker-compose.yml`; the additional `cap_add: [IPC_LOCK]` is kept for defense-in-depth (lands the capability in the bounding set so a future root entrypoint or ambient-capability scenario benefits). Verifiable live via `docker exec fwd grep VmLck /proc/1/status` returning a non-zero kB value. mlock prevents the kernel from paging plaintext key buffers to `/swapfile`; it does **not** prevent core dumps, `/proc/$pid/mem` reads by privileged processes on the host, or in-process Python GC copies of the original immutable `bytes` returned by the sealed-master decrypt before our `bytearray` wrap (Phase 10's optional `ctypes`-based memory pinning addresses the latter). Compromise of `fwd` while running, OR host read access to BOTH the mode-0600 master-key file AND the SQLite ciphertexts, grants the attacker the ability to recover all wallet plaintext keys; offline theft of the SQLite ciphertexts WITHOUT the master-key file yields ciphertext only. There is no separate key-management process boundary — this is the deliberate v1.0.0a1 trade-off for low-value Flare automation keys (≈ tens of USD/key) on a host that is never publicly exposed (`decisions.md` D1; `threat-model.md` A4). (Supersedes the v0.1.2 Vault-Transit-envelope design, itself a pivot from the originally-intended Vault signing, infeasible because Vault has no secp256k1 Transit key type.)

2. **Default-deny.** Every signing request is denied unless policy explicitly permits caller × wallet × contract × method × value × rate. New callers and new wallets enter with zero capabilities.

3. **Sign intent, never opaque bytes.** Every signing request must decode to a known ABI shape against the policy-bound contract. Unparseable calldata = refuse. The audit log records the decoded human-readable intent, not the raw hex.

4. **One nonce manager per (wallet, chain).** SQLite `BEGIN IMMEDIATE` serializes nonce reservation. Concurrent signing requests against the same wallet cannot collide. Nonce release on confirmed-or-dropped, reconciliation on startup.

5. **Append-only audit log.** Every request, decision, signature, and broadcast outcome is recorded in a hash-chained log (`prev_hash`, `row_hash`). Rows are never deleted, never updated. Tamper-evidence is verifiable by a CLI that walks the chain.

6. **Caller identity is bearer-token-with-scope, not username-and-password.** Each caller has an API key issued by `fwd`. The key is mapped in policy to a specific set of `(wallet, contract, method, max_value, rate)` permissions. Compromise of one key cannot exceed that caller's policy.

7. **No `PRIVATE_KEY=` in any AP `.env` file post-migration.** Eliminating that pattern is what `fwd` exists to do. Any commit reintroducing a backend private key into a `.env` file is a regression and must be reverted before merge.

8. **No unseal ceremony (v1.0.0a1).** The sealed-master backend loads its 32-byte AES-256-GCM master from a mode-0600 host file owned by the `fwd` user at startup — no Vault, no Shamir, no `docker exec` unseal step, fully unattended on restart. (Superseded the Phase 3a–7 Vault 3-of-5 Shamir model when Vault was retired — `decisions.md` D1, the asset-class rationale; honest history of the prior model lives there.)

9. **Single replica.** `fwd` runs as one container. Restart on failure, not failover. The signer is a singleton by design.

10. **Host-agnostic deployment.** `docker-compose.yml` + `.env.example` runs identically on any host with Docker + Docker Compose. No bake of Scaleway / ap-ftso-02 / IP-specific assumptions into the repo. Host-specific config flows through `.env`, period.

11. **Replacement, not retry-from-zero.** Stuck transactions are resubmitted with the same nonce and bumped `maxPriorityFeePerGas` (× 1.125, capped at 5 retries). A reserved nonce is never silently abandoned; it confirms, replaces, or surfaces to operator.

12. **Public repo, private config.** `gitlab.com/proofs.africa/fwd` is public. The security model is policy + custody, not concealment. Actual `policy.yaml` values, caller API keys, Vault unseal shares, and Litestream credentials live outside the repo (separate private repo or env-injected on the host).

13. **Linear forward versioning.** Every ship bumps the next linear patch number in BOTH `pyproject.toml` and `fwd/version.py`. No back-port semver. Main is the only delivery target. Carryover from FICSM Core invariant #8.

14. **Real-RPC verification is the validation.** Unit tests with mocked RPCs are necessary but not sufficient. Every signing-path change must be verified against a live Coston2 RPC before merging to the production-flow code. Mocks lie. Carryover from FICSM Core invariant #13. The **v0.4.5 concurrency bug** and the **v0.5.2 deny-audit bug** (Core invariant #19) are the canonical proofs: both were unit-green, both were structurally invisible to mocked tests, both were caught only by the operator-driven live drill, and both would otherwise have reached the v1.0.0 production migration. A defect a mock cannot see is closed by a test on real infrastructure **plus** the doctrine that names its class — never by the point-patch alone (see #19, the deeper rule).

15. **Operator gates every production migration.** No automated `.env` sweep. Each application's migration to `fwd` (Phase 8 onwards) is its own ship with its own operator approval — even when the code change is mechanical. Migrations are the moments where a mistake translates to lost keys.

16. **Decrypt-on-demand, zeroize-on-completion.** Plaintext private keys are not cached in `fwd`'s process memory between signing operations. Each `/v1/sign-and-send` call decrypts the wallet's privkey via Vault, wraps the result in a mutable `bytearray`, signs the transaction with `eth-account` from a `bytes()` view of that buffer, and zeroizes the buffer in `finally`. Process-wide privkey caches are forbidden as a regression and are enforced by `tests/unit/test_envelope_signer.py::test_no_32byte_state_after_*` (introspects signer instance state for any 32-byte `bytes`/`bytearray` after each call). The buffer-zeroize contract is enforced by `test_create_wallet_buffer_is_all_zero_after_zeroize` and the sign_transaction equivalent. Combined with `mlockall`-protected process memory (Core invariant #1), this bounds the A3/A4 attack surface for the v0.1.2 single-process custody design to the active signing operation. Note: Python's GC may have copied the immutable `bytes` returned by `vault.decrypt` to other addresses before we wrap in `bytearray`; this best-effort caveat is documented in `architecture.md` § Implementation hazards #2 and accepted in v1. Phase 10's optional `ctypes`-based memory pinning addresses the residual.

17. **Custody is proportionate to the asset class (v1.0.0a1).** `fwd` custodies low-value Flare automation keys (~1000 FLR ≈ tens of USD per key — FTSO-claim / registration / gas wallets, never treasury) on a host that is never publicly exposed. The custody backend is therefore a **sealed local master** (AES-256-GCM, 32-byte key in a mode-0600 host file owned by the `fwd` user), NOT HashiCorp Vault. The Vault container + Transit + 3-of-5 Shamir-across-failure-domains + the production wipe-and-redo ritual were **retired at v1.0.0a1**: two independent audits (`docs/reviews/v0.5.4-*`, `v0.5.5-*`) found the doctrine/ops weight disproportionate to the asset class, and Vault's one differentiator over a sealed master — an independent decrypt-audit-trail against a track-covering attacker — was worthless at this value/exposure and was never even enabled (v0.5.5 audit OE-2). Disaster recovery for this asset class is **regenerate the wallet + on-chain `setClaimRecipient` rotation** (≈ free), not a distributed-share ceremony. The master-key file is `policy.yaml`-class private config (Core invariant #12 — gitignored, never in repo/image, operator-provisioned via `clifwd master generate`). If the master file is suspected compromised: regenerate it, re-seal every wallet (Phase 7 rotation flow), rotate on-chain recipients. (Instituted v1.0.0a1; supersedes the prior Vault-Shamir #17, which governed Phase 3a–7 Vault dev — honest history in `decisions.md` D1. The Core #7 "structurally indistinguishable from `.env PRIVATE_KEY=`" test still binds: the master file MUST be 0600/owned and never committed.)

18. **Doctrine and code do not drift.** Every claim in `CLAUDE.md`, `decisions.md`, `architecture.md`, and `threat-model.md` either describes existing code/config behaviour OR is explicitly marked deferred to a named phase that will make it true. When code drifts from doctrine, ship the code that makes the doctrine true; when doctrine drifts from reality, rewrite the doctrine to admit what the code actually does — but never let the two disagree silently. Every audit cross-references doctrine claims to code (the v0.3.1 audit at `docs/reviews/` is the canonical example); drift is the easiest finding to surface and the cheapest to fix early. Drift is detected by audit; drift is fixed by aligning one to the other; drift is **never** tolerated as "we'll fix it later" without an explicit deferred-phase marker. Why this matters: `fwd`'s value rests on doctrine being trustworthy. If Core invariant #X is partial fiction, every future agent reading `CLAUDE.md` operates on a softer foundation than they think, and every higher layer (Phase 4 caller auth, Phase 7 policy + audit, Phase 8 production migration) inherits that softness. The audit at v0.3.1 surfaced four documentation-vs-implementation gaps that had silently accumulated; v0.3.2 closed them and instituted this invariant to prevent recurrence.

19. **Forensic audit rows survive the failure they record.** An audit-log row that explains a *denied*, *errored*, or *aborted* operation MUST be durably committed independently of — and is never unwound by — the transaction whose rollback that same failure triggers. The forbidden anti-pattern: append the forensic row to the shared `RequestScope`/`AdminScope` session, then `raise`, letting the exception propagate through `fwd.infra.db.session_scope` whose `except Exception: rollback` discards the row. In `fwd` this is enforced by **commit-before-raise on the single shared session**: every exception arm that writes a `sign-and-send` / `wallet-*` / `caller-*` / `policy-load` row calls `await audit_repo.commit()` (`app/sign_and_send.py`'s three arms) or `await session.commit()` (`main.py::_startup_policy_load`, before `SystemExit(1)`) before re-raising. It MUST be the already-open session — opening a second `session_scope` for the forensic write re-introduces the v0.4.5 two-session `BEGIN IMMEDIATE` writer-lock deadlock. The commit additionally makes the failure path's *operational* end-state doctrinally correct rather than whatever a blanket rollback yields: a step-8/9 **deny** keeps its D14 rate increment (the attempt is counted; deny does not release); a **pre-broadcast** failure's explicit nonce/rate releases run before the commit so the net is zero; a **broadcast** failure keeps the reserved nonce (the tx may be in mempools — the receipt watcher decides). The approved path is unaffected (no exception → `session_scope` commits once → D16 atomicity of the approved row with nonce+tx+rate preserved). Enforcement is a regression test that drives the **real** `session_scope` rollback with a self-validating without-commit control (a mocked session is structurally blind to this — that blindness is precisely why the defect shipped at v0.5.0a6 in `main.py`, was point-fixed during the a7 Reviewer pass, **silently recurred at v0.5.2 in `sign_and_send.py`**, and was caught only by the Phase 7 GA live drill three ships later). **Why this is critical:** the row exists to answer "what was refused or failed, and why" — losing it on the very path it documents is a silent, total failure of Core invariant #5 (append-only audit) and the accountability #2/#3 rest on, invisible to every unit test, and a reopening of the exact gap `fwd` exists to close — a signer that refuses correctly but keeps no record of refusals. **The deeper rule (why this is an invariant, not a patch):** a defect found is a defect *class* — it is closed only when the class is named in doctrine AND guarded by a test that fails for the class on real infrastructure; an instance-patch without both is a deferral of the next instance, and the v0.5.0a6→v0.5.2 recurrence is the proof. (Instituted at v0.5.4 after the Phase 7 GA drill surfaced the recurrence; partners with Core invariant #14.)

## Development workflow — Opus prescribes, Sonnet implements with deviation license, Opus reviews with overwrite authority

Four roles in deliberate tension. Carryover from FICSM § Development workflow, abbreviated.

### Reviewer (Opus 4.7) — PRESCRIBES

Drafts the canonical prompt for each ship: file paths, exact contents, drift rules, test deltas, verification block. Reviewer authority is *what `fwd` should be after this ship*.

Reviewer obligations:
- Phase 0: read code, verify codebase semantics, surface design questions to operator.
- Draft a self-contained canonical prompt at `~/.claude/plans/fwd-canonical-prompt-<ship>.md`.
- Pre-handoff scan: shell-var substitution defects, identifier-rename completeness, multi-segment `bash -c` wrapping (FICSM Core invariant #19).
- **Demarcate every hand-off in canonical prompts with EXACTLY this format — no variations:**
    1. **A bold marker on its own line**: `**HAND-OFF — <recipient> (paste verbatim into <destination>):**`
    2. **A blank line.**
    3. **A fenced code block** wrapping the entire hand-off payload end-to-end (use 4 backticks if the payload contains 3-backtick blocks; 5 backticks if nested deeper). **Nothing outside the fences belongs to the hand-off.**

  Pre-handoff scan (mandatory, runs against the canonical prompt before announcing it ready):
  ```sh
  grep -c '^\*\*HAND-OFF — ' ~/.claude/plans/fwd-canonical-prompt-<ship>.md  # ≥ 1
  ```
  AND a manual eyeball: the line immediately after the bold marker is empty; a fenced block opens within the next 3 lines and closes before any non-handoff content resumes.

  **Why this is enforced.** A Sonnet session pasted from "go look at this paragraph here" rather than "copy these exact bytes between these fences" is a recurring source of subtle deviations (truncation at paragraph boundaries, accidentally-included Reviewer-aside text, missed instructions buried in surrounding prose). The fence is a hard boundary the operator can copy verbatim with zero ambiguity. **No exceptions** — even a one-line hand-off goes inside fences. Every canonical prompt at `~/.claude/plans/fwd-canonical-prompt-*.md` MUST satisfy this; a prompt missing the demarcation is incomplete and must not be handed off.

- **Always produce a Sonnet wrapper message alongside the canonical prompt.** The wrapper is what the operator pastes into a fresh Sonnet 4.6 session as the first user message; it points Sonnet at the canonical prompt file rather than dumping the prompt contents into chat. Wrapper requirements (no exceptions):
    1. Name the canonical prompt file path explicitly (e.g., `/home/l/.claude/plans/fwd-canonical-prompt-v0.4.0a5.md`).
    2. Instruct Sonnet to read the file in full BEFORE doing anything else.
    3. Tell Sonnet that the HAND-OFF fenced block inside the file is the authoritative spec — material outside the fences is Reviewer-internal context.
    4. Restate the no-commit / no-version-bump / no-doctrine-edit operating rules (Sonnet doesn't commit; Reviewer commits; Sonnet never edits `CLAUDE.md`, `pyproject.toml` version, `src/fwd/version.py`, or anything under `docs/`).
    5. Require deviation surfacing per the final-report format in the canonical prompt.
    6. End with "Begin by reading the canonical prompt file."

  The Reviewer writes the wrapper bespoke for each ship — it is short (10-20 lines), names the specific version + one-line description, and is presented to the operator immediately after the canonical prompt file is announced ready.

  **Why this is enforced.** A canonical prompt is a long Reviewer-internal document with Phase 0 findings, deviation-handling tables, and verification gates that are NOT instructions to Sonnet — only the HAND-OFF fenced block is. Pasting the whole prompt into Sonnet without the wrapper invites Sonnet to read the Reviewer-aside text as instructions ("I see — the Reviewer wants me to consider F8.1 carefully" → Sonnet implements F8.1's audit framing rather than the spec). The wrapper is the seam: the operator copies the wrapper verbatim into chat, Sonnet reads the file, finds the fence, implements what's inside. Wrapper missing = ship is not ready to hand off.

### Implementer (Sonnet 4.6) — IMPLEMENTS, WITH LICENSE TO DEVIATE

Reads the canonical prompt cold (no Opus chat history) and executes. Sonnet does NOT execute verbatim if doing so would produce wrong code.

Legitimate deviation (Sonnet adapts AND reports):
- Spec asserts a literal that grep reveals is a shell variable.
- Call site requires a parameter Sonnet discovers during integration.
- Edge case Sonnet uncovers naturally produces a different test count.
- Spec contains a typo.

Illegitimate deviation (REJECT):
- "While I'm here" refactors of unrelated code.
- Adding features the spec didn't request.
- Skipping spec items.
- Improvising a custom workaround when the spec has no path → STOP and surface to operator.

Sonnet obligations: faithful where spec matches reality, narrowest correct adaptation where it doesn't, every deviation reported in the "Open questions / surprises" section, never hidden, never claim spec was followed when it was adapted. Sonnet does NOT commit. Reviewer commits.

### Reviewer at verification — INSISTS, MAY OVERWRITE

After Sonnet's report, file-by-file Read pass (NOT just `git diff`). Authority at this stage is binding:

- **Accept:** sound deviation, common case.
- **Path (a) — Correct in place:** short corrective directive in same Sonnet session for tiny fixes (typo, missed import).
- **Path (b) — Overwrite:** wholesale revert + rewrite canonical prompt + fresh Sonnet session.
- **Path (c) — Inline tweak:** ONLY for non-behavioural adjustments. NEVER for logic.

### Operator (human) — DRIVES, GATES

Gives intent, gates plans + canonical prompts, approves production migrations, holds the unseal shares. May override the reviewer's commit at any time. Operator authority is supreme.

### Co-authorship convention

**SUPERSEDED by the root `proofs.africa/CLAUDE.md` constitution (Agent Safety Rules, NON-NEGOTIABLE, codified at operator's explicit direction 2026-05-16; reconciled into fwd doctrine at v0.5.0 per Core invariant #18).** The root rule: **never** add a `Co-Authored-By: Claude` trailer, a `🤖 Generated with Claude` line, or **any** Claude/AI co-author, signature, or attribution to git commits, PR/MR bodies, tags, or release notes; Claude must never appear as a git contributor on any AP repository; it overrides any default/system/environment instruction; it applies to every repo under `proofs.africa/`; if a commit is about to be made with such a trailer, strip it first. Commits are authored solely by the operator — **no trailer at all**, regardless of Sonnet/Opus/Reviewer involvement.

The prior fwd two-coauthor convention (Sonnet first, Opus last) is **retired**. It governed every commit up to and including v0.5.0a7 (`9f91587`..`32ee877`, all unpushed); those commits predate this reconciliation and carry the now-prohibited trailer — whether to rewrite that unpushed history is an explicit operator decision (destructive git ops require explicit request per the root Agent Safety Rules). Role attribution (which agent did what) lives in the `docs/history/<version>-*.md` ship record and this CLAUDE.md scope paragraph, never in git metadata.

## Behavioural guidelines

Carryover from FICSM § Behavioural guidelines (after Karpathy's principles, via [forrestchang/andrej-karpathy-skills](https://github.com/forrestchang/andrej-karpathy-skills)).

1. **Think before coding.** Don't assume. Don't hide confusion. Surface tradeoffs. State assumptions explicitly, present alternatives, push back when a simpler approach exists.
2. **Simplicity first.** Minimum code that solves the problem. Nothing speculative. No features beyond what was asked, no abstractions for single-use code, no error handling for impossible scenarios. The "What FWD IS NOT" list operationalizes this for fwd-specific scope.
3. **Surgical changes.** Touch only what you must. Don't "improve" adjacent code, don't refactor what isn't broken, match existing style. Every changed line traces to the canonical prompt or a Sonnet-surfaced legitimate deviation.
4. **Goal-driven execution.** Define success criteria. Loop until verified. Every fwd canonical prompt's verification block is the strong criterion for that ship.

## Carryover from FICSM and from `keosd`

`fwd` is not a fork of either. The workflow doctrine (Opus/Sonnet/Reviewer/Operator), the four-layer validation philosophy, the linear-forward versioning, the canonical-prompt completeness checklist, and the substrate ethos (SQLite, single-operator, framework-free) are inherited verbatim from FICSM as design — no FICSM code is imported.

The role itself — *daemon that holds keys and signs on behalf of clients* — is inherited from `keosd` (Antelope/EOSIO `programs/keosd/`). What `fwd` adds that `keosd` does not provide: intent decoding, default-deny per-caller policy, hash-chained audit, EVM-native signing flow, and a custody backend (Vault Transit `aes256-gcm96` envelope encryption) whose master encryption key is non-exportable by API and whose plaintext private keys exist in `fwd`'s memory only during the bounded signing operation.

The ~50 banked feedback memories at `~/.claude/projects/-home-l-working-gitlab-com-proofs-africa-fics/memory/` and the FICSM doctrine doc at `../ficsm/CLAUDE.md` act as a Phase-0 checklist for `fwd`'s reviewers.
