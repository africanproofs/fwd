# fwd — Flare Wallet Daemon

> Policy-gated signing service for African Proofs' EVM backend keys. Custody-first; substrate-minimal; Anthropic agents are first-class callers. A purpose-built key-custody-and-signing daemon for autonomous agents on Flare in 2026.

## Identity

`fwd` holds AP's automation private keys, gated by declarative policy and recorded in an append-only audit log. Every `.env PRIVATE_KEY` line in AP backends — `ftso-fee-claimer`, `apregister/`, `apcli`, future `fics` write paths, future Claude agents — calls `fwd` instead of holding keys directly.

The custody property `fwd` rests on: **a 32-byte AES-256-GCM master key exists only in a mode-0600 host file owned by the `fwd` user (never in the repo or image — Core invariant #12); each wallet private key is envelope-encrypted at rest under it and exists as plaintext in `fwd`'s process memory only during the bounded signing operation, after which the buffer is zeroized (Core invariant #16).** Decryption and signing happen in `fwd`'s own process. The custody model is proportionate to the asset class (low-value Flare automation keys; the host is never publicly exposed — Core invariant #17). Design rationale: `decisions.md` D1.

The workflow doctrine below is settled — transferred verbatim from FICSM (`../ficsm/CLAUDE.md` § Development workflow), where it was earned through FICS' five-month design cycle and the S0+S1+S2 hardware sealing on 2026-04-25. `fwd` inherits the operating discipline, not the substrate; the substrate (single-purpose signing service vs multi-stratum control plane) is fwd's own.

## Scope (current state)

**Current state.** `fwd` is a zero-egress, sign-only signer. It signs ABI-decoded EVM transactions and policy-gated native (value-only, empty-calldata) transfers (`POST /v1/sign-transaction`, the latter gated by a `native_transfers` recipient-allowlist + per-tx value cap + per-wallet daily aggregate cap — the keyless gas-funder path) and EIP-191 FSP protocol messages (`POST /v1/sign-fsp-message`), allocates nonces locally under `BEGIN IMMEDIATE`, and **never broadcasts or makes any outbound connection** — clients broadcast the signed payload and report the outcome back (`/v1/transactions/{id}/broadcast-result` + `/receipt`; stuck txs via `/sign-replacement`). Custody is a sealed local master (AES-256-GCM, 32-byte mode-0600 host file). Default-deny per-caller policy with ABI intent decoding, chain-bound contract rules, and a fail-closed gate on unconstrainable non-scalar args; hash-chained audit log; SQLite state with a local Litestream replica. One container on an `internal: true` network — no egress, no host port; admin via the `clifwd` host wrapper (`docker exec fwd clifwd` under the hood; `fwdctl` is an equivalent invocation alias; incl. `clifwd policy init` to generate a schema-correct policy + `clifwd policy validate`, the pre-deploy consistency gate). **Grants are keyed by `capability_id`** (`<consumer>/<network>/<role>`, ADR-0001 §3): `clifwd capability grant` ingests a consumer's `<consumer> spec --json`, **re-renders the custody diff itself**, and — default-deny, only on `--approve` — mints each caller by `capability_id` (carried on the policy `CallerBinding` + the audit row; back-compat: name-only grants still validate). `clifwd capability list` / `GET /v1/admin/capabilities` is the read-only, admin-gated granted-capabilities surface (the `doctor` "fwd=granted" leg) — derived from the **live policy** (so a hand-edited ungoverned grant is detectable), joined with each caller's status, sorted by `capability_id`. The operator authors `policy.yaml`; fwd's in-container app **mints + renders the diff but does NOT write `policy.yaml`** (Core #6/#12). fwd **emits the complete v2 handoff bundle** — the non-secret network config — which MUST include the `NETWORK` selector (clif silently defaults to flare without it, `cli.py:715`; a105) — PLUS the minted bearer tokens, pinned v2, mode-0600, TTL ~10 min (never a signing key, Core #7) — for clif to `import-credentials`: `fwd onboard` publishes it to **fwd's own outbox** (`${FWD_DIR}/handoff/<consumer>-<net>.json`) and `fwdctl capability grant --approve --emit-bundle <path> --config NETWORK=<net> [--config K=V …]` emits it for **any** consumer (pre-mint conformance gate: refuses a null `wallet_name`, a missing `NETWORK`, or a `NETWORK` contradicting the spec — BEFORE minting, since tokens are return-once; also the rotation channel); the consumer pulls it. **`fwd onboard rewards` is the *reference consumer's* (clif's) turnkey deployment, not the onboarding abstraction** — a new consumer starts from the consumer-generic path (`<x> spec --json` → `fwdctl capability grant --emit-bundle --config …` → `<x>ctl import-credentials`), never by forking onboard (`consumer-contract-v1` §6b). **fwd never reads OR writes a consumer's `.env` or directory — the bundle in fwd's outbox is the sole handoff (Invariant #5 + membrane)**; clif imports the bundle into its own `.env`, and a re-onboard of an existing caller rotates (re-mint), since fwd retains no token plaintext (Core #1/#16) and may not read clif's `.env` to recover one. Production-deployed; the consumer `clif` is migrated; the reward-claim path and fwd's FSP message *signing* (the clif↔fwd sign-broadcast-report integration) are mainnet-verified, and FSP REWARD_DISTRIBUTION on-chain protocol *acceptance* is **demonstrated** — for reward epoch 404 the daemon's `signRewards` landed our signing-policy key's `RewardsSigned` event and the epoch finalized on BOTH Flare (`rewardsHash` `0xff02f8…095dd`, 51.77% signing weight) and Songbird (`0x8eb571…eab5`, 50.43%), and the rewards were then claimed — all in one unattended daemon run — proving the imported signing-policy key is an accepted on-chain registered voter. UPTIME signing uses the same signer-registration path (acceptance follows) and stays gated off by default (`UPTIME_AUTO_ENABLED`) (Core invariant #17; `docs/architecture.md` § API surface; `docs/history/1.1.0a96-*.md`).

**Next:** Phase 9 continues with additional structured protocol-message types and consumers; Phase 10 is hardening (auto-unseal, metrics, optional HSM/mTLS). The revocable **`fsp-register`** capability (the keyless provider's one-time EntityManager `confirm*Registration` permissions) has shipped; the new-Songbird-provider canary's on-chain registration via it is the live operator-gated step. **Provider-distribution (in progress):** making the stack runnable by any Flare FTSO provider on their own host. The onboarding tooling (`clifwd policy init`/`validate`) and a build-from-source `curl|sh` installer have shipped: `install/install.sh` git-clones the public source, builds the image locally, and brings up an inert default-deny daemon behind a custody gate (`--no-start` defers bring-up; design in `docs/one-command-install.md`, host wrappers in `install/`). **The installer is fwd-only:** the clif consumer (reward claiming + FSP signing) is a SEPARATE deployment — its own compose project + egress that joins fwd's `internal: true` callers network; fwd never clones, builds, launches, or co-hosts it (clif's own `clifctl` manages it). Onboarding's only consumer touch-point is **publishing the complete v2 handoff bundle** (config + tokens; `<consumer>-<net>.json`, 0600, TTL ~10 min) to **fwd's own outbox** (`${FWD_DIR}/handoff/`) — **fwd never reads or writes a consumer's `.env` or directory (Invariant #5 + membrane)**; the consumer pulls the bundle into its own `.env` (ADR-0001 §Scope; ADR-0003; `consumer-contract-v1` §4 v2). The remaining Phase-1 sub-steps are `get.proofs.africa` hosting and a fetched-manifest checksum step. Each consumer's `.env PRIVATE_KEY=` deletion is that consumer's own operator-gated migration (Core invariant #15).

The project's history — per-version ship narratives + architectural decisions — lives in `docs/history/` (`SHIP-LOG.md` + per-version records, indexed in `docs/history/README.md`) and `docs/decisions.md`. Those are the quarantined record; the current-state docs describe only the present (Core invariant #18).

Disaster recovery — restoring fwd's wallets from the sealed-master backup (`master.key` + `state.db`) onto a new or rebuilt host — is documented in `RESTORE-RUNBOOK.md` (gitignored, Core invariant #12: it references the backup bundle and is kept with the off-host bundle, never committed).

## What FWD Deliberately IS NOT

These are not in scope until a real consumer or proven need surfaces. Re-introducing any requires explicit operator authorization tied to a concrete consumer:

- **Not a user wallet.** Frontends (`apregister-web`, `proofs-website`) keep thirdweb v5. fwd is for *backend automation*, not user flows.
- **Not multi-chain beyond EVM Flare-family.** Flare, Songbird, Coston2 only. No Bitcoin, Solana, or Cosmos.
- **Not clustered, not HA, not horizontally scalable.** A signer is a coherence boundary, not a scaling unit. One container, one wallet set, one nonce manager per (wallet, chain).
- **No K8s, no Pulumi, no Helm.** `docker-compose.yml` is the deployment artifact. K3s exists in AP infra but `fwd` does not run on it.
- **fwd's compose is fwd-only; it does not deploy consumers.** The project is `fwd` + `litestream` on the `internal: true` callers network — nothing else, and no egress network in the project. The clif consumer (claiming + FSP signing) is a SEPARATE deployment with its OWN compose project + egress that joins fwd's callers network as an external network; fwd never clones, builds, launches, or co-hosts clif (`clifctl` manages it). `fwd start` brings up only fwd + litestream; the installer is fwd-only (`--with-clif` is removed). Onboarding's sole clif touch-point is **emitting the complete v2 bundle** (config + tokens) to **fwd's own outbox** (`${FWD_DIR}/handoff/`; the `--clif-env-dir` env-write was deleted in a102); fwd never reads or writes clif's `.env` (Invariant #5). Bundling a consumer into fwd's project would defeat the zero-egress boundary this design draws.
- **Not a broadcaster.** fwd signs and allocates nonces; **clients broadcast** the signed tx and report the outcome back (`/v1/transactions/{tx_id}/broadcast-result`, `/receipt`). fwd never calls `eth_sendRawTransaction`.
- **No network egress at all.** fwd makes **no outbound connection** — code-level: no RPC/`httpx` client in `app|api|infra`; network-level: the `internal: true` compose network gives the container no internet route. Inbound only, from callers on the `internal: true` Docker bridge (`http://fwd:8080`); **there is NO host port** — `internal: true` removes host→container publishing, so admin runs via the `clifwd` host wrapper (`docker exec fwd clifwd …`). No public DNS.
- **No autonomous policy.** Every rule is declarative YAML. The LLM never decides whether to sign.
- **No web UI.** HTTP API + a thin CLI for admin operations. No dashboard.
- **No multi-signer / threshold / MPC in v1.** Single sealed master, single key per wallet.
- **No HSM hardware in v1.** YubiHSM 2 is a Phase 10 option.
- **No `web3.py`.** `eth-account` covers the signing path with a fraction of the dependency tree (`httpx` is used only by the admin CLI, not the daemon).
- **No raw-digest signing.** The arbitrary-raw-digest endpoints `/sign-message` and `/sign-typed-data` (free caller-supplied digest) are deferred (Phase 10 — NOT mounted), and arbitrary `eth_sign`-style raw-digest endpoints will never exist. `src/fwd/main.py` mounts two signing routes: `/v1/sign-transaction` and `/v1/sign-fsp-message`. The latter is **not** a raw-digest endpoint — it is EIP-191 `personal_sign` over a 32-byte messageHash fwd **reconstructs** from typed FSP fields (the caller supplies no digest); this "will never exist" statement therefore stays literally true.
- **No long-lived caller credentials issued by humans.** Caller API keys are minted by `fwd` itself, scoped per policy, rotatable from the CLI.

## Core invariants

1. **Keys never persist plaintext.** Each wallet's secp256k1 private key is generated by a secure RNG (internally by `wallets create` via `eth_account.Account.create()`, or supplied via `wallets import`), envelope-encrypted with AES-256-GCM under a 32-byte master key held in a mode-0600 host file (`SealedMaster`, `src/fwd/infra/sealed_master.py`), and stored as `seal:v1:<ciphertext>` in SQLite. Plaintext keys exist in `fwd`'s process memory only during the bounded signing operation and are zeroized in-place on the mutable `bytearray` after each signature. **Process memory is locked against swap via `mlockall(MCL_CURRENT | MCL_FUTURE)` at lifespan startup (`src/fwd/main.py::lifespan`).** Because the `fwd` container runs as non-root user `fwd` (uid 1000) per the Dockerfile, the actual mechanism that allows `mlockall` to succeed is `ulimits.memlock: -1` (unlimited `RLIMIT_MEMLOCK`) in `docker-compose.yml`; the additional `cap_add: [IPC_LOCK]` is kept for defense-in-depth (lands the capability in the bounding set so a future root entrypoint or ambient-capability scenario benefits). Verifiable live via `docker exec fwd grep VmLck /proc/1/status` returning a non-zero kB value. mlock prevents the kernel from paging plaintext key buffers to `/swapfile`; it does **not** prevent core dumps, `/proc/$pid/mem` reads by privileged processes on the host, or in-process Python GC copies of the original immutable `bytes` returned by the sealed-master decrypt before our `bytearray` wrap (Phase 10's optional `ctypes`-based memory pinning addresses the latter). Compromise of `fwd` while running, OR host read access to BOTH the mode-0600 master-key file AND the SQLite ciphertexts, grants the attacker the ability to recover all wallet plaintext keys; offline theft of the SQLite ciphertexts WITHOUT the master-key file yields ciphertext only. There is no separate key-management process boundary — this is the deliberate trade-off for low-value Flare automation keys (≈ tens of USD/key) on a host that is never publicly exposed (`decisions.md` D1; `threat-model.md` A4).

2. **Default-deny.** Every signing request is denied unless policy explicitly permits caller × wallet × contract × method × value × rate. New callers and new wallets enter with zero capabilities.

3. **Sign intent, never opaque bytes.** fwd signs ABI-decoded transactions OR EIP-191 personal-signed structured protocol messages whose 32-byte body fwd reconstructs from policy-checked typed fields — callers never supply a raw digest. Every `/v1/sign-transaction` request must decode to a known ABI shape against the policy-bound contract; every `/v1/sign-fsp-message` request reconstructs the FSP messageHash from typed fields (message type, reward epoch id, and for REWARD_DISTRIBUTION the claims tuple + rewards hash) — no caller-supplied opaque hash. Unparseable calldata / an unknown message type = refuse. fwd signs and returns the intent it decoded; it never broadcasts (the client does). Safety rests on byte-verified preimages + the EIP-191 domain prefix + address-level key-domain segmentation. The audit log records the decoded human-readable intent (or, for FSP, the reconstructed messageHash + emitted v,r,s), not a raw opaque digest.

4. **One nonce manager per (wallet, chain).** SQLite `BEGIN IMMEDIATE` serializes nonce reservation; concurrent signing requests against the same wallet cannot collide. fwd is the single nonce *reservation* authority, and `reserve_next` under `BEGIN IMMEDIATE` is the only nonce operation fwd performs — purely local, no network. fwd does **not** seed or reconcile nonces from chain (it has no egress): the initial seed is the admin `nonce-init` endpoint, and reconciliation is client-fed chain-truth via the admin, bounded-monotonic `nonce-sync` endpoint. A reserved nonce is released on a client-reported `rejected_releaseable` broadcast outcome (tail-only; non-tail gaps surface as operator-visible drift via `nonce/holes`), kept on `rejected_nonce_too_low` (chain is ahead → nonce-sync), and confirmed on a client-reported receipt.

5. **Append-only audit log.** Every signing request, policy decision, signature, admin mutation, and client-reported broadcast outcome is recorded in a hash-chained log (`prev_hash`, `row_hash`). Rows are never deleted, never updated. Tamper-evidence is verifiable by a CLI that walks the chain.

6. **Caller identity is bearer-token-with-scope, not username-and-password.** Each caller has an API key issued by `fwd`. The key is mapped in policy to a specific set of `(wallet, contract, method, max_value, rate)` permissions. Compromise of one key cannot exceed that caller's policy.

7. **No `PRIVATE_KEY=` in any AP `.env` file post-migration.** Eliminating that pattern is what `fwd` exists to do. Any commit reintroducing a backend private key into a `.env` file is a regression and must be reverted before merge.

8. **No unseal ceremony.** The sealed-master backend loads its 32-byte AES-256-GCM master from a mode-0600 host file owned by the `fwd` user on each signing operation (zeroized after) — no `docker exec` unseal step, fully unattended on restart.

9. **Single replica.** `fwd` runs as one container. Restart on failure, not failover. The signer is a singleton by design.

10. **Host-agnostic deployment.** `docker-compose.yml` + `.env.example` runs identically on any host with Docker + Docker Compose. No bake of host-specific or IP-specific assumptions into the repo. Host-specific config flows through `.env`, period.

11. **Replacement, not retry-from-zero.** A stuck transaction is resubmitted at the same nonce with bumped `maxPriorityFeePerGas` (×1.125, capped at 5 retries). fwd does not watch the chain (no egress), so the **client** detects the stuck tx and calls `sign-replacement`, which re-signs the **same recorded intent at the same nonce** at the higher tip and **keeps the tx `submitted`**; the client then broadcasts the replacement and reports its receipt via the normal `/receipt` call (which accepts any hash fwd recorded for the tx), confirming the nonce. fwd never hands a reserved nonce to a *different* intent. A reserved nonce is never silently abandoned; it confirms (client `receipt`), is released (client `rejected_releaseable`, tail-only), or surfaces to the operator as an unresolved hole (`GET /v1/admin/nonce/holes`).

12. **Public repo, private config.** `https://github.com/africanproofs/fwd` is the canonical public repo (the build-from-source installer git-clones it). The security model is policy + custody, not concealment. Actual `policy.yaml` values, caller API keys, and the `master.key` sealed master live outside the repo (separate private repo or env-injected / host-provisioned).

13. **Linear forward versioning.** Every ship bumps the next linear patch number in BOTH `pyproject.toml` and `fwd/version.py`. No back-port semver. Main is the only delivery target. Carryover from FICSM Core invariant #8.

14. **Real-infrastructure verification is the validation.** Unit tests with mocked RPCs are necessary but not sufficient — mocks lie. Every signing-path change is verified on real infrastructure before merge. Since fwd makes no RPC call itself, the validation boundary is the **client↔fwd↔chain integration**: a signing-path change is proven by a client broadcasting an fwd-signed tx on a real chain (Coston2) and the report-back driving fwd's state to match the on-chain effect. A defect a mock cannot see is closed by a test on real infrastructure **plus** the doctrine that names its class — never by the point-patch alone (see #19, the deeper rule). Carryover from FICSM.

15. **Operator gates every production migration.** No automated `.env` sweep. Each application's migration to `fwd` (Phase 8 onwards) is its own ship with its own operator approval — even when the code change is mechanical. Migrations are the moments where a mistake translates to lost keys.

16. **Decrypt-on-demand, zeroize-on-completion.** Plaintext private keys are not cached in `fwd`'s process memory between signing operations. Each `/v1/sign-transaction` call decrypts the wallet's privkey via the sealed master (`SealedMaster.decrypt`), wraps the result in a mutable `bytearray`, signs the transaction with `eth-account` from a `bytes()` view of that buffer, and zeroizes the buffer in `finally`. Process-wide privkey caches are forbidden as a regression and are enforced by `tests/unit/test_envelope_signer.py::test_no_32byte_state_after_*` (introspects signer instance state for any 32-byte `bytes`/`bytearray` after each call). The buffer-zeroize contract is enforced by `test_create_wallet_buffer_is_all_zero_after_zeroize` and the sign_transaction equivalent. Combined with `mlockall`-protected process memory (Core invariant #1), this bounds the A3/A4 attack surface for the single-process custody design to the active signing operation. Note: Python's GC may have copied the immutable `bytes` returned by the sealed-master decrypt to other addresses before we wrap in `bytearray`; this best-effort caveat is documented in `architecture.md` § Implementation hazards #2 and accepted in v1. Phase 10's optional `ctypes`-based memory pinning addresses the residual.

17. **Custody is proportionate to the asset class.** `fwd` custodies low-value Flare automation keys (~1000 FLR ≈ tens of USD per key — FTSO-claim / registration / gas wallets, never treasury) on a host that is never publicly exposed. The custody backend is a **sealed local master** (AES-256-GCM, 32-byte key in a mode-0600 host file owned by the `fwd` user). Disaster recovery for this asset class is **regenerate the wallet + on-chain re-authorization** (≈ free), not a distributed-share ceremony. The master-key file is `policy.yaml`-class private config (Core invariant #12 — gitignored, never in repo/image, operator-provisioned via `clifwd master generate`). If the master file is suspected compromised: regenerate it, re-seal every wallet, re-authorize on-chain. The Core #7 "structurally indistinguishable from `.env PRIVATE_KEY=`" test binds: the master file MUST be 0600/owned and never committed. **[Flag — DR mechanic unverified:** the exact on-chain step to restore claim execution after wallet regeneration is `ClaimSetupManager.setClaimExecutors` re-authorization of the new executor (NOT recipient rotation); this DR path is not yet verified end-to-end and is confirmed at the production cutover.] **FSP signing-policy key:** the FSP signing-policy key is custodied under the same sealed master and produces valid EIP-191 votes the `FlareSystemsManager` recovers. Its recovery is **not "free"** — it depends on on-chain signing-policy re-registration. On-chain FSP-protocol acceptance is **demonstrated** (reward epoch 404: our key's `RewardsSigned` events landed and the epoch finalized on Flare + Songbird, then the rewards were claimed, all unattended — the imported key is an accepted on-chain registered voter; `docs/history/1.1.0a96-*.md`). A compromise can still produce valid FSP signatures until detected and the key is rotated + re-registered — see the FSP signing-policy key compromise/rotation runbook in `docs/restore-runbook.md`.

18. **Doctrine and code do not drift; current-state docs describe the present only.** The current-state docs — `CLAUDE.md`, `README.md`, `architecture.md`, `threat-model.md`, `dependencies.md` — describe the code as it is now: present tense, no "was X / used to / retired / superseded / fixed in vX" archaeology, no version-by-version narrative, no references to deprecated or discarded designs. When the code changes, the current-state docs are **rewritten to the new present** — the old wording is replaced, not annotated-as-superseded. Every current-state claim either describes existing code/config behaviour OR is explicitly marked deferred to a named phase that will make it true; drift (a current-state doc claiming something the code does not do) is forbidden, surfaced by audit, and fixed by rewriting the doc to the present — never tolerated as "we'll fix it later". The project's history — how it evolved, why decisions were made, what was tried and abandoned — lives ONLY in the quarantined historical record: `docs/history/` (per-version ship narratives + `SHIP-LOG.md`, append-only — Core invariant #13) and `docs/decisions.md` (the append-only decision log). A reader of the current-state docs learns what `fwd` IS and never time-travels; a reader who wants the why/evolution goes to the history files. Why this matters: `fwd`'s value rests on doctrine being trustworthy AND readable — a current-state doc buried in archaeology is as useless as one that is partial fiction. (Amended v1.1.0a22 — operator directive; `decisions.md` D21.)

19. **Forensic audit rows survive the failure they record.** An audit-log row that explains a *denied*, *errored*, or *aborted* operation MUST be durably committed independently of — and is never unwound by — the transaction whose rollback that same failure triggers. The forbidden anti-pattern: append the forensic row to the shared `RequestScope`/`AdminScope` session, then `raise`, letting the exception propagate through `fwd.infra.db.session_scope` whose `except Exception: rollback` discards the row. In `fwd` this is enforced by **commit-before-raise on the single shared session**: every exception arm that writes a `sign-transaction` / `wallet-*` / `caller-*` / `policy-load` row calls `await audit_repo.commit()` (`app/sign_transaction.py`) or `await session.commit()` (`main.py::_startup_policy_load`, before `SystemExit(1)`) before re-raising. It MUST be the already-open session — a second `session_scope` for the forensic write re-introduces a two-session `BEGIN IMMEDIATE` writer-lock deadlock. The commit also leaves the failure path's *operational* end-state correct: a **deny** keeps its rate increment (the attempt is counted; deny does not release); a **pre-sign** failure's explicit nonce/rate releases run before the commit so the net is zero. The approved path is unaffected (no exception → `session_scope` commits once → atomicity of the approved row with nonce+tx+rate preserved). Enforcement is a regression test that drives the **real** `session_scope` rollback with a self-validating without-commit control (a mocked session is structurally blind to this). **Why this is critical:** the row exists to answer "what was refused or failed, and why" — losing it on the very path it documents is a silent, total failure of Core invariant #5 (append-only audit) and the accountability #2/#3 rest on, invisible to every unit test, and a reopening of the exact gap `fwd` exists to close. **The deeper rule (why this is an invariant, not a patch):** a defect found is a defect *class* — it is closed only when the class is named in doctrine AND guarded by a test that fails for the class on real infrastructure; an instance-patch without both is a deferral of the next instance. (Partners with Core invariant #14.)

## Development workflow — Opus prescribes, Sonnet implements with deviation license, Opus reviews with overwrite authority

Four roles in deliberate tension. Carryover from FICSM § Development workflow, abbreviated.

### Reviewer (Opus 4.7) — PRESCRIBES

Drafts the canonical prompt for each ship: file paths, exact contents, drift rules, test deltas, verification block. Reviewer authority is *what `fwd` should be after this ship*.

Reviewer obligations:
- Phase 0: read code, verify codebase semantics, surface design questions to operator.
- Draft a self-contained canonical prompt at `~/.claude/plans/fwd-canonical-prompt-<ship>.md`.
- **Per-ship doctrine surface (v1.0.0; feature ships):** verify a **feature ship** touches ONLY (1) `docs/history/<version>-*.md`, (2) one `docs/history/README.md` line, (3) the one CLAUDE.md § Scope *current-state* line — and reject any per-version § Scope paragraph as Core-#18 drift. **Constitutional-amendment** and **bounded post-verification reconciliation** ships have their own defined bounded surfaces and are verified against those, not the 3-artifact feature cap (see § Linear-forward versioning).
- Pre-handoff scan: shell-var substitution defects, identifier-rename completeness, multi-segment `bash -c` wrapping (FICSM Core invariant #19).
- **Demarcate every hand-off in canonical prompts with EXACTLY this format — no variations:**
    1. **A bold marker on its own line**: `**HAND-OFF — <recipient> (paste verbatim into <destination>):**`
    2. **A blank line.**
    3. **A fenced code block** wrapping the entire hand-off payload end-to-end (use 4 backticks if the payload contains 3-backtick blocks; 5 backticks if nested deeper). **Nothing outside the fences belongs to the hand-off.**

  Pre-handoff scan (mandatory, runs against the canonical prompt before announcing it ready):
  ```sh
  grep -c '^\*\*HAND-OFF — ' ~/.claude/plans/fwd-canonical-prompt-<ship>.md  # ≥ 1
  ```
  AND a manual eyeball: the line immediately after the bold marker is empty; a fenced block opens within the next 3 lines and closes before any non-handoff content resumes.

  **Why this is enforced.** A Sonnet session pasted from "go look at this paragraph here" rather than "copy these exact bytes between these fences" is a recurring source of subtle deviations (truncation at paragraph boundaries, accidentally-included Reviewer-aside text, missed instructions buried in surrounding prose). The fence is a hard boundary the operator can copy verbatim with zero ambiguity. **No exceptions** — even a one-line hand-off goes inside fences. Every canonical prompt at `~/.claude/plans/fwd-canonical-prompt-*.md` MUST satisfy this; a prompt missing the demarcation is incomplete and must not be handed off.

- **The hand-off is ONE self-contained markdown FILE that is itself the complete, ready-to-paste message to the recipient (operator directive 2026-05-19, clarified after two misdeliveries; `docs/decisions.md` D18 — supersedes the prior "point at the file, do not dump contents" rule).** The Reviewer authors exactly one `~/.claude/plans/<name>.md` whose **entire contents** are what the operator copies wholesale into the other agent. The Reviewer's deliverable to the operator is **the file path plus "open it, select all, paste"** — nothing else; the message is never assembled in, or pasted out of, the chat reply. That single file MUST contain, in order:
    1. A 2–4 line framing preamble at the very top: name the recipient; state that the rest of this file is the authoritative spec end-to-end; restate the operating boundary (an implementer doesn't commit / bump version / edit `CLAUDE.md`, `pyproject.toml`, `src/fwd/version.py`, `docs/`; Reviewer commits; for a peer/consumer agent, the equivalent boundary); end the preamble with a "Begin" line.
    2. Immediately below it, the full spec body. Nothing the recipient must read lives outside this one file; deviation-surfacing per the spec's final-report format is required.

  Forbidden — each is a real misdelivery that occurred 2026-05-19: (a) a pointer-only message that merely names the path for the recipient to open (fragile — broke when the file was not where the recipient expected); (b) the message dumped inline into the chat reply inside a fence (forced the operator to hand-extract it from Reviewer prose — explicitly rejected); (c) two files (a prompt file plus a separate wrapper) — one file only, no duplicated content, single source of truth.

  The Reviewer writes the wrapper bespoke for each ship — it is short (10-20 lines), names the specific version + one-line description, and is presented to the operator immediately after the canonical prompt file is announced ready.

  **Why this is enforced (reconciled, D18).** The prior rule pointed the recipient at a file to avoid dumping a long Reviewer-internal document whose asides could be mis-read as instructions. That rationale is already neutralised by the standing requirement that the prompt body be fully self-contained (root constitution — no back-reference, no Reviewer-aside outside the spec). Three delivery forms were tried and the first two failed in practice (2026-05-19): a pointer-only message broke because it assumed the operator placed the file where the recipient expected; the message dumped inline into the chat reply forced the operator to manually select it out of surrounding Reviewer prose. The fix that holds: the hand-off is itself one file, and the only thing handed to the operator is its path — open, select-all, paste, one action, zero extraction, zero file-placement dependency. Applies to EVERY hand-off — Sonnet implementer and peer/consumer Opus agents alike. A hand-off delivered as a path-pointer, or assembled in the chat reply, or split across two files = not done right.

### Implementer (Sonnet 4.6) — IMPLEMENTS, WITH LICENSE TO DEVIATE

Reads the canonical prompt cold (no Opus chat history) and executes. Sonnet does NOT execute verbatim if doing so would produce wrong code.

Legitimate deviation (Sonnet adapts AND reports):
- Spec asserts a literal that grep reveals is a shell variable.
- Call site requires a parameter Sonnet discovers during integration.
- Edge case Sonnet uncovers naturally produces a different test count.
- Spec contains a typo.

Illegitimate deviation (REJECT):
- "While I'm here" refactors of unrelated code.
- Adding features the spec didn't request.
- Skipping spec items.
- Improvising a custom workaround when the spec has no path → STOP and surface to operator.

Sonnet obligations: faithful where spec matches reality, narrowest correct adaptation where it doesn't, every deviation reported in the "Open questions / surprises" section, never hidden, never claim spec was followed when it was adapted. Sonnet does NOT commit. Reviewer commits.

### Reviewer at verification — INSISTS, MAY OVERWRITE

After Sonnet's report, file-by-file Read pass (NOT just `git diff`). Authority at this stage is binding:

- **Accept:** sound deviation, common case.
- **Path (a) — Correct in place:** short corrective directive in same Sonnet session for tiny fixes (typo, missed import).
- **Path (b) — Overwrite:** wholesale revert + rewrite canonical prompt + fresh Sonnet session.
- **Path (c) — Inline tweak:** ONLY for non-behavioural adjustments. NEVER for logic.

### Operator (human) — DRIVES, GATES

Gives intent, gates plans + canonical prompts, approves production migrations, holds the `master.key` sealed master and operator secrets. May override the reviewer's commit at any time. Operator authority is supreme.

Commits are authored solely by the operator — **no trailer at all**, regardless of Sonnet/Opus/Reviewer involvement.

Role attribution (which agent did what) lives in the `docs/history/<version>-*.md` ship record, never in git metadata.

## Behavioural guidelines

Carryover from FICSM § Behavioural guidelines (after Karpathy's principles, via [forrestchang/andrej-karpathy-skills](https://github.com/forrestchang/andrej-karpathy-skills)).

1. **Think before coding.** Don't assume. Don't hide confusion. Surface tradeoffs. State assumptions explicitly, present alternatives, push back when a simpler approach exists.
2. **Simplicity first.** Minimum code that solves the problem. Nothing speculative. No features beyond what was asked, no abstractions for single-use code, no error handling for impossible scenarios. The "What FWD IS NOT" list operationalizes this for fwd-specific scope.
3. **Surgical changes.** Touch only what you must. Don't "improve" adjacent code, don't refactor what isn't broken, match existing style. Every changed line traces to the canonical prompt or a Sonnet-surfaced legitimate deviation.
4. **Goal-driven execution.** Define success criteria. Loop until verified. Every fwd canonical prompt's verification block is the strong criterion for that ship.

## Linear-forward versioning

Per Core invariant #13: every ship bumps the next linear patch number in BOTH `pyproject.toml` and `fwd/version.py`. No back-port semver. **Commit-message form is governed by the root `proofs.africa/CLAUDE.md` NON-NEGOTIABLE rule (codified 2026-05-16, reconciled into fwd doctrine at v0.5.0 per Core invariant #18): a single terse conventional-commit line — type + generic verb only (`docs: update`, `feat: update`, `fix: update`, …) — no body, no bullets, no rationale, no scope, no file/feature specifics, no "why". The back-reference, deviation log, and full ship narrative live in `docs/history/<version>-*.md` (indexed in `docs/history/README.md`), never in the commit message.**

**Per-ship doctrine surface (instituted v1.0.0 — the corpus-bloat remedy; fourth independent audit B-verdict).** A ship updates exactly three doctrine artifacts and no more: (1) `docs/history/<version>-*.md` (the canonical full narrative), (2) one line in `docs/history/README.md` (the version index), (3) the single CLAUDE.md § Scope *current-state* line (current / next / blocked only). **No ship appends a per-version paragraph to CLAUDE.md § Scope** — the verbatim per-version narrative lives only in `docs/history/` (`SHIP-LOG.md` is the frozen, never-grown v0.1.0→v1.0.0a3 relocation; a new version adds only its deep file + one index line). A fat § Scope paragraph is drift (Core invariant #18) and is rejected at Reviewer verification. This kills the bloat generator and the recurring "§ Scope silently stopped at vX.Y" drift the audits caught repeatedly.

**Constitutional-amendment & bounded-reconciliation ship-types (instituted v1.1.0a3 — operator-authorized constitutional act 2026-05-19; `docs/decisions.md` D17).** The 3-artifact cap above governs **feature ships**. Two non-feature ship-types have their own *defined, bounded* surfaces and are NOT rejected at Reviewer verification for exceeding three artifacts:

- **Constitutional-amendment ship.** Amends this CLAUDE.md's process/invariant doctrine itself. Bounded surface: the amended CLAUDE.md section(s) + a `docs/decisions.md` D-record + the three feature-ship artifacts (history file, README line, § Scope current-state line) + the two version files. It is self-ratifying (the amendment ship is governed by the definition it introduces; the self-reference is recorded honestly in its D-record, Core invariant #18) and must be explicitly operator-authorized — it is **never** a Reviewer self-grant. v1.1.0a3 is the genesis instance (this paragraph).

- **Bounded post-verification reconciliation ship.** Reconciles invariant *text* to code that a *prior, already-shipped, byte/GATE-verified* ship made true (e.g. a Step-0/GATE-verified primitive). Constrained to: **(i)** only invariant text the just-shipped, byte-verified code makes true — nothing speculative, nothing GATE-pending; **(ii)** every reconciled edit annotated inline `(code in ship vX.Y.ZaN makes this true)`; **(iii)** NO § Scope narrative paragraph — the corpus-bloat the per-ship rule kills stays killed; **(iv)** ONE coherent ship — the reconciliation is never fragmented across versions (fragmentation creates Core-#18 partially-true doctrine states on main). Bounded surface: the reconciled invariant lines (CLAUDE.md / `docs/decisions.md` / `docs/architecture.md` / `docs/threat-model.md`) + a D-record + the three feature-ship artifacts + the two version files. It cannot ship until the verification gate of the ship whose code it reconciles has passed. Reusable for every future Step-0/GATE-verified phase (9a-iii, 9b, 9c, 10x) without re-authorization.

Neither ship-type relaxes Core invariant #18 (no silent drift; honest history) — each *narrows* it by forcing the reconciliation into one annotated, operator-visible, gate-anchored ship instead of leaking partial truth across feature ships.
