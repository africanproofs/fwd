# fwd — Flare Wallet Daemon

> Policy-gated signing service for African Proofs' EVM backend keys. Custody-first; substrate-minimal; Anthropic agents are first-class callers. The redesign of `keosd` for autonomous agents on Flare in 2026.

## Identity

`fwd` holds AP's automation private keys AES-256-GCM-sealed under a 32-byte master key kept in a mode-0600 host file (loaded once at startup; v1.0.0a1 retired the HashiCorp Vault backend — see `decisions.md` D1); decryption and signing happen in `fwd`'s own process, gated by declarative policy and recorded in an append-only audit log. Every `.env PRIVATE_KEY` line in AP backends — `ftso-fee-claimer`, `apregister/`, `apcli`, future `fics` write paths, future Claude agents — calls `fwd` instead of holding keys directly.

The custody property `fwd` rests on: **the 32-byte AES-256-GCM master key exists only in a mode-0600 host file owned by the `fwd` user (never in the repo or image — Core invariant #12); each wallet private key is envelope-encrypted at rest under it and exists as plaintext in `fwd`'s process memory only during the bounded signing operation, after which the buffer is zeroized (Core invariant #16).** This is the v1.0.0a1 custody model, proportionate to the asset class (low-value Flare automation keys; the host is never publicly exposed — Core invariant #17). HashiCorp Vault was retired at v1.0.0a1; the prior Vault-Transit-envelope design and the reasons it was chosen then abandoned are honest history in `decisions.md` D1.

The workflow doctrine below is settled — transferred verbatim from FICSM (`../ficsm/CLAUDE.md` § Development workflow), where it was earned through FICS' five-month design cycle and the S0+S1+S2 hardware sealing on 2026-04-25. `fwd` inherits the operating discipline, not the substrate; the substrate (single-purpose signing service vs multi-stratum control plane) is fwd's own.

## What FWD Deliberately IS NOT

These are not in scope until a real consumer or proven need surfaces. Re-introducing any requires explicit operator authorization tied to a concrete consumer:

- **Not a user wallet.** Frontends (`apregister-web`, `proofs-website`) keep thirdweb v5. fwd is for *backend automation*, not user flows.
- **Not multi-chain beyond EVM Flare-family.** Flare, Songbird, Coston2 only. No Bitcoin, Solana, Cosmos, Antelope.
- **Not clustered, not HA, not horizontally scalable.** A signer is a coherence boundary, not a scaling unit. One container, one wallet set, one nonce manager per (wallet, chain).
- **No K8s, no Pulumi, no Helm.** `docker-compose.yml` is the deployment artifact. K3s exists in AP infra but `fwd` does not run on it.
- **Not a broadcaster (v1.1.0a9).** fwd signs and allocates nonces; **clients broadcast** the signed tx and report the outcome back (`/v1/transactions/{tx_id}/broadcast-result`, `/receipt`). fwd never calls `eth_sendRawTransaction`.
- **No network egress at all (v1.1.0a9/a11).** fwd makes **no outbound connection** — code-level: no RPC/`httpx` client in `app|api|infra`; network-level: the `internal: true` compose network gives the container no internet route (verified — a container on that network cannot reach `flare-api.flare.network:443`). Inbound only, from callers on the `internal: true` Docker bridge (`http://fwd:8080`); **there is NO host port** — `internal: true` removes host→container publishing (corrected v1.1.0a15 after the a14 cutover surfaced the a11 error), so admin runs via `docker exec fwd clifwd …`. No `signer.proofs.africa` DNS. (Supersedes the v1 "No public network exposure" wording — fwd is now egress-free, not merely ingress-restricted.)
- **No autonomous policy.** Every rule is declarative YAML. The LLM never decides whether to sign.
- **No web UI.** HTTP API + a thin CLI for admin operations. No dashboard.
- **No multi-signer / threshold / MPC in v1.** Single Vault, single key per wallet.
- **No HSM hardware in v1.** YubiHSM 2 is a Phase 10 option.
- **No `web3.py`.** `eth-account` + `httpx` cover the signing path with a fraction of the dependency tree.
- **No raw-digest signing.** The arbitrary-raw-digest endpoints `/sign-message` and `/sign-typed-data` (free caller-supplied digest) are deferred (Phase 10 — NOT mounted), and arbitrary `eth_sign`-style raw-digest endpoints will never exist. `src/fwd/main.py` mounts two signing routes: `/v1/sign-and-send` and (v1.1.0a2) `/v1/sign-fsp-message`. The latter is **not** a raw-digest endpoint — it is EIP-191 `personal_sign` over a 32-byte messageHash fwd **reconstructs** from typed FSP fields (the caller supplies no digest); this "will never exist" statement therefore stays literally true. (The prior "exist" wording was Core #18 drift, reconciled v0.5.5; the "mounts only `/v1/sign-and-send`" wording was v1.1.0a2 drift, reconciled v1.1.0a5 — *code in v1.1.0a1/a2, live-Coston2-proven by the v1.1.0a4 drill, makes this true*.)
- **No long-lived caller credentials issued by humans.** Caller API keys are minted by `fwd` itself, scoped per policy, rotatable from the CLI.

## Core invariants

1. **Keys never persist plaintext.** Each wallet's secp256k1 private key is generated externally (secure RNG), envelope-encrypted with AES-256-GCM under a 32-byte master key held in a mode-0600 host file (`SealedMaster`, `src/fwd/infra/sealed_master.py`; v1.0.0a1 retired Vault Transit — `decisions.md` D1), and stored as `seal:v1:<ciphertext>` in SQLite. Plaintext keys exist in `fwd`'s process memory only during the bounded signing operation and are zeroized in-place on the mutable `bytearray` after each signature. **Process memory is locked against swap via `mlockall(MCL_CURRENT | MCL_FUTURE)` at lifespan startup (`src/fwd/main.py::lifespan`).** Because the `fwd` container runs as non-root user `fwd` (uid 1000) per the Dockerfile, the actual mechanism that allows `mlockall` to succeed is `ulimits.memlock: -1` (unlimited `RLIMIT_MEMLOCK`) in `docker-compose.yml`; the additional `cap_add: [IPC_LOCK]` is kept for defense-in-depth (lands the capability in the bounding set so a future root entrypoint or ambient-capability scenario benefits). Verifiable live via `docker exec fwd grep VmLck /proc/1/status` returning a non-zero kB value. mlock prevents the kernel from paging plaintext key buffers to `/swapfile`; it does **not** prevent core dumps, `/proc/$pid/mem` reads by privileged processes on the host, or in-process Python GC copies of the original immutable `bytes` returned by the sealed-master decrypt before our `bytearray` wrap (Phase 10's optional `ctypes`-based memory pinning addresses the latter). Compromise of `fwd` while running, OR host read access to BOTH the mode-0600 master-key file AND the SQLite ciphertexts, grants the attacker the ability to recover all wallet plaintext keys; offline theft of the SQLite ciphertexts WITHOUT the master-key file yields ciphertext only. There is no separate key-management process boundary — this is the deliberate v1.0.0a1 trade-off for low-value Flare automation keys (≈ tens of USD/key) on a host that is never publicly exposed (`decisions.md` D1; `threat-model.md` A4). (Supersedes the v0.1.2 Vault-Transit-envelope design, itself a pivot from the originally-intended Vault signing, infeasible because Vault has no secp256k1 Transit key type.)

2. **Default-deny.** Every signing request is denied unless policy explicitly permits caller × wallet × contract × method × value × rate. New callers and new wallets enter with zero capabilities.

3. **Sign intent, never opaque bytes.** fwd signs ABI-decoded transactions OR EIP-191 personal-signed structured protocol messages whose 32-byte body fwd reconstructs from policy-checked typed fields — callers never supply a raw digest. Every `/v1/sign-transaction` request (the zero-egress sign-only endpoint, v1.1.0a9; was `/v1/sign-and-send`) must decode to a known ABI shape against the policy-bound contract; every `/v1/sign-fsp-message` request reconstructs the FSP messageHash from typed fields (message type, reward epoch id, and for REWARD_DISTRIBUTION the claims tuple + rewards hash) — no caller-supplied opaque hash. Unparseable calldata / an unknown message type = refuse. fwd signs and returns the intent it decoded; it never broadcasts (the client does) — the model is *strengthened*, not weakened, by removing the broadcast surface. Safety rests on byte-verified preimages + the EIP-191 domain prefix + address-level key-domain segmentation. The audit log records the decoded human-readable intent (or, for FSP, the reconstructed messageHash + emitted v,r,s), not a raw opaque digest. *(The EIP-191 clause: code in v1.1.0a1/a2 makes this true — byte-verified at Step 0 and proven on live Coston2 by the v1.1.0a4 drill; the real FlareSystemsManager recovers fwd's EIP-191 signer. `docs/reviews/v1.1.0a4-clif-fsp-live-drill-adjudication.md`.)*

4. **One nonce manager per (wallet, chain).** SQLite `BEGIN IMMEDIATE` serializes nonce reservation. Concurrent signing requests against the same wallet cannot collide. **(v1.1.0a9 zero-egress — D20):** fwd remains the single nonce *reservation* authority, and `reserve_next` under `BEGIN IMMEDIATE` is the only nonce operation fwd performs — it is purely local (no network). fwd does **not** seed or reconcile nonces from chain (it has no egress): the initial seed is the admin `nonce-init` endpoint (a8), and reconciliation is client-fed chain-truth via the admin, bounded-monotonic `nonce-sync` endpoint (a13). A reserved nonce is released on a client-reported `rejected_releaseable` broadcast outcome (tail-only; non-tail gaps surface as operator-visible drift via `nonce/holes`), kept on `rejected_nonce_too_low` (chain is ahead → nonce-sync), and confirmed on a client-reported receipt.

5. **Append-only audit log.** Every request, decision, signature, and broadcast outcome is recorded in a hash-chained log (`prev_hash`, `row_hash`). Rows are never deleted, never updated. Tamper-evidence is verifiable by a CLI that walks the chain.

6. **Caller identity is bearer-token-with-scope, not username-and-password.** Each caller has an API key issued by `fwd`. The key is mapped in policy to a specific set of `(wallet, contract, method, max_value, rate)` permissions. Compromise of one key cannot exceed that caller's policy.

7. **No `PRIVATE_KEY=` in any AP `.env` file post-migration.** Eliminating that pattern is what `fwd` exists to do. Any commit reintroducing a backend private key into a `.env` file is a regression and must be reverted before merge.

8. **No unseal ceremony (v1.0.0a1).** The sealed-master backend loads its 32-byte AES-256-GCM master from a mode-0600 host file owned by the `fwd` user at startup — no Vault, no Shamir, no `docker exec` unseal step, fully unattended on restart. (Superseded the Phase 3a–7 Vault 3-of-5 Shamir model when Vault was retired — `decisions.md` D1, the asset-class rationale; honest history of the prior model lives there.)

9. **Single replica.** `fwd` runs as one container. Restart on failure, not failover. The signer is a singleton by design.

10. **Host-agnostic deployment.** `docker-compose.yml` + `.env.example` runs identically on any host with Docker + Docker Compose. No bake of Scaleway / ap-ftso-02 / IP-specific assumptions into the repo. Host-specific config flows through `.env`, period.

11. **Replacement, not retry-from-zero.** Stuck transactions are resubmitted with the same nonce and bumped `maxPriorityFeePerGas` (× 1.125, capped at 5 retries). **(v1.1.0a9/a13 zero-egress — D20):** the *trigger* is now the **client** (fwd has no receipt watcher and no egress): the client detects a stuck tx and calls `sign-replacement` (a13), which re-signs the **same recorded intent at the same nonce** at the higher tip. The reclaim mechanic is **same-intent replacement + operator alarm — fwd never hands a reserved nonce to a *different* intent.** A reserved nonce is never silently abandoned; it confirms (client `receipt`), replaces (client `sign-replacement`), is released (client `rejected_releaseable`, tail-only), or surfaces to the operator as an unresolved hole (`GET /v1/admin/nonce/holes`).

12. **Public repo, private config.** `gitlab.com/proofs.africa/fwd` is public. The security model is policy + custody, not concealment. Actual `policy.yaml` values, caller API keys, Vault unseal shares, and Litestream credentials live outside the repo (separate private repo or env-injected on the host).

13. **Linear forward versioning.** Every ship bumps the next linear patch number in BOTH `pyproject.toml` and `fwd/version.py`. No back-port semver. Main is the only delivery target. Carryover from FICSM Core invariant #8.

14. **Real-RPC verification is the validation.** Unit tests with mocked RPCs are necessary but not sufficient. Every signing-path change must be verified against a live Coston2 RPC before merging to the production-flow code. Mocks lie. Carryover from FICSM Core invariant #13. The **v0.4.5 concurrency bug** and the **v0.5.2 deny-audit bug** (Core invariant #19) are the canonical proofs: both were unit-green, both were structurally invisible to mocked tests, both were caught only by the operator-driven live drill, and both would otherwise have reached the v1.0.0 production migration. A defect a mock cannot see is closed by a test on real infrastructure **plus** the doctrine that names its class — never by the point-patch alone (see #19, the deeper rule). **(v1.1.0a9 zero-egress — D20):** fwd's own code no longer makes any RPC call, so the validation boundary moves to the **client↔fwd↔chain integration** — a signing-path change is proven by a client broadcasting an fwd-signed tx on real Coston2 and the report-back driving fwd's state to match the on-chain effect. The **v1.1.0a12 funded live drill** (tx `0x14440b…95cbd`, Coston2 block 31,028,196, status 1 → fwd `mined`) is the canonical instance: it caught the non-checksummed-`to` `TypeError` nonce-wedge — invisible to every mocked test, surfaced only on the live path. "Mocks lie" holds exactly as before; only the locus of the live test shifted from fwd to the client integration.

15. **Operator gates every production migration.** No automated `.env` sweep. Each application's migration to `fwd` (Phase 8 onwards) is its own ship with its own operator approval — even when the code change is mechanical. Migrations are the moments where a mistake translates to lost keys.

16. **Decrypt-on-demand, zeroize-on-completion.** Plaintext private keys are not cached in `fwd`'s process memory between signing operations. Each `/v1/sign-and-send` call decrypts the wallet's privkey via the sealed master (`SealedMaster.decrypt`), wraps the result in a mutable `bytearray`, signs the transaction with `eth-account` from a `bytes()` view of that buffer, and zeroizes the buffer in `finally`. Process-wide privkey caches are forbidden as a regression and are enforced by `tests/unit/test_envelope_signer.py::test_no_32byte_state_after_*` (introspects signer instance state for any 32-byte `bytes`/`bytearray` after each call). The buffer-zeroize contract is enforced by `test_create_wallet_buffer_is_all_zero_after_zeroize` and the sign_transaction equivalent. Combined with `mlockall`-protected process memory (Core invariant #1), this bounds the A3/A4 attack surface for the v0.1.2 single-process custody design to the active signing operation. Note: Python's GC may have copied the immutable `bytes` returned by the sealed-master decrypt to other addresses before we wrap in `bytearray`; this best-effort caveat is documented in `architecture.md` § Implementation hazards #2 and accepted in v1. Phase 10's optional `ctypes`-based memory pinning addresses the residual.

17. **Custody is proportionate to the asset class (v1.0.0a1).** `fwd` custodies low-value Flare automation keys (~1000 FLR ≈ tens of USD per key — FTSO-claim / registration / gas wallets, never treasury) on a host that is never publicly exposed. The custody backend is therefore a **sealed local master** (AES-256-GCM, 32-byte key in a mode-0600 host file owned by the `fwd` user), NOT HashiCorp Vault. The Vault container + Transit + 3-of-5 Shamir-across-failure-domains + the production wipe-and-redo ritual were **retired at v1.0.0a1**: two independent audits (`docs/reviews/v0.5.4-*`, `v0.5.5-*`) found the doctrine/ops weight disproportionate to the asset class, and Vault's one differentiator over a sealed master — an independent decrypt-audit-trail against a track-covering attacker — was worthless at this value/exposure and was never even enabled (v0.5.5 audit OE-2). Disaster recovery for this asset class is **regenerate the wallet + on-chain `setClaimRecipient` rotation** (≈ free), not a distributed-share ceremony. The master-key file is `policy.yaml`-class private config (Core invariant #12 — gitignored, never in repo/image, operator-provisioned via `clifwd master generate`). If the master file is suspected compromised: regenerate it, re-seal every wallet (Phase 7 rotation flow), rotate on-chain recipients. (Instituted v1.0.0a1; supersedes the prior Vault-Shamir #17, which governed Phase 3a–7 Vault dev — honest history in `decisions.md` D1. The Core #7 "structurally indistinguishable from `.env PRIVATE_KEY=`" test still binds: the master file MUST be 0600/owned and never committed.) **[Flag — DR mechanic unverified (v1.0.0, fourth-audit F-class):** the exact on-chain step to restore claim execution after wallet regeneration is `ClaimSetupManager.setClaimExecutors` re-authorization of the new executor (NOT recipient rotation); this DR re-authorization path is NOT Reviewer-verified end-to-end — the v1.0.0 Coston2 rehearsal proved claim-*execution* custody, not DR rotation — and is confirmed at the production cutover. The `setClaimRecipient` wording above is retained as originally written and flagged, not rewritten, per Core invariant #18 (no rewriting an unverified mechanic into security doctrine).] **FSP signing-policy hot key (v1.1.0a5 reconciliation):** the v1.1.0a1/a2 FSP code custodies the signing-policy key under the same sealed master; the v1.1.0a4 live Coston2 drill proved it produces valid EIP-191 votes the real `FlareSystemsManager` recovers. Proportionality holds for this key too, but its recovery is **not "free"** — it depends on verified on-chain signing-policy re-registration (the Coston2 drill established **P3=NO**: the fwd-generated key is not yet a registered voter; `signUptimeVote` reverts `'invalid signing policy address'` *after* recovering fwd's signer — `docs/reviews/v1.1.0a4-clif-fsp-live-drill-adjudication.md`), and a compromise can produce valid FSP signatures until detected and the key is rotated + re-registered. (*Code in v1.1.0a1/a2, drill-proven v1.1.0a4, makes this true; on-chain FSP-protocol acceptance is explicitly deferred — GATE-1 F2 / P3=NO.*)

18. **Doctrine and code do not drift.** Every claim in `CLAUDE.md`, `decisions.md`, `architecture.md`, and `threat-model.md` either describes existing code/config behaviour OR is explicitly marked deferred to a named phase that will make it true. When code drifts from doctrine, ship the code that makes the doctrine true; when doctrine drifts from reality, rewrite the doctrine to admit what the code actually does — but never let the two disagree silently. Every audit cross-references doctrine claims to code (the v0.3.1 audit at `docs/reviews/` is the canonical example); drift is the easiest finding to surface and the cheapest to fix early. Drift is detected by audit; drift is fixed by aligning one to the other; drift is **never** tolerated as "we'll fix it later" without an explicit deferred-phase marker. Why this matters: `fwd`'s value rests on doctrine being trustworthy. If Core invariant #X is partial fiction, every future agent reading `CLAUDE.md` operates on a softer foundation than they think, and every higher layer (Phase 4 caller auth, Phase 7 policy + audit, Phase 8 production migration) inherits that softness. The audit at v0.3.1 surfaced four documentation-vs-implementation gaps that had silently accumulated; v0.3.2 closed them and instituted this invariant to prevent recurrence.

19. **Forensic audit rows survive the failure they record.** An audit-log row that explains a *denied*, *errored*, or *aborted* operation MUST be durably committed independently of — and is never unwound by — the transaction whose rollback that same failure triggers. The forbidden anti-pattern: append the forensic row to the shared `RequestScope`/`AdminScope` session, then `raise`, letting the exception propagate through `fwd.infra.db.session_scope` whose `except Exception: rollback` discards the row. In `fwd` this is enforced by **commit-before-raise on the single shared session**: every exception arm that writes a `sign-and-send` / `wallet-*` / `caller-*` / `policy-load` row calls `await audit_repo.commit()` (`app/sign_and_send.py`'s three arms) or `await session.commit()` (`main.py::_startup_policy_load`, before `SystemExit(1)`) before re-raising. It MUST be the already-open session — opening a second `session_scope` for the forensic write re-introduces the v0.4.5 two-session `BEGIN IMMEDIATE` writer-lock deadlock. The commit additionally makes the failure path's *operational* end-state doctrinally correct rather than whatever a blanket rollback yields: a step-8/9 **deny** keeps its D14 rate increment (the attempt is counted; deny does not release); a **pre-broadcast** failure's explicit nonce/rate releases run before the commit so the net is zero; a **broadcast** failure keeps the reserved nonce (the tx may be in mempools — the receipt watcher decides). The approved path is unaffected (no exception → `session_scope` commits once → D16 atomicity of the approved row with nonce+tx+rate preserved). Enforcement is a regression test that drives the **real** `session_scope` rollback with a self-validating without-commit control (a mocked session is structurally blind to this — that blindness is precisely why the defect shipped at v0.5.0a6 in `main.py`, was point-fixed during the a7 Reviewer pass, **silently recurred at v0.5.2 in `sign_and_send.py`**, and was caught only by the Phase 7 GA live drill three ships later). **Why this is critical:** the row exists to answer "what was refused or failed, and why" — losing it on the very path it documents is a silent, total failure of Core invariant #5 (append-only audit) and the accountability #2/#3 rest on, invisible to every unit test, and a reopening of the exact gap `fwd` exists to close — a signer that refuses correctly but keeps no record of refusals. **The deeper rule (why this is an invariant, not a patch):** a defect found is a defect *class* — it is closed only when the class is named in doctrine AND guarded by a test that fails for the class on real infrastructure; an instance-patch without both is a deferral of the next instance, and the v0.5.0a6→v0.5.2 recurrence is the proof. (Instituted at v0.5.4 after the Phase 7 GA drill surfaced the recurrence; partners with Core invariant #14.)

    1. **A bold marker on its own line**: `**HAND-OFF — <recipient> (paste verbatim into <destination>):**`
    2. **A blank line.**
    3. **A fenced code block** wrapping the entire hand-off payload end-to-end (use 4 backticks if the payload contains 3-backtick blocks; 5 backticks if nested deeper). **Nothing outside the fences belongs to the hand-off.**

  Pre-handoff scan (mandatory, runs against the canonical prompt before announcing it ready):
  ```sh
  grep -c '^\*\*HAND-OFF — ' ~/.claude/plans/fwd-canonical-prompt-<ship>.md  # ≥ 1
  ```
  AND a manual eyeball: the line immediately after the bold marker is empty; a fenced block opens within the next 3 lines and closes before any non-handoff content resumes.

  **Why this is enforced.** A Sonnet session pasted from "go look at this paragraph here" rather than "copy these exact bytes between these fences" is a recurring source of subtle deviations (truncation at paragraph boundaries, accidentally-included Reviewer-aside text, missed instructions buried in surrounding prose). The fence is a hard boundary the operator can copy verbatim with zero ambiguity. **No exceptions** — even a one-line hand-off goes inside fences. Every canonical prompt at `~/.claude/plans/fwd-canonical-prompt-*.md` MUST satisfy this; a prompt missing the demarcation is incomplete and must not be handed off.

- **The hand-off is ONE self-contained markdown FILE that is itself the complete, ready-to-paste message to the recipient (operator directive 2026-05-19, clarified after two misdeliveries; `docs/decisions.md` D18 — supersedes the prior "point at the file, do not dump contents" rule).** The Reviewer authors exactly one `~/.claude/plans/<name>.md` whose **entire contents** are what the operator copies wholesale into the other agent. The Reviewer's deliverable to the operator is **the file path plus "open it, select all, paste"** — nothing else; the message is never assembled in, or pasted out of, the chat reply. That single file MUST contain, in order:
    1. A 2–4 line framing preamble at the very top: name the recipient; state that the rest of this file is the authoritative spec end-to-end; restate the operating boundary (an implementer doesn't commit / bump version / edit `CLAUDE.md`, `pyproject.toml`, `src/fwd/version.py`, `docs/`; Reviewer commits; for a peer/consumer agent, the equivalent boundary); end the preamble with a "Begin" line.
    2. Immediately below it, the full spec body. Nothing the recipient must read lives outside this one file; deviation-surfacing per the spec's final-report format is required.

  Forbidden — each is a real misdelivery that occurred 2026-05-19: (a) a pointer-only message that merely names the path for the recipient to open (fragile — broke when the file was not where the recipient expected); (b) the message dumped inline into the chat reply inside a fence (forced the operator to hand-extract it from Reviewer prose — explicitly rejected); (c) two files (a prompt file plus a separate wrapper) — one file only, no duplicated content, single source of truth.

  The Reviewer writes the wrapper bespoke for each ship — it is short (10-20 lines), names the specific version + one-line description, and is presented to the operator immediately after the canonical prompt file is announced ready.

  **Why this is enforced (reconciled, D18).** The prior rule pointed the recipient at a file to avoid dumping a long Reviewer-internal document whose asides could be mis-read as instructions. That rationale is already neutralised by the standing requirement that the prompt body be fully self-contained (root constitution — no back-reference, no Reviewer-aside outside the spec). Three delivery forms were tried and the first two failed in practice (2026-05-19): a pointer-only message broke because it assumed the operator placed the file where the recipient expected; the message dumped inline into the chat reply forced the operator to manually select it out of surrounding Reviewer prose. The fix that holds: the hand-off is itself one file, and the only thing handed to the operator is its path — open, select-all, paste, one action, zero extraction, zero file-placement dependency. Applies to EVERY hand-off — Sonnet implementer and peer/consumer Opus agents alike. A hand-off delivered as a path-pointer, or assembled in the chat reply, or split across two files = not done right.

### Implementer (Sonnet 4.6) — IMPLEMENTS, WITH LICENSE TO DEVIATE

Reads the canonical prompt cold (no Opus chat history) and executes. Sonnet does NOT execute verbatim if doing so would produce wrong code.

Legitimate deviation (Sonnet adapts AND reports):
- Spec asserts a literal that grep reveals is a shell variable.
- Call site requires a parameter Sonnet discovers during integration.
- Edge case Sonnet uncovers naturally produces a different test count.
- Spec contains a typo.

Illegitimate deviation (REJECT):
- "While I'm here" refactors of unrelated code.
- Adding features the spec didn't request.
- Skipping spec items.
- Improvising a custom workaround when the spec has no path → STOP and surface to operator.

Sonnet obligations: faithful where spec matches reality, narrowest correct adaptation where it doesn't, every deviation reported in the "Open questions / surprises" section, never hidden, never claim spec was followed when it was adapted. Sonnet does NOT commit. Reviewer commits.

### Reviewer at verification — INSISTS, MAY OVERWRITE

After Sonnet's report, file-by-file Read pass (NOT just `git diff`). Authority at this stage is binding:

- **Accept:** sound deviation, common case.
- **Path (a) — Correct in place:** short corrective directive in same Sonnet session for tiny fixes (typo, missed import).
- **Path (b) — Overwrite:** wholesale revert + rewrite canonical prompt + fresh Sonnet session.
- **Path (c) — Inline tweak:** ONLY for non-behavioural adjustments. NEVER for logic.

### Operator (human) — DRIVES, GATES

Gives intent, gates plans + canonical prompts, approves production migrations, holds the unseal shares. May override the reviewer's commit at any time. Operator authority is supreme.

## Behavioural guidelines

Carryover from FICSM § Behavioural guidelines (after Karpathy's principles, via [forrestchang/andrej-karpathy-skills](https://github.com/forrestchang/andrej-karpathy-skills)).

1. **Think before coding.** Don't assume. Don't hide confusion. Surface tradeoffs. State assumptions explicitly, present alternatives, push back when a simpler approach exists.
2. **Simplicity first.** Minimum code that solves the problem. Nothing speculative. No features beyond what was asked, no abstractions for single-use code, no error handling for impossible scenarios. The "What FWD IS NOT" list operationalizes this for fwd-specific scope.
3. **Surgical changes.** Touch only what you must. Don't "improve" adjacent code, don't refactor what isn't broken, match existing style. Every changed line traces to the canonical prompt or a Sonnet-surfaced legitimate deviation.
4. **Goal-driven execution.** Define success criteria. Loop until verified. Every fwd canonical prompt's verification block is the strong criterion for that ship.

## Linear-forward versioning

Per Core invariant #13: every ship bumps the next linear patch number in BOTH `pyproject.toml` and `fwd/version.py`. No back-port semver. **Commit-message form is governed by the root `proofs.africa/CLAUDE.md` NON-NEGOTIABLE rule (codified 2026-05-16, reconciled into fwd doctrine at v0.5.0 per Core invariant #18): a single terse conventional-commit line — type + generic verb only (`docs: update`, `feat: update`, `fix: update`, …) — no body, no bullets, no rationale, no scope, no file/feature specifics, no "why". The back-reference, deviation log, and full ship narrative live in `docs/history/<version>-*.md` (indexed in `docs/history/README.md`), never in the commit message.** The prior fwd long-form ship-paragraph commit style is retired (it produced exactly the verbose structured messages the root rule forbids as an AI tell); it governed every commit through v0.5.0a7.

**Per-ship doctrine surface (instituted v1.0.0 — the corpus-bloat remedy; fourth independent audit B-verdict).** A ship updates exactly three doctrine artifacts and no more: (1) `docs/history/<version>-*.md` (the canonical full narrative), (2) one line in `docs/history/README.md` (the version index), (3) the single CLAUDE.md § Scope *current-state* line (current / next / blocked only). **No ship appends a per-version paragraph to CLAUDE.md § Scope** — the verbatim per-version narrative lives only in `docs/history/` (`SHIP-LOG.md` is the frozen, never-grown v0.1.0→v1.0.0a3 relocation; a new version adds only its deep file + one index line). A fat § Scope paragraph is drift (Core invariant #18) and is rejected at Reviewer verification. This kills the bloat generator and the recurring "§ Scope silently stopped at vX.Y" drift the audits caught repeatedly.

**Constitutional-amendment & bounded-reconciliation ship-types (instituted v1.1.0a3 — operator-authorized constitutional act 2026-05-19; `docs/decisions.md` D17).** The 3-artifact cap above governs **feature ships**. Two non-feature ship-types have their own *defined, bounded* surfaces and are NOT rejected at Reviewer verification for exceeding three artifacts:

- **Constitutional-amendment ship.** Amends this CLAUDE.md's process/invariant doctrine itself. Bounded surface: the amended CLAUDE.md section(s) + a `docs/decisions.md` D-record + the three feature-ship artifacts (history file, README line, § Scope current-state line) + the two version files. It is self-ratifying (the amendment ship is governed by the definition it introduces; the self-reference is recorded honestly in its D-record, Core invariant #18) and must be explicitly operator-authorized — it is **never** a Reviewer self-grant. v1.1.0a3 is the genesis instance (this paragraph).

- **Bounded post-verification reconciliation ship.** Reconciles invariant *text* to code that a *prior, already-shipped, byte/GATE-verified* ship made true (e.g. a Step-0/GATE-verified primitive). Constrained to: **(i)** only invariant text the just-shipped, byte-verified code makes true — nothing speculative, nothing GATE-pending; **(ii)** every reconciled edit annotated inline `(code in ship vX.Y.ZaN makes this true)`; **(iii)** NO § Scope narrative paragraph — the corpus-bloat the per-ship rule kills stays killed; **(iv)** ONE coherent ship — the reconciliation is never fragmented across versions (fragmentation creates Core-#18 partially-true doctrine states on main). Bounded surface: the reconciled invariant lines (CLAUDE.md / `docs/decisions.md` / `docs/architecture.md` / `docs/threat-model.md`) + a D-record + the three feature-ship artifacts + the two version files. It cannot ship until the verification gate of the ship whose code it reconciles has passed. Reusable for every future Step-0/GATE-verified phase (9a-iii, 9b, 9c, 10x) without re-authorization.

Neither ship-type relaxes Core invariant #18 (no silent drift; honest history) — each *narrows* it by forcing the reconciliation into one annotated, operator-visible, gate-anchored ship instead of leaking partial truth across feature ships.

## Carryover from FICSM and from `keosd`

`fwd` is not a fork of either. The workflow doctrine (Opus/Sonnet/Reviewer/Operator), the four-layer validation philosophy, the linear-forward versioning, the canonical-prompt completeness checklist, and the substrate ethos (SQLite, single-operator, framework-free) are inherited verbatim from FICSM as design — no FICSM code is imported.

The role itself — *daemon that holds keys and signs on behalf of clients* — is inherited from `keosd` (Antelope/EOSIO `programs/keosd/`). What `fwd` adds that `keosd` does not provide: intent decoding, default-deny per-caller policy, hash-chained audit, EVM-native signing flow, and a custody backend (Vault Transit `aes256-gcm96` envelope encryption) whose master encryption key is non-exportable by API and whose plaintext private keys exist in `fwd`'s memory only during the bounded signing operation.

The ~50 banked feedback memories at `~/.claude/projects/-home-l-working-gitlab-com-proofs-africa-fics/memory/` and the FICSM doctrine doc at `../ficsm/CLAUDE.md` act as a Phase-0 checklist for `fwd`'s reviewers.
