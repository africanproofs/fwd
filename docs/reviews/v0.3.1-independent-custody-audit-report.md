## Executive summary

No Critical plaintext-leak path was found in the current v0.3.1 code path. The implemented signing flow decrypts on demand, signs, and zeroizes the mutable `bytearray` buffer in `finally`.

The main custody risks are doctrine drift, not an immediately observed current leak: `fwd` process memory is not actually `mlock`ed, the structlog scrubber promised by the Phase-3 hazard docs is absent, tests do not enforce the zeroization/no-cache properties the docs claim they enforce, and the threat model contradicts itself about whether a compromised `fwd`/AppRole can extract wallet keys under the envelope-encryption design.

## Chapter 1 - Custody correctness

Questions answered: private-key lifecycle, `eth-account` copy behavior, Vault token lifecycle, `mlock`, logging, and Vault reset behavior.

### High - `fwd` memory is not `mlock` protected despite Core invariant #1

Evidence:
- `CLAUDE.md:78` says plaintext keys are protected by `mlock` against swap.
- `CLAUDE.md:108` says Core invariant #16 relies on `mlock`-protected process memory.
- `docs/threat-model.md:89` says `fwd` has `IPC_LOCK` capability in compose.
- `docker-compose.yml:5-6` grants `IPC_LOCK` only to the `vault` service.
- `config/vault/config.hcl:14` enables Vault mlock, not fwd mlock.
- `rg mlock` found no Python call in `src/fwd/`.

Impact: the plaintext key and Vault token exposure window can survive outside RAM if the host swaps or dumps process memory. This is exactly the persistence class the doctrine says is avoided. Current dev posture lowers urgency, but this should be fixed or the invariant rewritten before Phase 8.

### Medium - structlog scrubber is absent after plaintext key paths landed

Evidence:
- `docs/architecture.md:682-686` says a custom processor redacts any 32-byte hex-shaped string and that Phase 3+ enforces it.
- `src/fwd/main.py:38-46` configures structlog without such a processor.
- `docs/history/0.3.0-phase-3c-sign-and-send.md:111` now says the scrubber is Phase 7, contradicting the architecture hazard section.

Current log call review:
- `src/fwd/app/sign_and_send.py:164-174` logs wallet, chain, addresses, nonce, gas, fee, and `tx_hash`; it does not log `signed.raw_transaction` or plaintext.
- `src/fwd/infra/vault_client.py:111` logs only login success.
- `src/fwd/infra/vault_client.py:137` logs only the Vault path on 403.
- `src/fwd/app/wallet_create.py:59` logs `str(VaultError)`, which currently includes HTTP status/body snippets but not request JSON or plaintext.

Impact: no current log call passes a private key or signed raw transaction, but the documented protection is not in place. This becomes more dangerous in Phase 4 if CLI import lands before the scrubber.

### Observation - Python zeroization is best-effort and the docs should stop implying otherwise

Evidence:
- `src/fwd/infra/envelope_signer.py:67-70` receives immutable `bytes` from Vault, copies to `bytearray`, then creates another immutable `bytes` object for `Account.from_key(...)`.
- `src/fwd/infra/envelope_signer.py:72-77` copies signed output into the return tuple.
- `src/fwd/infra/envelope_signer.py:93-99` keeps the `LocalAccount` from `Account.create()` alive through encrypt + address derivation; its original immutable key survives until the local `account` is unreachable.
- `src/fwd/infra/envelope_signer.py:78-79` and `109-111` zeroize only the mutable buffer.
- `docs/architecture.md:680` correctly admits Python GC may already have copied key material.

Impact: acceptable for the documented v0.3.1 trade-off if treated as best-effort. The practical window is bounded to the function call and local temporary lifetime, not a process-wide cache. The phrase "microseconds" is not evidenced and should be softened unless measured.

### Observation - Vault token "zeroization" is security theatre

Evidence:
- `src/fwd/infra/vault_client.py:54` stores `_token` as a Python `str`.
- `src/fwd/infra/vault_client.py:63-65` overwrites the attribute with a new all-zero string, then `None`.
- `src/fwd/infra/vault_client.py:46-47` also stores AppRole role_id/secret_id as strings for the client lifetime.

Impact: this clears references, not the underlying immutable string buffers. Acceptable as best-effort cleanup, but not evidence for the `mlock`/zeroize claims in `docs/decisions.md:265` and `docs/architecture.md:493-496`.

### Observation - `docker compose down -v`/volume removal is the destructive reset path

Evidence:
- `docker-compose.yml:73-76` defines named volumes `vault-data`, `fwd-state`, `litestream-replica`.
- `CLAUDE.md:110` mandates `docker volume rm fwd_vault-data` for the Phase 8 wipe-and-redo.
- No host port exposes Vault; host curl to `127.0.0.1:8200` was refused.

Impact: the current reset semantics match the doctrine. The operational warning needs to be more visible before production because accidental volume deletion destroys decryptability.

## Chapter 2 - Auth surface

Questions answered: admin token comparison, AppRole over internal HTTP, non-expiring `secret_id`, 403 retry semantics, endpoint shape, admin-key rotation, and Phase 4 boundary.

### Medium - AppRole `secret_id` is non-expiring/unlimited and rotation is not yet operationalized

Evidence:
- `scripts/vault-init.sh:56-63` sets `secret_id_ttl=0` and `secret_id_num_uses=0`.
- `docs/decisions.md:272` says operator-driven secret_id rotation must be documented before production.
- No production runbook for AppRole secret rotation exists yet.

Impact: acceptable for Phase 3-7 dev only because Core invariant #17 mandates wipe-and-redo before production. Phase 8 should have a concrete rotate/reissue procedure, not just doctrine.

### Medium - Vault auth traffic is HTTP inside Docker; isolation holds from host but not from host-root/Docker-root

Evidence:
- `src/fwd/infra/vault_client.py:96-100` sends role_id/secret_id as JSON to Vault.
- `config/vault/config.hcl:7-8` listens on HTTP with TLS disabled.
- `docker-compose.yml:67-70` marks `fwd-internal` internal.
- Host curl to `127.0.0.1:8200` failed, confirming no accidental host port.

Impact: fine for the current single-host dev boundary. It is not a defense against host root, Docker daemon access, or a malicious container already on `fwd-internal`. If TLS is still deferred, docs should call that out honestly.

### Observation - admin auth comparison is correct; no alternate token compare found

Evidence:
- `src/fwd/api/admin_auth.py:32-33` uses `hmac.compare_digest`.
- `src/fwd/cli/wallets.py:26-35` forwards the admin key; it does not compare it.

Impact: no timing finding here.

### Observation - 403 reauth semantics are reasonable but low signal on policy denial

Evidence:
- `src/fwd/infra/vault_client.py:136-144` reauths once and raises `VaultError("403 after reauth")` on a second 403.
- `tests/unit/test_vault_client.py:52-91` covers retry and double-403.

Impact: correct for expired-token recovery. It will turn a persistent policy denial into a generic VaultUnavailable response at the API boundary; acceptable for v0.3.1, but Phase 7 logs should distinguish token expiry from policy denial.

### Medium - `/v1/sign-and-send` is temporarily admin-gated; Phase 4 must avoid preserving that mental model

Evidence:
- `src/fwd/api/sign.py:76-81` gates `/v1/sign-and-send` with `admin_required`.
- `src/fwd/api/sign.py:1` documents that caller auth lands in Phase 4.
- `src/fwd/api/wallets.py:37-42` also uses `admin_required` for true admin wallet creation.

Impact: the URL shape is correct (`/v1/sign-and-send` is not under `/v1/admin`). The risk is implementation inertia: caller identity and caller policy must thread through signing; admin bootstrap must stay separate.

## Chapter 4 - Doctrine consistency

Questions answered: which core invariants/decisions are enforced, deferred, or aspirational.

### High - threat model contradicts the envelope-encryption blast radius

Evidence:
- `docs/threat-model.md:106-120` correctly says compromised `fwd` can call `transit/decrypt/fwd-master`, recover all wallet private keys for which it has ciphertexts, and exfiltrate them.
- `docs/threat-model.md:259` then says "`fwd` process compromise" means keys cannot be extracted.
- `docs/threat-model.md:128-130` says AppRole/Vault compromise can sign but cannot extract keys, but the actual Vault policy grants `transit/decrypt/fwd-master` in `config/vault/policies/fwd-app.hcl:10-12`.
- Wallet ciphertexts are stored in SQLite at `src/fwd/infra/wallet_repo.py:25`.

Impact: this is not wording polish. It is the core risk of the v0.1.2 pivot. A compromised `fwd` process or attacker with AppRole token plus SQLite ciphertexts can decrypt wallet private keys. Correct the summary table and A5 before Phase 4/7 policy claims obscure this.

### Medium - several "Phase 3+" enforcement claims are not true

Examples:
- No plaintext caching introspection test: `docs/architecture.md:655` promises it; no such test exists.
- Zeroized-buffer test: `docs/architecture.md:678` promises it; `tests/unit/test_envelope_signer.py:20-108` never observes the buffer after zeroize.
- Structlog scrubber: `docs/architecture.md:686` promises it; `src/fwd/main.py:38-46` lacks it.

Impact: the code may be acceptable, but the enforcement claims are not. Mark them deferred or add the tests.

## Chapter 7 - Phase 4-8 risks

Questions answered: likely design assumptions that will bite during caller auth, nonce/state, backup/restore, policy/audit, and first production migration.

### High - Phase 5 nonce reconciliation is underspecified

Evidence:
- `src/fwd/app/sign_and_send.py:106` currently uses `eth_getTransactionCount(..., "pending")` per request.
- `docs/implementation-plan.md:122` only says compare DB nonce to `eth_getTransactionCount(latest)` and warn on drift.

Impact: startup reconciliation must handle pending vs latest, transactions broadcast with unknown response, replacement attempts, nonce gaps, dropped transactions, and DB rollback boundaries. "Warn on drift" is not enough for a custody signer.

### High - Phase 6 backup consistency between SQLite and Vault snapshots is not documented

Evidence:
- `docs/architecture.md:573-588` describes separate Litestream SQLite restore and Vault Raft snapshot restore.
- No consistency point is specified between wallet ciphertext rows and the Vault master-key state/key versions able to decrypt them.

Impact: restoring SQLite and Vault to mismatched points can produce wallets that exist in DB but cannot decrypt, or nonce/audit state that disagrees with custody state. Phase 6 needs a consistency model and drill.

### High - Phase 8 migration ordering/rollback is not yet runbooked

Evidence:
- `docs/implementation-plan.md:173-184` lists generation, policy, on-chain rotation, consumer cutover, and epoch verification.
- No dedicated key-rotation/cutover/rollback runbook exists.

Impact: if `setClaimRecipient` points on-chain revenue to an address that is not durably persisted/restorable in fwd, rollback is hard. The runbook should require wallet creation, decrypt/sign smoke test, backup snapshot, policy/caller creation, and only then on-chain rotation.

### Medium - Phase 4 `policy_path` is a free-form string today

Evidence:
- `src/fwd/api/wallets.py:27-30` accepts `policy_path` with length only.
- `src/fwd/app/wallet_create.py:23-27` stores it unchanged.

Impact: if Phase 4 caller auth stores caller `policy_path` before Phase 7 defines policy semantics, the team may bake in the wrong indirection. Define whether policy is caller-owned, wallet-owned, or a join of caller-wallet-action before writing caller migrations.

### Medium - per-request dependency context managers will not host Phase 5/7 background tasks

Evidence:
- `src/fwd/app/dependencies.py:17-44` constructs Vault/session/RPC managers per request.
- Phase 5 receipt watcher and Phase 7 token renewal are long-running tasks.

Impact: Phase 5 likely needs FastAPI lifespan wiring and shared resources. Plan that refactor deliberately.

### Medium - Phase 7 audit chain transaction semantics are not specified

Open points:
- Genesis/root when table is empty.
- Whether audit rows are in the same DB transaction as the state mutation or independent.
- What happens when the signing transaction rolls back after an audit write.
- How `prev_hash` is locked under concurrent writes.

Impact: these are easy to get wrong after the schema lands. Specify before implementation.

### Medium - Phase 8 availability/SLO for `ftso-fee-claimer` is absent

Evidence:
- Phase 8 goal is one full reward epoch claimed via fwd.
- No fallback/SLO doc exists for fwd down at claim time.

Impact: removing `.env PRIVATE_KEY` is correct, but claim windows are revenue-bearing. Define operator response: unseal SLA, restart behavior, degraded mode if Vault sealed, and whether missing an epoch is acceptable.

### Observation - Phase 7 scrubber needs a smarter policy than "redact all 32-byte hex"

Evidence:
- `src/fwd/app/sign_and_send.py:173` currently logs `tx_hash`, a public 32-byte hex string.
- `docs/architecture.md:686` proposes redacting every 32-byte hex string.

Impact: redacting tx hashes hurts operations. A field-aware scrubber or explicit safe wrapper for public tx hashes is preferable.

## Final recommendation

Do not block Phase 4 on a large rewrite. Do block Phase 4/5 planning on three small corrections:

1. Correct the doctrine: `mlock` is absent; threat-model A4/A5/summary must reflect decrypt-capability reality; Phase-3 enforcement claims are not true.
2. Add the missing safety rails before new secret-handling paths land: structlog scrubber, real zeroize/no-cache tests, and explicit `settings` boundary enforcement.
3. Author Phase 8 operational runbooks early: production wipe/re-init rehearsal, AppRole/admin-key rotation, backup consistency drill, and claim-recipient cutover/rollback.
