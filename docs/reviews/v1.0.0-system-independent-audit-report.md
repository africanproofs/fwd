## Findings

### 1. Stale `.env PRIVATE_KEY=` can bypass clif's keyless gate

- **Severity:** High
- **Ownership:** `clif`
- **Disposition lane:** `STOP-SHIP`
- **Evidence:** `clif/config.py:74-86`, `clif/config.py:89-90`, `clif/config.py:136-139`, `tests/test_config.py:1-25`; observed output: a temp `.env` containing `CLAIM_EXECUTOR_PRIVATE_KEY=dummy` produced `NO_RAISE coston2`.

`assert_keyless()` scans `os.environ` before `Settings` loads `.env`. Unknown `.env` keys are ignored by pydantic, so clif will not hold or use the key, but the Phase 8b claim "the `.env PRIVATE_KEY=` line is gone" can be false while clif starts cleanly. Fix: scan the configured `.env` source for `PRIVATE_KEY` names before loading settings, and test it.

### 2. Production idempotency can pin a failed on-chain claim forever

- **Severity:** High
- **Ownership:** `clif` + `fwd`
- **Disposition lane:** `STOP-SHIP`
- **Evidence:** `clif/fwd_client.py:50-61`, `clif/claimer.py:97-116`, `src/fwd/app/sign_and_send.py:193-229`, `clif/cli.py:327-349`, `clif/cli.py:360-368`, `clif/cli.py:469-473`.

Production `claim`/`auto` use a deterministic idempotency key by network/type/beneficiary/last epoch. fwd replays any existing transaction for that key before policy or status checks. If a production claim is accepted by fwd but reverts on-chain before the operator fixes the cause, clif has no production retry discriminator; the same epoch can replay the cached failed tx forever. Rehearsal has `--idem-tag`; production does not. Fix: add an explicit operator-only retry discriminator for manual `clif claim`, or make fwd replay status-aware for terminal failed/dropped transactions.

### 3. fwd transport failure can crash `clif auto` instead of degrading

- **Severity:** High
- **Ownership:** `clif`
- **Disposition lane:** `STOP-SHIP`
- **Evidence:** `clif/fwd_client.py:127-130`, `clif/claimer.py:117-126`, `clif/cli.py:592-644`; observed output: `httpx.ConnectError` propagated as `ConnectError`, not `FwdRetryableError`.

`FwdClient.sign_and_send()` does not wrap httpx transport exceptions. `submit_claims()` catches only `FwdTerminalError` and `FwdRetryableError`, so a down/restarting fwd daemon can terminate `clif auto` instead of recording retryable/degraded state. Docker restart helps process liveness, but it loses the claimed "never exits on claim error" behavior and weakens reward-expiry monitoring. Fix: convert httpx transport errors in sign/status paths to `FwdRetryableError`, with tests.

### 4. Vault-retirement doctrine is still false in operator-facing files

- **Severity:** Medium
- **Ownership:** `fwd`
- **Disposition lane:** `doctrine-honesty`
- **Evidence:** root `CLAUDE.md:42`, `fwd/CLAUDE.md:9`, `fwd/CLAUDE.md:174`, `fwd/.env.example:9-18`, `fwd/.env.example:39-63`, `docker-compose.yml:1-84`.

The code stack has retired Vault; the root constitution, fwd identity text, Core #16 wording, and `.env.example` still describe Vault/AppRole/snapshots. This does not block signing correctness, and a broad doctrine cleanup would be the old pathology. But active operator-facing setup files must not tell the next agent/operator to configure dead Vault variables. Fix only the active setup claims touched by the v1.0.0 ship, or mark them historical.

### 5. clif's own fwd-contract doc still contradicts the current fwd policy example

- **Severity:** Low
- **Ownership:** `clif`
- **Disposition lane:** `doctrine-honesty`
- **Evidence:** `clif/docs/fwd-contract.md:74-79` says fwd's policy example is wrong; current fwd diff changes `docs/policy.example.yaml:56` to the correct `claim(address,address,uint24,bool,(bytes32[],(uint24,bytes20,uint120,uint8))[])`.

This is not a custody bug. It is a stale warning after the fwd fix. Leaving it creates operator doubt at the exact handoff where the policy must be copied carefully. Fix the warning in the same clif correctness ship as the STOP-SHIP items; do not create a separate reconciliation ship.
