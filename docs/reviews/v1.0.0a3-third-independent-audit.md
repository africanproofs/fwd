## 0. Why you exist (read this first — it changes how you should audit)

`fwd` is a policy-gated EVM signing daemon for African Proofs. Its entire
stated purpose (Core invariant #7) is to **delete every `.env PRIVATE_KEY=`
line in AP's backends** and replace it with a custody service. As of
v1.0.0a3 it has shipped ~47 history docs, 19 Core invariants, 17 decisions,
a four-role workflow doctrine, a doctrine-ship freeze, and **two prior
independent stack/over-engineering audits** — and has **never deleted a
single `.env PRIVATE_KEY=` line.** Zero. The first one is "Phase 8b", still
pending.

The two prior audits converged on the same verdict:

- **v0.5.4 (first):** stack mostly right; over-engineering = "process has
  become the product"; Vault is the open question.
- **v0.5.5 (second, designed to be Reviewer-unneutralisable):** same; 0
  Critical / 3 High; fastest action = one bounded cleanup, then **freeze
  audits and ship Phase 8**.

Acting on those, the operator and Reviewer then:

1. **Retired HashiCorp Vault entirely (v1.0.0a1).** Replaced it with
   `SealedMaster` — AES-256-GCM (`cryptography` AESGCM), a 32-byte master
   in a mode-0600 host file owned by the `fwd` user, ciphertext
   `seal:v1:<b64(nonce‖ct)>` in SQLite. Driven by an operator asset-class
   reframe ("~1000 FLR ≈ tens of USD per key; Flare-automation only; host
   never publicly exposed"). Deleted `vault_client.py`, `vault-init.sh`,
   `ci_vault_init.py`, `config/vault/`, the vault + vault-snapshot compose
   services, the CI vault stage.
2. **Published + then MET the Core #14 live gate (v1.0.0a2 → v1.0.0a3).**
   Claimed: a real Coston2 tx (`0xc222bf62…5ac5e6`, block 30662555) mined
   with on-chain `from` recovering to the fwd-sealed wallet — proving the
   sealed-master custody path end-to-end with no Vault.
3. **Ratified a doctrine-ship FREEZE.** No more doctrine/audit/
   reconciliation ships until the first Phase 8b `.env PRIVATE_KEY=`
   deletion. Yet v1.0.0a1 and v1.0.0a3 both performed "in-ship doctrine
   reconciliation" justified as "Phase-8 work the freeze permits".

**Your audit is therefore NOT a fresh general review. It is a
decision-forcing audit with exactly one job: tell the operator whether
Phase 8b should ship as-is, what (custody-real, minimal) must exist first,
and whether the project is converging on simplicity or has merely
relocated its complexity.** A finding that would require a *non-Phase-8
reconciliation ship* to fix is, by the freeze's own logic, a finding you
must mark **DEFER** unless it is custody-critical. You are not here to
generate a doctrine-nit backlog. Generating one would prove the
over-engineering thesis a third time at the operator's expense.

## 1. Mandatory verdict A — the stack (post-pivot)

The stack changed materially since v0.5.5 (Vault gone; `cryptography`
added; Litestream now replicates SQLite to a local volume only). Give a
**one-paragraph verdict** plus a **per-component keep/cut/fix table**.
Specifically pressure-test, with evidence from the files:

- **`SealedMaster` correctness (the new custody primitive — `src/fwd/infra/sealed_master.py`).** This is brand-new crypto code on the
  custody path that the prior audits never saw. Check, concretely:
  (a) **nonce uniqueness** — is a fresh 96-bit random nonce generated per
  `encrypt`? GCM nonce reuse under one key is catastrophic (forgery +
  plaintext recovery). (b) **master-file validation** — mode 0600, owner
  == euid, exactly 32 bytes: is it robust to symlink / FIFO / TOCTOU
  between stat and open / running as root? (c) **zeroize honesty** — the
  master must live in RSS for the whole process lifetime to decrypt on
  demand; is "zeroize on exit" therefore cosmetic, and is that documented
  honestly (Core invariant #18)? (d) the SQLite column is still named
  **`vault_master_key`** holding the literal `local:v1` — latent
  misleading naming a future operator/agent trips on: drift or acceptable?
- **Backup/DR coherence post-pivot (high-value, possibly broken).**
  Litestream replicates SQLite (the *ciphertexts*). The master key is an
  out-of-band mode-0600 host file that Litestream does **not** back up. A
  Litestream restore therefore yields ciphertexts that cannot be decrypted
  without the separately-held master. Read `docs/runbooks/restore.md` and
  Core invariant #17 (DR = "regenerate wallet + on-chain
  `setClaimRecipient`"). **Is the disaster-recovery story actually
  coherent and rehearsed for the sealed-master world, or is `restore.md`
  now stale Vault-era doctrine?** Rate this by production-key impact.
- **Litestream's continued worth** with Vault gone and DR being
  "regenerate, not restore" — does the replication sidecar still earn its
  place, or is it now substrate without a consumer?

## 2. Mandatory verdict B — over-engineering (the delta, not a re-run)

Both prior audits said "yes, process is the product." Do **not** just
agree. Measure the **delta since v0.5.5**:

- Doctrine corpus then vs now (invariants, decisions, history docs, audit
  artefacts). Did the freeze + the v1.0.0a1 substrate *deletion* bend the
  complexity curve down, or did the project relocate complexity from
  Vault-substrate into **doctrine-reconciliation ceremony** (the freeze
  itself, "in-ship Phase-8 reconciliation", audit-of-audits, backfilled
  scope paragraphs, this prompt)?
- **Is the freeze holding or being routed around?** v1.0.0a1 and v1.0.0a3
  each did doctrine reconciliation under a "Phase-8 in-ship" label. State
  plainly: is "Phase-8 in-ship reconciliation" a legitimate carve-out, or
  has the Reviewer found a rationalisation that lets the reconciliation
  loop continue under a new name while the freeze provides cover? This is
  the single most uncomfortable question; answer it directly.
- Give a **one-line over-engineering verdict** and a concrete **"stop
  doing this" list** (≤5 items, each naming the specific ceremony and the
  cheaper alternative).

## 5. Stakes rubric (apply to every finding)

Rate each finding exactly one of:

- **CUSTODY-CRITICAL** — can cause loss/leak of a production key or a
  silent custody failure. These can be NO-GO blockers.
- **CORRECTNESS** — wrong behaviour, no direct key loss (e.g. broken DR
  runbook with the master still in hand).
- **DRIFT/DOCTRINE** — doctrine ≠ code, naming, ceremony. **Default
  disposition: DEFER past Phase 8b.** Only escalate if it hides a
  custody-critical issue.

A finding with no production-key story is, by definition, not a Phase-8b
blocker. Say so.

## 6. Anti-over-engineering rule for THIS audit (binding on you)

You are auditing a project whose diagnosed disease is excess process. Do
not administer more of the disease:

- **Maximum 8 findings total.** If you have more, you have not
  prioritised; merge or drop.
- Every finding ≤120 words: claim → file evidence → stakes rating →
  one-line fix or DEFER.
- No finding may recommend a new doctrine artefact, invariant, or audit.
- Lead with the GO/NO-GO and the two verdict one-liners. The operator
  must get the decision in the first 15 lines of your report.
- If your honest conclusion is "the prior audits were right, nothing
  material changed, just ship Phase 8b" — **say exactly that and stop.**
  That is a complete, valuable answer, not a failure to find things.
