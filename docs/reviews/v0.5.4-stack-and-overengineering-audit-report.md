# fwd v0.5.4 - Stack And Over-Engineering Audit Report

## 0. Executive Verdict

Stack verdict: **Mostly right, 6 components misfit.** The core substrate - Python, FastAPI, SQLite, `eth-account`, `httpx`, Pydantic policy, caller auth, and Docker Compose - is appropriate for a single-host signing daemon, but Vault-as-envelope-only, replacement-on-stuck, policy-insensitive idempotency replay, anchorless hash-chain machinery, speculative ABI/dependency scaffolding, and the snapshot/process apparatus need an explicit keep/drop decision before Phase 8. Over-engineering verdict: **Process has become the product.** The project has 6,857 source LOC, 11,400 test LOC, 2,570 core doctrine LOC, 43 history files, four compose services, and about 1.25 GB of visible runtime images, while the checkpoint's stated production value remains zero deleted `.env PRIVATE_KEY=` lines. This is not a claim that the code is sloppy; the opposite is mostly true, and the live drills behind Core #14/#19 caught real bugs. The problem is that the ceremony and generality now consume more decision bandwidth than the first production migration. The Reviewer should preserve the parts proven by live failures and cut or defer the parts that do not directly delete the first production key.

## 2. Over-Engineering Findings

### OE-1 - Vault is now a heavy envelope oracle, not a signer

Severity: **High**

Claim: The Vault dependency is the largest stack-fit question because D1's original "keys never leave signer" rationale died when secp256k1 Transit signing proved impossible, but the project retained the whole Vault/Shamir/AppRole/Raft/snapshot apparatus.

Evidence: D1 says Vault runs on the same Docker host and only wraps/unwraps externally generated private keys (`docs/decisions.md:11`, `docs/decisions.md:25`). The threat model concedes compromised `fwd` can issue decrypt calls and recover all wallet keys (`docs/threat-model.md:106-120`), and leaked AppRole plus SQLite ciphertexts is materially as severe (`docs/threat-model.md:130-144`). Compose runs Vault and a Vault snapshot sidecar (`docker-compose.yml:2-30`, `docker-compose.yml:100-116`), and local image output shows 466MB for Vault plus 466MB for `fwd-vault-snapshot`.

Why disproportionate or speculative: For Phase 8 the concrete job is one `ftso-fee-claimer` migration and one epoch claim (`docs/implementation-plan.md:183-198`). Vault does not prevent the main runtime extraction scenario; it adds operational state, unseal ceremony, policies, AppRole lifecycle, snapshots, and restore coupling for an envelope-only function.

Cost: The first production migration must now carry Vault init, Shamir distribution, AppRole hygiene, Raft snapshot restore, and sidecar backup correctness before any AP backend gets value. It also increases the number of failure modes the Operator must rehearse before real keys move.

Steelman: Vault still buys a mature non-exportable master key API, Shamir unseal, a familiar operational model, Vault-side audit logs independent of `fwd`, and a cleaner Phase 10 path to stronger custody. Avoiding custom cryptography is a real benefit, and D1 explicitly considered simpler encrypted keystore designs (`docs/decisions.md:15-22`).

Net verdict: Vault can be defended, but not by inertia from the dead Transit-signing architecture. It must be re-chosen as an operator-valued operations/audit substrate, not assumed to be a security boundary it is not.

Action: **keep & defend**, only after an explicit Operator decision before Phase 8.

### OE-2 - Doctrine and workflow have outrun delivered value

Severity: **High**

Claim: The process apparatus is now disproportionate to a 6,857 LOC daemon that has not deleted a production key yet.

Evidence: Phase-1 measurements show 6,857 source LOC, 11,400 test LOC, 2,570 core doctrine LOC, and 43 history files. The workflow mandates canonical prompts, exact HAND-OFF fences, wrappers, and file-by-file Reviewer passes (`CLAUDE.md:170-205`, `CLAUDE.md:225-236`). The implementation ledger contains multiple doctrine-only ships with no code/test changes, including v0.5.0a1/a2 and v0.5.4 (`docs/implementation-plan.md:282-283`, `docs/implementation-plan.md:290`). The purpose remains deleting `.env PRIVATE_KEY=` (`CLAUDE.md:144`), while Phase 8 is still the first production migration (`docs/implementation-plan.md:183-198`).

Why disproportionate or speculative: The project's own guideline says "Minimum code" and "Nothing speculative" (`CLAUDE.md:248-249`). Doctrine-only version bumps and wrapper ceremony do not directly advance the Phase 8 migration unless they encode a defect class proven by live failure.

Cost: Every ship pays review, history, version, prompt, wrapper, and drift-maintenance tax. The tax is already producing drift: architecture still says policy is hot-reloaded (`docs/architecture.md:105`) while later doctrine says startup-only (`docs/architecture.md:605-607`); the ABI README says arrays/tuples return `None` (`config/abis/README.md:69-74`) while the code uses B1 projection and returns `None` only on decode failure (`src/fwd/domain/intent.py:6-13`, `src/fwd/domain/intent.py:112-158`); architecture still describes Scaleway backups and `clifwd reconcile` (`docs/architecture.md:834-844`) while compose uses a local backup volume (`docker-compose.yml:124-134`).

Steelman: The ceremony has caught real classes of defects. Core #14 names the v0.4.5 concurrency bug and v0.5.2 deny-audit bug as unit-green, live-only failures (`CLAUDE.md:158`), and Core #19 codifies the recurrence so it is not just patched once (`CLAUDE.md:168`).

Net verdict: Keep the live-drill discipline and defect-class invariants. Cut doctrine-only version bumps, reduce history churn, and collapse prompt/wrapper ceremony unless the next ship is a high-risk custody migration.

Action: **cut now**.

### OE-3 - Receipt watcher replacement-on-stuck is pulled forward for a low-QPS Phase 8 consumer

Severity: **Medium**

Claim: Automatic replacement-on-stuck is more general than the first production consumer needs.

Evidence: The watcher is 327 LOC with 534 LOC of unit tests, polls continuously, scans submitted transactions, and can re-sign/rebroadcast with bumped tips (`src/fwd/app/receipt_watcher.py:61-102`, `src/fwd/app/receipt_watcher.py:198-318`). Defaults poll every 2 seconds, treat 30 seconds as stuck, and retry up to 5 times (`src/fwd/settings.py:47-53`). Phase 8 is one `ftso-fee-claimer` migration and one full reward epoch claim cycle (`docs/implementation-plan.md:183-198`), not a latency-sensitive high-volume sender.

Why disproportionate or speculative: The simplest Phase 8 flow can return a tx hash, let the caller/operator observe chain finality, and require explicit retry/reconcile on failure. Replacement policy is valuable for continuous senders, but Phase 8's workload is sparse and operator-visible.

Cost: It keeps a background signing-capable path alive, requires stuck-clock and fee-bump doctrine, and extends the blast radius of watcher bugs into the signing path. It also forced shared `RequestScope` coupling with the same writer-lock machinery (`src/fwd/app/receipt_watcher.py:87-102`).

Steelman: Nonce continuity matters, and the project has real evidence that concurrency and live chain behavior beat mocks (`CLAUDE.md:158`). A stuck transaction can block all later nonces for the wallet, so automatic replacement is not imaginary.

Net verdict: Keep status tracking if the caller needs it, but defer automatic replacement-on-stuck until a real production pattern shows operator-supervised retry is insufficient.

Action: **defer to Phase 10**.

### OE-4 - Idempotency replay bakes in subtle policy-bypass semantics before a caller proves the need

Severity: **Medium**

Claim: The idempotency implementation is too strong for Phase 8 because replay returns a cached approved result without re-evaluating policy.

Evidence: D14 states a matching `Idempotency-Key` does not re-evaluate policy and remains valid even if `policy.yaml` changes unless paired with caller-key rotation (`docs/decisions.md:525`). The code checks idempotency before wallet resolution and before the policy gate (`src/fwd/app/sign_and_send.py:175-211`). The feature has 448 LOC of dedicated unit tests by measurement.

Why disproportionate or speculative: Phase 8 has one known caller and can persist `tx_id` or ask `/v1/transactions/{tx_id}`. A policy-insensitive replay rule is a permanent semantic commitment for a retry concern that can be handled more narrowly.

Cost: Tightening policy alone does not invalidate old idempotency keys. Future reviewers must reason about the exception before every policy change, and the audit log now needs duplicate-row semantics.

Steelman: The dangerous failure is a network drop after broadcast but before the caller receives the response. Idempotency prevents duplicate nonce consumption and duplicate signing in exactly that case, and the duplicate audit row preserves forensics.

Net verdict: The retry safety is legitimate, but the current no-reeval semantics are stronger than Phase 8 needs. Bind replay to a short TTL or policy hash later; do not treat it as core until the real caller integration demonstrates the failure mode.

Action: **defer to Phase 10** for policy-insensitive replay semantics; keep simple status-based retry for Phase 8.

### OE-5 - Hash-chain audit is ahead of its anchoring story

Severity: **Medium**

Claim: Append-only audit rows are load-bearing; the full hash-chain and walker are only partially load-bearing until an external anchor exists.

Evidence: D16's hash-chain scheme is extensive (`docs/decisions.md:620-734`). It explicitly concedes that an attacker with SQLite write access can modify a row and recompute hashes forward, and only an out-of-band snapshot or Phase 10 on-chain anchor detects that (`docs/decisions.md:720`, `docs/architecture.md:827-830`). The audit repo has 479 LOC of tests by measurement, and `audit-verify-failure` self-write remains deferred (`docs/decisions.md:643-649`, `docs/architecture.md:768-769`).

Why disproportionate or speculative: For Phase 8, the key accountability need is durable approved/denied/error rows. Tamper-evidence without an anchor is weaker than the doctrine's surface area suggests.

Cost: Canonical JSON, row hashing, windowed verification, self-write deferrals, and forensic-row durability rules add maintenance burden and increase doctrine drift risk. The v0.5.2 incident shows this area is easy to get subtly wrong (`CLAUDE.md:158`, `CLAUDE.md:168`).

Steelman: The audit log is a real differentiator from `.env PRIVATE_KEY=`, and the v0.5.2 live drill proved missing failure rows are not academic. A hash chain also catches accidental or partial corruption early, even before on-chain anchoring.

Net verdict: Keep durable audit rows and the CLI verifier. Stop treating the hash chain as a completed non-repudiation feature until Phase 10 anchors it externally.

Action: **defer to Phase 10** for self-write-on-break and stronger tamper-evidence claims; keep durable rows and local verification as the defended v1 baseline.

### OE-6 - Future-facing dependencies and ABI scope violate the project's own "nothing speculative" rule

Severity: **Low**

Claim: Some stack surface exists for future consumers, not the v0.5.4 or Phase 8 consumer.

Evidence: `prometheus-client` is a direct dependency (`pyproject.toml:27`) while metrics are explicitly Phase 10 (`docs/implementation-plan.md:234`, `docs/architecture.md:856`). `coincurve` is a direct dependency (`pyproject.toml:20`), but `rg` found no `src/fwd` use; the historical spike says key generation used `eth_account.Account.create()`, not `coincurve` (`docs/history/0.2.0-spike-coston2.md:40`). The ABI registry ships ERC20 even though the README says it has "no consumer at v0.5.0" (`config/abis/README.md:93-95`).

Why disproportionate or speculative: These are exactly the additions guideline 2 warns against: future observability, future HSM/raw signing support, and future token wallets (`CLAUDE.md:248-249`).

Cost: More dependencies to audit, lock, build, patch, and explain; more ABI files to keep synchronized; more accidental attack surface in a public repo.

Steelman: Each item is small in isolation. `prometheus-client` is pure Python and likely harmless, `coincurve` preserves a known secp256k1 primitive, and ERC20 ABIs are public and cheap.

Net verdict: Small does not mean free. The project should prove its anti-speculation doctrine by removing these until a named consumer lands.

Action: **cut now**.

## 3. Under-Engineering / Gaps

### UE-1 - The first real consumer integration is the missing product

Severity: **High**

Claim: The real under-engineered surface is not more signer substrate; it is the Phase 8 `ftso-fee-claimer` cutover path.

Evidence: Core #7 says deleting `.env PRIVATE_KEY=` is what `fwd` exists to do (`CLAUDE.md:144`). Phase 8 deliverables require a production wallet, policy entry, on-chain claim-recipient rotation, `ftso-fee-claimer` calling `/v1/sign-and-send`, deletion of the old `.env` key, Songbird rehearsal, and Flare epoch success (`docs/implementation-plan.md:183-198`). At the v0.5.4 checkpoint, the audit prompt's ground truth says zero production `.env PRIVATE_KEY=` lines have been deleted (`docs/reviews/v0.5.4-stack-and-overengineering-audit.md:26-33`).

Why this matters: Every additional substrate ship before the first cutover increases the chance that the project optimizes abstractions instead of value. The first migration will reveal the actual client ergonomics, policy shape, runbook holes, and operational pain.

Action: Make Phase 8 adapter/runbook/live rehearsal the next work item; do not add new generic substrate first.

### UE-2 - If Vault stays, production unseal/share hygiene is a blocker, not a doc footnote

Severity: **High**

Claim: The production Vault ceremony is under-tested relative to its importance.

Evidence: Core #17 allows the dev shortcut only before real privkeys, then mandates wipe-and-redo, deleting the dev init file, rerunning Vault init, and distributing 3-of-5 shares across distinct failure domains before the first production migration (`CLAUDE.md:164`). Phase 8 starts with a production wallet in Vault (`docs/implementation-plan.md:187-198`).

Why this matters: If the Operator keeps Vault, the first production migration is only safe after this ritual is rehearsed and accepted. A production key behind the single-laptop dev shortcut is explicitly "structurally indistinguishable" from the `.env PRIVATE_KEY=` pattern (`CLAUDE.md:164`).

Action: Treat production Vault reset/share distribution as a Phase 8 gate, not background ops.

### UE-3 - The documented v1 API surface is not the shipped API surface

Severity: **Medium**

Claim: Architecture promises endpoints that are not present in the app at v0.5.4.

Evidence: `docs/architecture.md` says the v1 API surface is frozen and lists `POST /v1/sign-typed-data`, `GET /v1/wallets`, and `GET /v1/audit` (`docs/architecture.md:323-333`). The app includes only health, wallets admin, sign, callers, and transactions routers (`src/fwd/main.py:356-360`). CLI docs still call caller-facing `GET /v1/wallets` Phase 7+ (`src/fwd/cli/wallets.py:73-80`). `rg` found no `def sign_typed` or sign-typed route under `src/fwd`.

Why this matters: This is not a correctness bug for Phase 8 if `ftso-fee-claimer` only needs `/v1/sign-and-send`, but it is a consumer-contract risk. The docs say "frozen for v1"; consumers and future agents will trust that unless corrected.

Action: Before Phase 8, the Reviewer should adjudicate whether these endpoints remain v1 commitments or are explicit Phase 9/10 deferrals.

### UE-4 - Decoded intent is not persisted where the schema says it will be

Severity: **Medium**

Claim: The project built `transaction_args` and ABI decoding, but the transaction record still stores only selector-level method data.

Evidence: The architecture signing flow says decoded args are inserted into `transaction_args` (`docs/architecture.md:194`), and the schema defines `transaction_args` (`docs/architecture.md:286`). The sign-and-send persistence path sets `contract_address = request.to` and `method_name = request.data[:10]` (`src/fwd/app/sign_and_send.py:380-383`). `rg transaction_args` found only Alembic/docs/history hits, not `src/fwd` writes.

Why this matters: The audit log carries request/decision context, but transaction status and history remain weaker than the schema and doctrine imply. For Phase 8 forensics, selector-only transaction records make downstream status review less useful.

Action: The Reviewer should adjudicate whether decoded-arg persistence is a Phase 8 gap or whether selector-only transaction rows are the intended v1 contract.

## 4. Doctrine-To-Code Proportionality

Verdict: **not proportionate as currently operated.** The code volume is not the problem by itself: 415 passing tests, 4 integration skips due unreachable dev Vault, and the v0.4.5/v0.5.2 live failures justify a serious test and live-drill culture. The disproportion is the ongoing ratio of doctrine/workflow/history to the single missing value event.

The measurable spine is stark: 6,857 source LOC, 11,400 test LOC, 2,570 core doctrine LOC across five core docs, 43 history files, 56 test files, 51 source files, 25 direct dependency roots, 82 installed-package lines, four compose services, and about 1.25 GB of visible runtime images. The project also has drift despite Core #18: hot reload vs startup-only (`docs/architecture.md:105`, `docs/architecture.md:605-607`), Scaleway backup docs vs local backup compose (`docs/architecture.md:834-844`, `docker-compose.yml:124-134`), ABI README `None` framing vs B1 projection (`config/abis/README.md:69-74`, `src/fwd/domain/intent.py:6-13`), and `busy_timeout=5000` in a module docstring vs `30000` in code (`src/fwd/infra/db.py:1-4`, `src/fwd/infra/db.py:54-62`).

Keep the doctrine that names real defect classes: Core #14, Core #17, Core #19, default-deny, no `.env PRIVATE_KEY=`, and the live Coston2 verification gate. Consolidate or stop the doctrine that functions mainly as process metadata: doctrine-only version bumps, duplicated history paragraphs, wrapper/HAND-OFF formalism for low-risk edits, and multiple places describing the same runtime surface.

## 5. Time-To-Value

The pace served custody discipline through Phase 7, but it is now slowing the project relative to its purpose. From the 2026-04-30 start to the 2026-05-17 v0.5.4 checkpoint, the project delivered a careful substrate and zero production key deletions (`docs/reviews/v0.5.4-stack-and-overengineering-audit.md:26-33`). That trade was acceptable before live policy/audit proof. It stops being acceptable after Phase 7 GA because the next unknowns are in the first real consumer integration, not in more generic substrate.

The one change that accelerates value without sacrificing proven custody discipline: make the next ship exclusively the Phase 8 `ftso-fee-claimer` migration rehearsal and cutover path, with no new generalized platform capability unless that migration blocks on it.
