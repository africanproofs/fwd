- Phase 8b: GO — the next substantive ship should be Phase 8b, not another audit; Vault is gone, the sealed-master path has live testnet evidence, and remaining issues are bounded cutover controls.
- Stack verdict: mostly right after the Vault deletion; keep the two-service stack, harden master-file opening, and stop treating Litestream as custody restore.
- Over-engineering verdict (delta since v0.5.5): code complexity fell materially, but process ceremony routed around the freeze under "Phase 8 in-ship" labels.
- Freeze integrity: routed-around — v1.0.0a1 was legitimate Phase 8 custody work, but v1.0.0a3 still shipped scope/history/runbook reconciliation instead of the first production key deletion.

## Phase 8b readiness checklist (ordered, ≤7, each custody-justified)
1. Harden the master-key file load before the production key: open and `fstat` the same inode, reject symlinks where the platform supports it, confirm regular file, `0600`, current uid, and exactly 32 bytes. This protects the root encryption key.
2. Make the operator DR choice explicit at cutover: either back up `config/master.key` out of band, or accept regeneration-only DR and confirm the identity wallet can run `setClaimRecipient` after host loss. Litestream alone cannot recover sealed keys.
3. Install the Phase 8b policy with only the required FTSO reward/claim-recipient call surface, fixed chain, fixed beneficiary where applicable, and no generic transfer/approval allowance. This limits signer abuse.
4. Move the caller key into fwd sealed custody and delete the active `.env PRIVATE_KEY` fallback from the fee-claimer path. This is the actual custody migration.
5. Run one lower-stakes Songbird claim path through fwd using the same caller-generated calldata that production will use. This catches runbook-shape defects before Flare value is at stake.
6. Run the Flare production claim path through fwd, then verify RPC receipt, `from`, target contract, and fwd audit-chain continuity. This proves custody and forensic trace for the real asset path.
7. Operator spot-check the v1.0.0a3 Coston2 transaction evidence before trusting it as a gate: hash `0xc222bf62d30017daf67f42d472677ee0ffe6afb35592c0895a4c1d957b5ac5e6`, block `30662555`, `from` `0xf49c60a324553956d197c4c5bc15b57b0adb4231`.

## Findings (≤8, ≤120 words each, stakes-rated)

1. **[CORRECTNESS] Restore guidance is incompatible with the current custody model.** `docs/runbooks/restore.md:3-15`, `44-49`, `54-62`, `210-260`, and `548-566` still require Vault snapshots, Vault env vars, and Vault health. Current Compose has only `fwd` and `litestream` (`docker-compose.yml:1-84`), while Litestream backs up only `/data/state.db` (`config/litestream/litestream.yml:16-23`). Steelman: this is documentation drift, and D1/Core #17 intentionally allow regeneration plus `setClaimRecipient`. Net: Phase 8b may proceed only if the operator does not believe the old restore runbook recovers sealed keys.

2. **[CORRECTNESS] SealedMaster validates a path, then opens it.** `src/fwd/infra/sealed_master.py:36-49` checks `isfile`, mode, owner, and size before `open(path, "rb")`; it does not bind validation to the file descriptor, reject symlinks explicitly, or address root execution. Steelman: an attacker able to race or replace `config/master.key` likely already has serious local access, and private-host operation is the accepted model. Net: one small hardening belongs in Phase 8b because this file is the whole custody root.

3. **[DRIFT/DOCTRINE] Active doctrine still describes Vault as live custody.** `CLAUDE.md:9`, `174`, `docs/threat-model.md:102-144`, and `docs/decisions.md:47-69` still present Vault/AppRole/Transit as active or semi-active guidance, while `docs/history/1.0.0a1-vault-to-sealed-master.md:7-15` says Vault was removed. Steelman: the project explicitly chose in-ship reconciliation and the core invariants now contain honest sealed-master blast-radius text at `CLAUDE.md:144-180`. Net: do not block Phase 8b, but stop using stale doctrine as an authority over current code.

4. **[DRIFT/DOCTRINE] The freeze was routed around, not held.** `MEMORY.md:3-5` points to the freeze, and `doctrine-ship-freeze-in-effect.md:10-30` says no more doctrine/reconciliation/audit ships before Phase 8. v1.0.0a1 was real custody simplification, but v1.0.0a3 added scope/history/runbook reconciliation after the freeze (`docs/history/1.0.0a3-sealed-master-verification-met.md:17-70`). Steelman: those edits captured live evidence and corrected a real runbook defect. Net: enough; the next substantive change must be Phase 8b execution, not meta-work.

5. **[CORRECTNESS] The runbook-defect pattern is real.** The Coston2 drill found that an assumed empty-`data` transaction was denied; the corrected path used ERC20 `transfer(amount=0)` calldata (`docs/history/1.0.0a3-sealed-master-verification-met.md:37-53`, `docs/runbooks/v1.0.0a1-sealed-master-verification.md:148-160`). Steelman: the live gate improved the runbook and proved the policy denied an unsafe shape. Net: for Phase 8b, the Reviewer must not invent transaction shapes; production rehearsal must use calldata generated by the actual fee-claimer path.

6. **[CORRECTNESS] Live evidence is self-reported by the Reviewer, not independently observed here.** The project records tx hash, block, sender, 37-row audit verification, and 426 passing tests (`CLAUDE.md:73-79`, `docs/history/1.0.0a1-vault-to-sealed-master.md:39-45`, `docs/history/1.0.0a3-sealed-master-verification-met.md:17-28`, `57-60`). Steelman: the evidence is specific and operator-verifiable, and I independently observed `426 passed in 17.17s`. Net: do not rerun the audit loop; the operator should spot-check the public transaction and audit command during Phase 8b.
