# fwd v0.5.5 - Second Independent Audit Report

## 0. Executive Verdict

Stack verdict: **Mostly right, 3 components misfit**: Vault until its audit device is made real, receipt replacement-on-stuck for the first low-volume consumer, and the hash-chain's unanchored tamper-evidence claims. Over-engineering verdict: **Process has become the product**: v0.5.5 improved real drift, but also added review/doctrine surface while leaving material drift and literal NUL bytes behind. Vault recommendation: **keep Vault for Phase 8**, because replacing custody substrate now is riskier than using a mature envelope service, but durable Vault audit logging and the Core #17 production wipe-and-redo are hard entry gates before the first production key. If durable Vault audit logging cannot be enabled before that key exists, replace Vault before custody. The Reviewer's ERC20, `coincurve`, and idempotency contests are mostly sound; the Reviewer's NUL/process and Vault-audit handling are not. This fourth audit did need to exist because it found a false NUL-closure claim, stale security doctrine, and an absent Vault audit device. No fifth audit is warranted if these are adjudicated; ship Phase 8.

## 1. Triangulation

Cold verdict before re-reading the third audit's conclusions: **Mostly right, 3 components misfit** on stack, and **Process has become the product** on over-engineering. The source evidence led there directly: Phase 8 is still the first production `.env PRIVATE_KEY=` deletion (`docs/implementation-plan.md:183-198`); the D1 pivot makes Vault an envelope service, not a signer (`docs/decisions.md:9-31`); the threat model admits compromised `fwd` can decrypt every managed wallet (`docs/threat-model.md:106-120`); and v0.5.5 itself records that the doctrine corpus had drifted against Core #18 (`docs/history/0.5.5-audit-reconciliation.md:13-17`).

Where I agree with the third audit:

- The core stack is not sloppy. Python/FastAPI, SQLite, explicit policy, ABI intent decoding, `eth-account`, `httpx`, local Docker Compose, and live Coston2 drills are defensible for a single-host signing daemon. Phase-1 measurements still support that: `415 passed, 4 skipped`, `419 tests collected`, 6,861 `src/fwd` LOC, 11,400 test LOC, 24 direct dependency roots after `prometheus-client` removal, 82 installed packages, and four compose services.
- Vault is the load-bearing stack question. D1 says Vault only wraps and unwraps 32-byte plaintext under `aes256-gcm96` (`docs/decisions.md:25`), while the threat model says `fwd` or leaked AppRole plus ciphertexts can recover all keys (`docs/threat-model.md:106-144`).
- Process has outrun delivered value. The project has 44 history docs, about 2,641 lines across the five core doctrine files plus v0.5.5 history, four audit prompt/report files, and zero production key deletions.
- Receipt replacement and hash-chain anchoring remain ahead of the first production consumer (`src/fwd/app/receipt_watcher.py:61-102`, `src/fwd/app/receipt_watcher.py:198-318`, `docs/decisions.md:720`, `docs/architecture.md:839-842`).

Where I diverge:

- The third audit's "6 components misfit" is now too high after v0.5.5. `prometheus-client` was cut; ERC20, `coincurve`, and idempotency have enough evidence to keep through Phase 8; decoded-intent persistence now has an explicit Phase-8 marker (`docs/architecture.md:199-207`, `docs/implementation-plan.md:295`).
- The third audit under-specified Vault. The decisive new fact is not only that Vault is envelope-only; it is that the threat model relies on Vault audit logs (`docs/threat-model.md:116`, `docs/threat-model.md:141`) while the current init/config path does not enable a Vault audit device.
- The third audit could not evaluate v0.5.5's reconciliation quality. That reconciliation made the NUL problem worse in at least three doctrine files by leaving actual NUL bytes where it claimed the class had been closed.

Where the first auditor was wrong:

- **ERC20 cut recommendation:** wrong after cross-checking the GA runbook. ERC20 `transfer(address,uint256)` calldata is the Phase 7 live deny-matrix vector (`docs/runbooks/phase-7-verification.md:315-371`), and the ABI README now correctly calls it load-bearing (`config/abis/README.md:108-114`).
- **`coincurve` cut recommendation:** wrong as a Phase-8 cut. `pyproject.toml` explicitly pins it as the secp256k1 backend (`pyproject.toml:20`); observed runtime backend is `eth_keys.backends.coincurve.CoinCurveECCBackend`. The pin is a supply-chain legibility choice, not an unused feature import.
- **Idempotency cut recommendation:** wrong for this checkpoint. It is subtle and should not grow, but removing live-proven retry protection after v0.5.3 would be higher risk than carrying the D14 caveat through Phase 8 (`docs/decisions.md:525`, `src/fwd/app/sign_and_send.py:175-211`).

## 2. v0.5.5 + Adjudication Audit

v0.5.5 did close real drift. It reconciled shipped vs deferred API surface (`docs/architecture.md:335-345`), marked `transaction_args` as Phase 8 rather than pretending it is wired now (`docs/architecture.md:199-207`), corrected local-volume backup reality (`docs/architecture.md:844-850`), documented ERC20 as the GA vector (`config/abis/README.md:108-114`), cut `prometheus-client`, and kept the test suite green with `415 passed, 4 skipped` (`docs/history/0.5.5-audit-reconciliation.md:51-53`).

It did **not** close the drift class. A byte scan found actual NUL bytes in `docs/decisions.md:653`, `docs/implementation-plan.md:294`, `docs/history/0.5.5-audit-reconciliation.md:22`, and an older history file. `file -b docs/decisions.md docs/history/0.5.5-audit-reconciliation.md` reports `data`, and `git show --stat 904030f` treats `docs/history/0.5.5-audit-reconciliation.md` as binary (`Bin 0 -> 8512 bytes`). That directly contradicts the history claim that the second NUL was caught and removed before commit (`docs/history/0.5.5-audit-reconciliation.md:22`).

The three Reviewer contests:

- **ERC20 kept: sound.** Steelman for cutting it: Phase 8 signs RewardManager `claim`, and every extra ABI broadens registry surface. Evidence against the cut is stronger: the Phase 7 live deny matrix uses ERC20 `transfer` calldata throughout (`docs/runbooks/phase-7-verification.md:315-371`), and the README ties ERC20 to the GA gate and Phase 9 token-wallet shape (`config/abis/README.md:108-114`). Net: keep and defend.
- **`coincurve` kept: sound, with a narrower rationale.** Steelman for cutting it: `rg` finds no direct `src/fwd` import, and `eth-account` can be installed without a direct `fwd` pin. Evidence for keeping: the project deliberately pins the active secp256k1 backend in `pyproject.toml:20`, and a runtime check showed `eth_keys.backends.coincurve.CoinCurveECCBackend`. Net: keep and defend as a custody-path supply-chain pin, not as "code imports it."
- **Idempotency replay kept: sound for Phase 8.** Steelman for cutting it: D14 says replay does not re-evaluate policy and can survive policy tightening unless the caller key is rotated (`docs/decisions.md:525`); the code checks idempotency before wallet resolution and policy gate (`src/fwd/app/sign_and_send.py:175-211`). Evidence for keeping: the branch is live-proven, records a `sign-and-send-duplicate` audit row, avoids duplicate signing after response-loss, and D14 already places policy-hash binding in Phase 10. Net: keep and defend through Phase 8; do not expand it.

The Reviewer's scope expansion was partly correct and partly self-validating. Correct: Core #18 required fixing more drift than the third auditor listed once the class was discovered. Unsound: the same ship that claimed byte-level hygiene left binary doctrine files behind, left material security drift in architecture, and left `docs/dependencies.md` stale. The result is an audit-reconciliation ship that proves both sides of the thesis: the Reviewer found real defects, and the process is now heavy enough to generate more defects while documenting the fix.

## 4. Over-Engineering Findings

### OE-1 - v0.5.5 and this fourth audit are now part of the process-over-product problem

Severity: **High**

Claim: The v0.5.5 reconciliation was necessary, but it also demonstrates that audit/reconciliation ships are consuming product momentum and creating new maintenance surface.

Evidence: `git show --stat 904030f` shows v0.5.5 added 440 insertions and 57 deletions, including a 136-line audit prompt, a 228-line audit report, 57 architecture lines, a history file reported as binary, and only one non-version `src` touch: a `db.py` docstring. The implementation ledger says Phase 8 is the first production migration and key deletion (`docs/implementation-plan.md:183-198`), but v0.5.5 inserted another reconciliation row and entry-gate sequence (`docs/implementation-plan.md:294-295`). This fourth audit found that the NUL class was not closed and that Vault audit logging was never enabled, so even the reconciliation needed reconciliation.

Steelman: The audit/reconciliation loop found real issues: stale API docs, stale backup docs, the `prometheus-client` cut, and the false ERC20 README framing. This fourth audit also found real operator-facing facts that should not be ignored.

Net verdict: v0.5.5 was worth doing once; continuing the pattern is now the anti-pattern. The process has earned one final hygiene cleanup, then it must stop blocking Phase 8.

Action: **{cut now}** Freeze non-Phase-8 doctrine/reconciliation/audit ships after the NUL/stale-doctrine cleanup.

### OE-2 - Vault is defended by an audit property that is not enabled today

Severity: **High**

Claim: Vault can still be the right Phase-8 choice, but the current defense is incomplete because the Vault audit device is absent.

Evidence: The threat model relies on Vault's audit device logging every decrypt/operation independently of `fwd` (`docs/threat-model.md:116`, `docs/threat-model.md:141`). `scripts/vault-init.sh` enables Transit, creates the master key, writes policies, enables AppRole, and creates roles, but contains no `vault audit enable` step (`scripts/vault-init.sh:24-94`). `config/vault/config.hcl` configures Raft storage, TCP listener, API/cluster addresses, UI, mlock, and log level, but no audit device (`config/vault/config.hcl:1-19`). `docker-compose.yml` mounts Vault data, config, and scripts, but no durable audit-log volume (`docker-compose.yml:18-21`). A targeted `rg --text` over scripts, Vault config, compose, and runbooks found audit documentation but no audit-enable command.

Steelman: Vault still buys real things over a small sealed-master file: a mature non-exportable master-key API, Shamir unseal, AppRole scoping, Raft snapshot/restore, operator familiarity, and a Phase 10 migration path. Avoiding a new home-grown custody primitive right before Phase 8 is prudent.

Net verdict: Keep Vault, but only as an explicitly chosen operations/audit substrate with audit logging made real before production keys. Without Vault audit logs, Vault's main differentiator over a Shamir-sealed local master is materially weaker.

Action: **{OPERATOR DECISION}** Keep Vault and enable durable audit logging before the first production key; if that cannot happen, replace Vault before custody.

### OE-3 - v0.5.5 left material doctrine drift after claiming class closure

Severity: **High**

Claim: The reconciliation did not merely miss cosmetic drift; it left security-relevant contradictions in canonical docs.

Evidence: `docs/architecture.md` still says the `fwd -> Vault` boundary lets an attacker request signatures but "cannot extract keys" (`docs/architecture.md:69-70`). D1 says Vault is only an encryption envelope that wraps and unwraps 32-byte plaintext (`docs/decisions.md:25`), and the threat model says compromised `fwd` can decrypt all wallet private keys (`docs/threat-model.md:106-120`). `docs/dependencies.md` still says Vault provides "Custody + signing (Transit engine, ECDSA secp256k1)" and Litestream replicates to S3-compatible storage (`docs/dependencies.md:31-35`), lists `hvac` although the project uses `httpx` for Vault (`docs/dependencies.md:47-48`), and describes three compose services while compose has four (`docker-compose.yml:1-116`).

Steelman: v0.5.5 improved several high-traffic docs, and `docs/dependencies.md` may be less canonical than `architecture.md` and `decisions.md`. The Reviewer was right to expand beyond the auditor's exact line list once Core #18 drift was proven.

Net verdict: Leaving the Vault trust-boundary sentence is a serious miss because it restates the dead Transit-signing security property. The reconciliation cannot be considered closed until these contradictions are removed.

Action: **{cut now}** One bounded cleanup of NUL bytes plus the Vault/dependency drift; no new doctrine.

### OE-4 - Receipt replacement-on-stuck is overbuilt for the first production consumer

Severity: **Medium**

Claim: Automatic re-sign/rebroadcast is more machinery than Phase 8 needs.

Evidence: The watcher continuously polls submitted transactions and can re-sign/rebroadcast with bumped fees (`src/fwd/app/receipt_watcher.py:61-102`, `src/fwd/app/receipt_watcher.py:198-318`). Defaults poll every 2 seconds, treat 30 seconds as stuck, and retry up to 5 times (`src/fwd/settings.py:47-53`). Phase 8 is one `ftso-fee-claimer` cutover and one full reward epoch on Songbird and Flare (`docs/implementation-plan.md:183-198`), not a high-QPS sender.

Steelman: Nonce continuity matters. A stuck transaction can block later nonces, and the project has repeated live evidence that chain behavior invalidates mock-only confidence.

Net verdict: The watcher should not be expanded before Phase 8. Deleting it now is not worth the churn, but it should be treated as frozen legacy surface until production traffic proves it needs more automation.

Action: **{defer to Phase 10}** Keep status tracking and existing behavior frozen; defer replacement sophistication.

### OE-5 - The hash-chain is useful, but its strongest tamper-evidence story is still Phase 10

Severity: **Medium**

Claim: Durable audit rows are load-bearing; the hash-chain should not be sold as completed non-repudiation until it is externally anchored.

Evidence: D16 says an attacker with SQLite write access can modify a row and recompute hashes forward, and only an external anchor or out-of-band snapshot detects that (`docs/decisions.md:720`). Architecture repeats that the chain is only as anchored as operator snapshots until Phase 10 on-chain anchoring (`docs/architecture.md:839-842`). The `audit-verify-failure` self-write remains deferred (`docs/decisions.md:643-649`).

Steelman: The audit log is a real improvement over `.env PRIVATE_KEY=`. The v0.5.2 live drill proved that missing denied/error rows are not academic, and local verification catches accidental corruption or partial tampering.

Net verdict: Keep the audit rows and CLI verifier. Stop adding audit-chain doctrine or semantics before Phase 8; stronger anchoring belongs in Phase 10.

Action: **{defer to Phase 10}** Keep local verification; defer self-write-on-break and external anchoring.

## 5. Fastest Path To The First `.env` Deletion

The blocker is not another architecture decision record. The blocker sequence is:

1. Remove literal NUL bytes and reconcile the remaining Vault/dependency doctrine contradictions. This is a hygiene fix, not a new process.
2. Operator chooses Vault under this audit's recommendation: keep Vault, enable durable Vault audit logging, and rehearse the Core #17 production wipe-and-redo before any production key.
3. Do the Phase 8 production cut: production wallet, policy entry, on-chain `setClaimRecipient`, `ftso-fee-claimer` calling `/v1/sign-and-send`, delete the first `PRIVATE_KEY` line, then complete Songbird and Flare epoch proof (`docs/implementation-plan.md:183-198`).

The decoded-intent to `transaction_args` gate should not become a fresh substrate project. Architecture already says the audit log carries the full decoded intent and forensics are not blind while `transaction_args` is unwired (`docs/architecture.md:199-207`). If the Operator wants that projection before the first epoch, do it as Phase 8 work only; do not let it justify another reconciliation ship.

The GitLab push block is a reproducibility/release-management risk, not a reason to keep auditing. The local checkpoint is 11 commits ahead of `origin/main` by observed `git rev-list --count f1ee3f1..HEAD`; the Operator must decide whether production may proceed from local-only history or whether remote publication is required before deployment. Do not solve that by adding more doctrine.

Freeze recommendation: **yes**. Freeze all non-Phase-8 doctrine, reconciliation, and audit ships until the first production `.env PRIVATE_KEY=` line is deleted.

Self-indictment: this fourth audit was the right move because it found unsound claims that affect Phase 8. A fifth audit is not the right move unless the bounded cleanup reveals a Critical key-loss defect.

## 6. Decisions Only The Operator Can Make

1. **Vault keep-vs-replace.** Recommendation: keep Vault for Phase 8. Trade-off: Vault keeps mature Shamir/AppRole/Raft operations and avoids new custody code, but it must enable durable audit logs or it loses the property the threat model relies on. If durable audit logging is refused or impossible, replace Vault before custody.
2. **Audit/reconciliation freeze.** Recommendation: freeze after one hygiene cleanup. Trade-off: the Reviewer may argue Core #18 requires more reconciliation first; the cost is delaying the only value event that matters.
3. **Local-only history under GitLab block.** Recommendation: decide explicitly before production deployment. Trade-off: proceeding local-only may be acceptable for a same-host operator cutover, but it weakens shared provenance and registry/release reproducibility.
4. **`transaction_args` as Phase-8 gate.** Recommendation: do not let it block the first key deletion unless the Operator specifically needs SQL projection of decoded args before the first epoch. Trade-off: forensics remain available in audit `request_json`/`decision_reason`, but transaction-table queries remain weaker until the projection is wired.
5. **Reviewer adjudication of this report.** Recommendation: route OE-1, OE-2, and OE-3 directly to the Operator if contested. Trade-off: the Reviewer is the audited party for v0.5.5; letting the same party neutralize the process findings would defeat this audit's purpose.
