## What `fwd` is (one paragraph context)

`fwd` is the Flare Wallet Daemon: a policy-gated signing service for African Proofs (AP)' EVM backend keys. It exists to delete every `.env PRIVATE_KEY=` line in AP's automation (`ftso-fee-claimer`, `apregister/`, `apcli`, future `fics` write paths, future autonomous agents) and replace them with one HTTP call to a service that knows the signing policy, owns an append-only audit, and never lets plaintext keys touch disk. It is single-host, single-replica, single-operator, Docker-Compose deployed, with HashiCorp Vault Transit (`aes256-gcm96`, `exportable=false`) doing envelope encryption of externally-generated secp256k1 privkeys, and `eth-account` doing the actual signing in `fwd`'s own process post-decrypt. v1 ships through Phase 8 (`ftso-fee-claimer` migration); Phase 10 is post-v1 hardening (auto-unseal, optional YubiHSM 2, on-chain audit anchor, mTLS).

Read `CLAUDE.md` § Identity (lines 1–11) and § Scope (the v0.3.1 paragraph) before you do anything else. They are the official self-description.

## Audit chapters

### Chapter 1 — Custody correctness

The single most important property. If `fwd` leaks a privkey, every other concern is moot.

Investigate:

- The privkey lifecycle in `EnvelopeSigner.create_wallet` (`src/fwd/infra/envelope_signer.py`). `Account.create()` returns a `LocalAccount` with `.key: bytes` (immutable). The code wraps in `bytearray(account.key)` and `_zeroize`s on `finally`. Does the *original* `account.key` `bytes` object survive past zeroization? At what point does it become unreachable?
- The privkey lifecycle in `EnvelopeSigner.sign_transaction`. `await self._vault.decrypt(ciphertext)` returns `bytes` (immutable). Same wrap-and-zeroize pattern. Same question.
- The `bytes(privkey_buf)` cast at the call site of `Account.from_key(...)`. `bytes()` on a `bytearray` produces a fresh immutable `bytes` object. The `bytearray` gets zeroized; the `bytes` does not. Where does that `bytes` object live, for how long, and is the practical exposure window bounded?
- The token cache in `VaultClient` (`src/fwd/infra/vault_client.py`). The `__aexit__` does `self._token = "0" * len(self._token); self._token = None`. Python strings are immutable; the original token's underlying buffer may persist in the interpreter's string interning or recent allocations until GC. Is this best-effort acceptable, or is it security theatre?
- Core invariant #1 claims `mlock`-protected process memory. Where is `mlock` called? (Search the codebase. If absent, this is a doctrine-vs-reality drift to flag.)
- Core invariant #16 claims no plaintext caching between requests. Is there *any* code path — including caches inside `eth_account` itself — that holds a privkey reference past `sign_transaction` return? The `LocalAccount` object created by `Account.from_key(bytes(privkey_buf))` may retain the key internally; does `signed = LocalAccount.sign_transaction(tx_dict)` then `del LocalAccount` happen? (It doesn't explicitly — the `LocalAccount` is a bound expression in the `try` block.)
- The structlog scrubber from architecture.md hazard #3 is NOT yet in place (Phase 7 deliverable). Trace every `logger.info/warning/error/exception` call in the codebase. Does any of them currently pass a value that could contain a privkey, signed_raw, or 32-byte hex? (Spot-check `app/sign_and_send.py`'s `sign_and_send.ok` event, `infra/vault_client.py`'s `vault.login.success` and `vault.403.reauth` events.)
- The Docker volume `vault-data` persists Vault's Raft state across container restarts. After `docker compose down -v`, all state is destroyed (including the master key). Confirm this is the only operator-side reset path.

Severity guide for this chapter: a real plaintext-leak path is **Critical**. A theoretical leak window measurable in microseconds and bounded by GC is **Observation** if it matches an existing documented caveat (architecture.md hazards #2). A pattern that increases the leak window unnecessarily is **High**.

### Chapter 2 — Auth surface

`fwd`'s auth boundary in v0.3.1 is exactly two tokens: `FWD_VAULT_ROLE_ID` + `FWD_VAULT_SECRET_ID` (env-injected, used to obtain a Vault client_token), and `FWD_ADMIN_KEY` (env-injected, presented as `Authorization: Bearer <key>` for the two admin endpoints).

Investigate:

- `src/fwd/api/admin_auth.py::require_admin`. Constant-time compare via `hmac.compare_digest`? Yes — verify. Are there other places (the `clifwd` CLI? logging?) that compare admin tokens with `==` or otherwise leak timing?
- `src/fwd/infra/vault_client.py::_login`. The role_id + secret_id are sent in the request body as JSON. The httpx pool is unencrypted HTTP (Vault is on `fwd-internal` Docker network with `internal: true`; TLS is not configured). Is the Docker bridge a trustworthy boundary? Read `docker-compose.yml` `networks:` block.
- `scripts/vault-init.sh` configures `secret_id_ttl=0 secret_id_num_uses=0`. Once minted, `fwd`'s secret_id never expires and has unlimited uses. What's the rotation story? (Per `decisions.md` D10, periodic-token migration at Phase 8 changes the role config; secret_id rotation becomes operator-driven hygiene.) Is the dev-mode "non-expiring secret_id" acceptable, given Core invariant #17's wipe-and-redo at Phase 8?
- The 403-fallback in `VaultClient._request`. On a 403, the code re-authenticates and retries once. Is this the right semantic? What if the 403 is *not* token expiry but actual policy denial (e.g., the operator manually revoked `fwd-app` policy)? The current code would re-auth (succeed) and retry (re-fail with 403). The second-403 raises `VaultError`. Does this surface clearly? Could a flapping policy mask a real auth issue?
- The admin endpoint shape. `POST /v1/admin/wallets` (Phase 3b) and `POST /v1/sign-and-send` (Phase 3c, currently admin-gated until Phase 4). The latter is anomalous: it's *not* an admin endpoint conceptually — it's a caller endpoint that's temporarily admin-gated. Does the URL prefix `/v1/` (not `/v1/admin/`) signal correctly? Is there documentation that a user reading the API surface in v0.3.1 might miss?
- `FWD_ADMIN_KEY` is a single static env var. No rotation possible without a service restart. Acceptable for v0.3.1's operator-driven dev posture? At what phase does this need to change?
- Phase 4 will replace `admin_required` with `caller_required` for `/v1/sign-and-send`. The `admin_required` symbol stays for the `/v1/admin/*` endpoints. What design risk should the team flag now? (The conflation of "admin" and "caller" auth in v0.3.1 may make the Phase 4 boundary harder to draw.)

### Chapter 3 — Layer architecture

`docs/architecture.md` § Layer boundaries asserts a four-layer separation: `domain` (pure, no I/O), `app` (orchestration), `infra` (adapters), `api`+`cli` (interface). `tests/unit/test_layer_boundaries.py` enforces import-graph rules.

Investigate:

- Does `tests/unit/test_layer_boundaries.py` cover all the rules in `architecture.md` § Layer boundaries → Enforcement? Specifically: the spec says "interface goes through app, not infra directly". The test allows `api: {app, domain}`. Are there other rules in the spec that the test doesn't enforce?
- The composition root pattern in `app/dependencies.py`. `SignerCM.__aenter__` opens both `VaultClient` and `session_scope` and constructs an `EnvelopeSigner`. `RpcManagerCM.__aenter__` constructs an `RpcManager`. Both managers delegate to infra. Is the layer rule `app: {domain, infra}` correct, or should `app/dependencies.py` be considered an infra-adjacent "wiring" file that violates the spirit of the spec?
- The `from fwd.infra.rpc import ALLOWED_CHAINS as ALLOWED_CHAINS` re-export idiom in `src/fwd/app/sign_and_send.py`. Is this a legitimate way to expose an infra constant through the app layer, or a sleight-of-hand around the boundary test?
- `VaultUnavailableError` is defined in *both* `src/fwd/app/wallet_create.py` and `src/fwd/app/sign_and_send.py`. Sonnet flagged this in their v0.3.0 implementation report as a future consolidation point. Is the duplication a real coupling concern (an api handler that catches one variant won't catch the other), or fine for v0.3.1's two-use-case scope?
- `src/fwd/settings.py` lives at the package root, not under any of the four layers. Is its layer assignment unambiguous? Domain code is forbidden from importing it; infra/app/api/cli may. Does the layer-boundary test enforce that, or is `settings` a free-for-all?
- The `cli/wallets.py` is a thin HTTP client that mirrors `cli/main.py::health`. It does NOT instantiate `VaultClient` or `WalletRepo` directly — good. But Phase 4 will add `clifwd wallets import`, which (per D9) is CLI-only-no-HTTP and DOES need direct in-process Vault + repo access. How does the team plan to add an in-process CLI flow without violating the existing "CLI is HTTP client" pattern?

### Chapter 7 — Phase 4–8 risks

The team is about to enter Phases 4–8. What design assumptions baked into v0.3.1 are likely to bite during those phases? Where will the team be tempted to take shortcuts?

Investigate:

- **Phase 4 (caller auth, v0.4.0-alpha)**. Will replace `admin_required` with `caller_required` for `/v1/sign-and-send`. Will add `clifwd callers create|list|revoke`, argon2id-hashed API keys, a `callers` table, bearer middleware on all `/v1/*` (except `/healthz`). Risks:
  - The current `admin_required` swap is one-line. But the *policy_path* on a caller (per `callers` table) needs to thread through to wallet-create + sign-and-send to determine permitted actions. The current `WalletCreateRequest.policy_path` is a free-form string with no validation. Phase 7 introduces real policy. Will the Phase 4 → Phase 7 path be smooth?
  - `clifwd wallets import` (D9) requires in-process Vault + repo access — a different shape from the current "CLI as HTTP client" pattern. How does the team plan to introduce this without splitting the CLI's mental model?

- **Phase 5 (state + nonces, v0.4.0)**. Adds `BEGIN IMMEDIATE` nonce manager, full schema (callers, nonces, transactions, transaction_args, transaction_hashes, audit_log, wallet_chains), receipt watcher, replacement-on-stuck. Risks:
  - The current `eth_getTransactionCount(addr, "pending")` per-request pattern is a documented race. The Phase 5 BEGIN IMMEDIATE path needs to reconcile against on-chain truth on startup. What's the reconciliation algorithm? Where is it speced?
  - The receipt watcher is an asyncio background task. Does the current `app/dependencies.py` lifecycle pattern (per-request CMs) accommodate a long-running task, or will Phase 5 need to refactor lifecycle?

- **Phase 6 (backup + restore, v0.4.x)**. Litestream → Scaleway, Vault Raft snapshots, executed restore drill. Risks:
  - Litestream replicates SQLite; Vault Raft snapshots are independent. The two backup streams must be restorable in a way that matches state — e.g., a wallet ciphertext in SQLite must correspond to a Vault master-key version that exists in the restored Vault. Is consistency between the two streams documented?
  - Has the team identified the Scaleway bucket, region, and credential rotation schedule?

- **Phase 7 (policy + audit, v0.5.0)**. The "value gate". YAML policy engine, ABI decoder, hash-chained audit, structlog scrubber, default-deny synthetic-attack test, background `renew-self` task. Risks:
  - The hash-chained audit (`audit_log.row_hash` over `audit_log.prev_hash || ...`) is the tamper-evidence mechanism. What's the chain root? What if the table is empty? What happens on Phase 5's transactional rollback — does the audit row need its own transaction?
  - The ABI decoder must handle the FTSO `RewardManager` ABI and the `ParticipantRegister` ABI. If those contracts upgrade, does fwd auto-detect? Or does the operator update an ABI artifact manually?
  - The structlog scrubber regex `^(0x)?[0-9a-fA-F]{64}$` (per architecture.md hazard #3) catches privkeys but also catches transaction hashes (which are 32-byte hex). Does the scrubber distinguish them? Is "redact tx hashes from logs" the right behaviour, or does the team need a smarter scrubber?

- **Phase 8 (first production migration, v1.0.0)**. The capstone. Risks:
  - The on-chain `setClaimRecipient` rotation is operator-driven. If the operator submits the rotation tx but `fwd`'s Phase 8 wallet doesn't yet exist (or the wallet creation didn't persist), the rotation succeeds and reward claims go to a dead address. What's the dependency ordering?
  - Once `ftso-fee-claimer` calls `fwd` instead of holding its own `.env PRIVATE_KEY=`, what's the fallback if `fwd` is down at claim time? Reward epochs are time-bounded; missing one is real revenue loss. Is the SLO documented?

Note any *specific* risk that, in your experience reviewing custody systems, has burned a similar project. If you've seen a project ship Phase 4 then realise the policy_path indirection was wrong and have to rewrite, say so.

Severity guide:

- **Critical**: privkey leak path that fires under normal operation; total auth bypass; data corruption that voids the audit chain.
- **High**: a real exploit requires unusual conditions (e.g., compromised host) but the consequence is severe; or a doctrine claim is materially false.
- **Medium**: an issue the team should address in the next 1–2 phases; not exploitable today but will compound.

- **Observation**: noted, no action required, but useful context (e.g., a deferred-by-phase decision the auditor wants to confirm is intentional).

Severity is your judgement call. The operator weighs it. Don't inflate.
