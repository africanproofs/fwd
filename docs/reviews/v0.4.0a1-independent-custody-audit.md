## What `fwd` is (one paragraph context)

`fwd` is the Flare Wallet Daemon: a policy-gated signing service for African Proofs (AP)'s EVM backend keys. It exists to delete every `.env PRIVATE_KEY=` line in AP's automation (`ftso-fee-claimer`, `apregister/`, `apcli`, future `fics` write paths, future autonomous agents) and replace them with one HTTP call to a service that knows the signing policy, owns an append-only audit, and never lets plaintext keys touch disk. It is single-host, single-replica, single-operator, Docker-Compose deployed, with HashiCorp Vault Transit (`aes256-gcm96`, `exportable=false`) doing envelope encryption of externally-generated secp256k1 privkeys, and `eth-account` doing the actual signing in `fwd`'s own process post-decrypt. v1 ships through Phase 8 (`ftso-fee-claimer` migration); Phase 10 is post-v1 hardening.

Read `CLAUDE.md` § Identity and § Scope (the v0.4.0a1 paragraph) before you do anything else.

### Chapter 1 — Custody correctness (Phase 4 surface)

Phase 4 added two new privkey-handling code paths: `app/wallet_import.py` (operator-supplied privkey from a host file) and `infra/envelope_signer.py::import_wallet` (the matching backend method).

Investigate:

- The bytearray-buffer escape paths in `app/wallet_import.py:110–182`. The use case wraps `bytes.fromhex(content)` into a `bytearray` at line 144 and overwrites the immutable reference at line 145 (`privkey_bytes = b""`). Is the original `bytes` object actually unreachable after that? Python's GC may have already copied it.
- `EnvelopeSigner.import_wallet` at `src/fwd/infra/envelope_signer.py`. The flow is: length-check, `Account.from_key(bytes(privkey_buf))`, optional address-mismatch check, `vault.encrypt(bytes(privkey_buf))`, persist. Each `bytes(privkey_buf)` creates a new immutable copy; the bytearray gets zeroized in `finally`. Does `WalletAddressMismatch` raise after the first `bytes(privkey_buf)` call but before zeroize? (It should, because the `try` wraps the `Account.from_key` line; the `finally` always fires.)
- **ToCToU** in `app/wallet_import.py`: `path.stat()` at lines 123–130, `path.read_text()` at line 133. Between the stat and the read, can a malicious actor replace the file (symlink swap, hard link, or a process running as the same UID)? For a CLI tool run by the operator on their own host, this is operator-trust territory; but flag it explicitly so the operator knows the limitation.
- Hazard #1 (no plaintext caching) post-`import_wallet`: does the resulting `EnvelopeSigner` instance hold any 32-byte `bytes`/`bytearray` after the call returns? Per `tests/unit/test_envelope_signer.py::test_no_32byte_state_after_*`, this is enforced for `create_wallet` and `sign_transaction`. **Is there an equivalent test for `import_wallet`?** If not, that's a test-gap finding.
- Hazard #2 (`bytearray`, not `bytes`) for `import_wallet`: does the buffer get zeroized in `finally` even on `WalletAddressMismatch`? Verify by trace of the code path.
- The shred path (`_shred_file`) at `app/wallet_import.py:185–201`: if `shred` is missing, it falls back to `path.unlink()` — which does NOT overwrite. Is this fall-back safe enough? Should it warn explicitly?
- Spot-check (per scope): mlock active, scrubber present, threat-model A5 honest. If any fails, that's a Chapter 5 regression.

Severity guide: a real plaintext-leak path is **Critical**. A theoretical leak window matching documented hazard caveats is **Observation**. A test-gap that leaves a hazard unenforced is **Medium** (or **High** if the hazard's enforcement is the doctrine's "Enforced by:" reference).

### Chapter 2 — Auth surface — argon2id correctness and operational hygiene

The new `infra/api_key.py` is the trust root for the entire caller-auth boundary. If argon2id is misused, every caller-authed request is at risk.

Investigate:

- `infra/api_key.py:37` instantiates `PasswordHasher()` with argon2-cffi defaults. As of argon2-cffi current, those are: `time_cost=3`, `memory_cost=65536` (64 MB), `parallelism=4`, `hash_len=32`, `salt_len=16`. Do these meet **OWASP 2024 password-storage cheat sheet** recommendations for argon2id? (OWASP recommends m=46MiB, t=1, p=1 OR m=19MiB, t=2, p=1. argon2-cffi defaults are stricter than OWASP minimums. Confirm.)
- Token format `fwd_live_<43-char-base64url>`. 43 base64url chars × 6 bits/char = 258 bits, but `secrets.token_urlsafe(32)` produces ~256 bits of entropy (32 bytes of randomness). Sufficient.
- `infra/api_key.py:71–82` extracts the prefix. Is there a timing oracle here? An attacker with a guessed token could time the verify-vs-prefix-mismatch path. Verify that the path is constant-time *up to the argon2id verify*, which itself is constant-time per argon2-cffi.
- **Prefix-collision DoS**: an attacker who has the admin key can mint many callers with the same `api_key_prefix`. Each subsequent legit auth request walks all prefix-matching active rows and argon2-verifies each (~50–100 ms per verify). With N rows sharing a prefix, auth latency scales as O(N × 50ms). Does `infra/caller_repo.py::list_by_prefix_active` have any cap? Does the auth path bound the iteration count?
- **Revocation atomicity**: `app/caller_resolution.py::resolve_caller` calls `repo.list_by_prefix_active(prefix)` then iterates `verify_api_key`. What if `repo.revoke()` fires between the list and the verify? The just-revoked caller could authenticate within the resolution window. Is this acceptable for v1 (there's no "logout" semantics to violate)?
- **Caller-key leak surface**: the `clifwd callers create` command outputs the API key to stdout. The operator captures via shell variable (`KEY=$(clifwd callers create ...)` would not work directly because the key goes to stdout but metadata to stderr — verify the actual output structure). Does the key end up in shell history? `~/.bash_history`? CI logs? Document.
- **Admin key rotation**: now that callers depend on admin to be issued, how does the operator rotate `FWD_ADMIN_KEY` without invalidating downstream caller relationships? Spoiler: caller keys are independent of admin key (admin only ISSUES; verification uses the per-caller argon2 hash). Confirm by reading the auth paths. Document the implication in your finding.

### Chapter 3 — D11 bright line — adversarial attestation (DEDICATED CHAPTER)

The cardinal property of v0.4.0a1: admin auth and caller auth are distinct, never bridged. If this property fails, every Phase 5–8 ship inherits the failure. Treat this chapter as a CTF.

Attack vectors to attempt (document each — pass or fail — with evidence):

1. **AST-level audit**: confirm `src/fwd/api/caller_auth.py` imports nothing from `src/fwd/api/admin_auth.py` and vice versa. Use `python -c "import ast; ..."` or a simple `grep`. Already covered by `tests/unit/test_admin_caller_bright_line.py::test_caller_auth_does_not_import_admin_auth` and `::test_admin_auth_does_not_import_caller_auth`. Run both; they must pass.

2. **Module-introspection audit**: confirm `inspect.getmembers(fwd.api.caller_auth)` exposes no admin_auth-derived symbols. Already covered by `::test_caller_auth_does_not_import_admin_auth_transitively`. Run it.

3. **URL-routing attack**: can a path-traversal in the URL bypass the dependency? Attempt `curl -H "Authorization: Bearer $FWD_ADMIN_KEY" http://127.0.0.1:8080/v1/admin/../sign-and-send` and `http://127.0.0.1:8080/v1/sign-and-send/`. FastAPI normalizes paths; both should return 401 (admin token rejected by `require_caller`). Document the actual responses.

4. **Token-format collision**: if the operator chose `FWD_ADMIN_KEY=fwd_live_<arbitrary-43-chars>` (mimicking the caller token format), does `require_admin` accept it (yes — it's the env var) AND `require_caller` reject it (yes — there's no row in the callers table with that argon2 hash)? Set `FWD_ADMIN_KEY` to a value matching the caller-token shape, restart fwd, and verify both endpoints behave correctly.

5. **`request.state.caller` mutation**: can a downstream handler overwrite `request.state.caller` with a different `Caller` instance? FastAPI dependency state is per-request and the api/sign.py handler does NOT explicitly modify it. But verify by inspection: nothing in `app/sign_and_send.py`, `api/sign.py`, or any other handler mutates `request.state.caller` after `require_caller` sets it. Phase 7's audit log will read this for attribution; if it's mutable, the audit-log integrity is compromised.

6. **Dependency-override leak**: in `tests/unit/test_admin_caller_bright_line.py::_make_sign_app`, the test uses `app.dependency_overrides[get_caller_repo]` to mock the repo. Are these overrides per-app (correct) or global (back-door)? Check FastAPI's `dependency_overrides` semantics: it's `app.dependency_overrides`, so per-app, scoped to that test's `FastAPI()` instance. Confirm. If a production code path uses `dependency_overrides` for something other than testing, that's a finding.

7. **Live curl tests** (the canonical D11 attestation; Reviewer already verified these at v0.4.0a1 ship time, but you must re-verify post-rebuild):

   ```sh
   KEY=$(grep -E '^FWD_ADMIN_KEY=' .env | cut -d= -f2-)

   # Admin token on caller endpoint → 401
   curl -s -o /dev/null -w "%{http_code}\n" -X POST http://127.0.0.1:8080/v1/sign-and-send \
     -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
     -d '{"wallet":"x","chain":114,"to":"0x0000000000000000000000000000000000000000","value_wei":"0","data":"0x","gas":21000}'

   # Caller token on admin endpoint → 401
   #   (Mint a caller via /v1/admin/callers, then use its api_key against /v1/admin/callers itself)

   # Revoked caller token on caller endpoint → 401
   #   (Mint a caller, revoke it via DELETE /v1/admin/callers/{name}, then use the now-revoked api_key)

   # Malformed bearer → 401
   curl -s -o /dev/null -w "%{http_code}\n" -X POST http://127.0.0.1:8080/v1/sign-and-send \
     -H "Authorization: Bearer not-a-token" -H 'Content-Type: application/json' \
     -d '{"wallet":"x","chain":114,"to":"0x0","value_wei":"0","data":"0x","gas":21000}'
   ```

   All four MUST return 401. If any returns 200, 400, 500, or anything else, the bright line is broken — surface as **Critical**.

8. **request.state.caller absence on admin endpoints**: confirm that admin endpoint handlers do NOT see a `request.state.caller` value. They shouldn't try to read it; if they do, that's a sign of admin/caller conflation creeping in.

If any attack succeeds, severity is **Critical**. If all attacks fail, document each failure mode briefly so the operator has audit evidence that the bright line was probed adversarially.
