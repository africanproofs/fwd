## Executive summary

The D11 bright line holds at this checkpoint. I did not find a path where an admin token authenticates to a caller endpoint, or where a caller token authenticates to an admin endpoint. The code has separate auth modules, structural tests pass, live curl probes reject credential crossing, and the shaped-admin-token collision probe accepts the shaped token only at the admin boundary and rejects it at caller auth.

The highest-priority concern is not D11. It is that Phase 4 added a new private-key import path, but the v0.3.2 hazard tests were not extended to `EnvelopeSigner.import_wallet`; the new `import_wallet` branch is also exactly the coverage hole reported by pytest (`src/fwd/infra/envelope_signer.py:116-138`). That is cheap to fix now and should be fixed before Phase 5 builds more state around imported wallets.

The other material issues are quality and ops hygiene: `ruff check .` currently fails despite the Phase 4 history claiming it passed, `--shred-source` silently degrades to plain unlink when `shred` is missing, caller-key handling has no operator runbook yet, and all integration tests skipped in this audit run. None of these is a Critical custody break, but several should be closed in v0.4.0a2 or alongside Phase 5.

## Findings

### Chapter 1 — Custody correctness (Phase 4 surface)

**F1.1 — `EnvelopeSigner.import_wallet` is not covered by the hazard #1/#2 enforcement tests** (Severity: Medium)

- **Evidence**: `src/fwd/infra/envelope_signer.py:116-138`; `tests/unit/test_envelope_signer.py:136-223`; `tests/unit/test_envelope_signer.py:229-292`; coverage output marks `src/fwd/infra/envelope_signer.py:116-138` missing.
- **Description**: Phase 4 added a third private-key path: `EnvelopeSigner.import_wallet`. It length-checks, derives the address via `Account.from_key(bytes(privkey_buf))`, encrypts via `vault.encrypt(bytes(privkey_buf))`, persists, and zeroizes in `finally`. The v0.3.2 tests enforce zeroize/no-32-byte-state for `create_wallet` and `sign_transaction`, but no equivalent test exercises `import_wallet`, including the `WalletAddressMismatch` path.
- **Status when read**: Active test gap.
- **Recommendation**: Add import-specific zeroize and no-32-byte-state tests, including expected-address mismatch and repo/create failure paths.

**F1.2 — `--shred-source` silently degrades to `unlink()` when `shred` is absent** (Severity: Medium)

- **Evidence**: `src/fwd/app/wallet_import.py:185-193`; `src/fwd/cli/wallets.py:158-161`; `docs/architecture.md:377`.
- **Description**: Architecture says `--shred-source` should run `shred -u` and exit non-zero with a warning if shredding fails. The implementation raises and warns when `shred` returns non-zero, but if `shred` is not on `PATH`, `_shred_file()` plain-unlinks the file and returns success. For a plaintext private-key source file, silent non-overwrite is not the operator contract implied by `--shred-source`.
- **Status when read**: Active doctrine/code drift.
- **Recommendation**: Treat missing `shred` as `ShredSourceFailed`, or print an explicit warning that only unlink occurred.

**F1.3 — Import file validation has an operator-trust ToCToU window and unavoidable immutable copies** (Severity: Observation)

- **Evidence**: `src/fwd/app/wallet_import.py:119-145`; `src/fwd/infra/envelope_signer.py:122-127`; `docs/architecture.md:680`.
- **Description**: The import use case stats the file, then reads it later; a same-UID process can replace the file between `path.stat()` and `path.read_text()`. The code also necessarily creates immutable `bytes` copies at `bytes.fromhex(content)` and `bytes(privkey_buf)`. These are not new catastrophic paths under the documented Python caveat, but they should remain treated as operator-trust territory rather than hard custody guarantees.
- **Status when read**: Documented caveat / accepted v1 limitation.

### Chapter 2 — Auth surface — argon2id correctness and operational hygiene

**F2.1 — Prefix-collision auth work is unbounded, though practical exploitability is low through the public admin API** (Severity: Low)

- **Evidence**: `src/fwd/infra/caller_repo.py:120-142`; `src/fwd/app/caller_resolution.py:37-45`.
- **Description**: `resolve_caller()` loads every active row with the presented 8-character prefix and argon2-verifies each one. There is no cap. The normal admin API does not let an attacker choose prefixes, so producing a target collision through `clifwd callers create` is not practical at 48 bits of prefix. Direct database tampering or a future import/bulk-create path would make this an O(N) auth latency lever.
- **Status when read**: Active but low practical risk.
- **Recommendation**: Put a small cap or uniqueness policy on active prefix matches before any bulk caller-management tooling exists.

**F2.2 — Revocation has a narrow list-then-verify race** (Severity: Observation)

- **Evidence**: `src/fwd/app/caller_resolution.py:37-45`; `src/fwd/infra/caller_repo.py:165-173`.
- **Description**: A request can load active candidates, then a concurrent admin revoke can set `revoked_at`, then the original request can still complete argon2 verification against its in-memory `Caller`. That is a sub-request race, not durable session semantics; v1 has no logout guarantee to violate.
- **Status when read**: Active race, acceptable for v1 if documented.

Argon2id itself is sound at this checkpoint: the installed defaults are Argon2id `t=3, m=65536 KiB, p=4, hash_len=32, salt_len=16`, and generated caller tokens have 32 random bytes of entropy.

### Chapter 7 — Operational posture — Phase 4 specific

**F7.1 — Caller-key issuance and rotation are code paths, not an operator runbook** (Severity: Medium)

- **Evidence**: `src/fwd/cli/callers.py:50-57`; `docs/decisions.md:188`; `docs/architecture.md:84-86`; `rg` found no runbook for caller-key rotation or shell-history hygiene.
- **Description**: `clifwd callers create` correctly sends metadata to stderr and the API key to stdout, so `KEY=$(clifwd callers create ...)` captures only the key. That also means the key will commonly live in shell variables, terminal scrollback, service env files, CI logs, or deployment scripts. The architecture says caller keys are rotatable by revoke + reissue, but there is no operator procedure for issuance, storage, rotation, or leak response.
- **Status when read**: Active ops gap, acceptable only pre-production.
- **Recommendation**: Add a Phase 8 runbook section for `FWD_API_KEY` handling: create, inject, verify, rotate, revoke old key, clear shell history/CI logs.

**F7.2 — `clifwd wallets list` is a stub and there is no documented wallet inventory path** (Severity: Low)

- **Evidence**: `src/fwd/cli/wallets.py:71-85`; `docs/history/0.4.0a1-caller-auth.md:81-83`.
- **Description**: The CLI tells the operator that `GET /v1/admin/wallets` is not implemented. That is acceptable at v0.4.0a1, but if an operator needs inventory today, the practical path is direct SQLite inspection. I did not find a documented safe command for doing that.
- **Status when read**: Deferred to Phase 5+ per history doc.

**F7.3 — Admin-key rotation remains restart-based and undocumented, but caller keys are independent of it** (Severity: Observation)

- **Evidence**: `src/fwd/api/admin_auth.py:21-35`; `src/fwd/app/caller_resolution.py:37-45`; `src/fwd/infra/caller_repo.py:47-55`.
- **Description**: Rotating `FWD_ADMIN_KEY` does not invalidate callers because caller verification uses the argon2 hashes in SQLite, not the admin key. The admin key still comes from cached settings, so changing it means changing `.env` and restarting `fwd`. That should be documented before Phase 8, but it is not a Phase 4 D11 defect.
- **Status when read**: Deferred ops runbook issue.

### Chapter 8 — Phase 5-8 risks

**F8.1 — Phase 5 transaction attribution must explicitly pass the resolved caller into the use case** (Severity: Medium)

- **Evidence**: `src/fwd/api/caller_auth.py:56-58`; `src/fwd/api/sign.py:77-107`; `src/fwd/app/sign_and_send.py:41-49`; `docs/architecture.md:236-252`.
- **Description**: Phase 4 authenticates and stashes `request.state.caller`, but the `post_sign_and_send` handler does not read the returned caller or pass a caller name into `SignAndSendRequest`. Phase 5's `transactions.caller` column is already specified as `NOT NULL`. If Phase 5 appends transaction rows without threading this value explicitly, the receipt watcher and Phase 7 audit log will inherit weak attribution.
- **Status when read**: Deferred to Phase 5, but must be handled there.
- **Recommendation**: Make caller identity an explicit input to the Phase 5 sign-and-send use case, not an implicit side-channel only available on `request.state`.

**F8.2 — Phase 7 must fail loud on unknown caller or wallet `policy_path` values** (Severity: Medium)

- **Evidence**: `docs/decisions.md:396-418`; `src/fwd/api/callers.py:34-37`; `src/fwd/api/wallets.py:28-31`.
- **Description**: Phase 4 correctly stores `policy_path` as free-form text for both callers and wallets. D13 says Phase 7 will validate consistency at policy load time and default-deny until fixed. That load-time failure must be explicit; otherwise a typo silently turns into outage or inconsistent authorization.
- **Status when read**: Deferred to Phase 7.

**F8.3 — Phase 8 caller cutover lacks the required operational choreography** (Severity: Medium)

- **Evidence**: `docs/dependencies.md:101`; `docs/decisions.md:188`; `docs/reviews/v0.4.0a1-independent-custody-audit.md:294`.
- **Description**: The first real caller migration needs a precise sequence: issue caller key, inject `FWD_URL` + `FWD_API_KEY`, cut over `ftso-fee-claimer`, verify one epoch, remove any admin-key or private-key fallback, and revoke obsolete credentials. I did not find that runbook in the repo.
- **Status when read**: Deferred to Phase 8.
