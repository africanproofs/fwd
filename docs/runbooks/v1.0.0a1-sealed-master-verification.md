# Sealed-master verification — manual operator gate (v1.0.0a1)

> Phase 8a Core invariant #14 gate. Prove the **sealed local master**
> custody path end-to-end against live Coston2: a real transaction
> signed via `POST /v1/sign-and-send` mines on-chain, and the on-chain
> `from` (recovered by Coston2 via secp256k1) equals the address `fwd`
> generated and AES-256-GCM-sealed under the mode-0600 host-file master.
> That recovery is impossible unless `SealedMaster.decrypt()` recovered
> the exact privkey from its `seal:v1:` ciphertext — so a single mined
> tx with a matching `from` proves the whole new custody chain.
>
> This is the v1.0.0a1 analog of the v0.3.1 Vault-path proof
> (`sign-and-send-verification.md`). Per Core invariant #14: real-RPC
> verification is the validation; mocks lie; the 426-test suite proves
> the contract against fakes, this runbook proves it against live
> Coston2 + the real sealed-master custody path + the real D16 chain.
>
> Mandatory before the v1.0.0a1 verification-met addendum is recorded
> in `docs/history/1.0.0a1-vault-to-sealed-master.md` (Reviewer-only
> follow-up, exactly as v0.3.1 / v0.4.1 / v0.4.6 / v0.5.3 recorded their
> proofs). It does NOT block the v1.0.0a1 code commit (already shipped,
> `5984eb1`).

## What changed vs the Vault-era runbook (read first)

- **No Vault.** There is no `fwd-vault` container, no `vault status`,
  no unseal, no `FWD_VAULT_ROLE_ID`/`FWD_VAULT_SECRET_ID`. `docker
  compose ps` shows only `fwd` and `fwd-litestream`.
- **The master key file replaces the unseal ritual.** `fwd` reads a
  32-byte AES-256-GCM master from `/run/fwd/master.key` (mode 0600,
  owned by the container's `fwd` uid 1000). It is `policy.yaml`-class
  private config (Core #12; gitignored at `config/master.key`).
- The Phase-7 policy gate is still in force — `/v1/sign-and-send`
  requires a loaded `policy.yaml` and a caller/wallet binding. The
  phase-7 binding amendments still apply (Phase-correct image; policy
  mounted; Step 0.6 revoke stale callers; `clifwd` invocation; no
  `sqlite3` in the slim image).

## Prerequisites

- A tree at ≥ v1.0.0a1 (`grep __version__ src/fwd/version.py` → `1.0.0a1`).
- `.env` has `FWD_ADMIN_KEY` set; `RPC_URL_COSTON2` reachable (default
  `https://coston2-api.flare.network/ext/C/rpc`).
- `docker compose config` exits 0 (the `vault`/`vault-snapshot`
  services are gone; the fwd service mounts
  `./config/master.key:/run/fwd/master.key:ro`).

## Steps

### 0. Generate + place the sealed master key.

```sh
# Build the v1.0.0a1 image and generate the master ON THE HOST:
docker compose build fwd
docker compose run --rm --no-deps --entrypoint clifwd fwd master generate --out /run/fwd/master.key  # writes inside the container fs only — NOT what we want
```

Do it host-side so the bind-mount source exists, then make it readable
by the container's `fwd` uid 1000:

```sh
# Generate the 32-byte master on the host (clifwd is in the image; run a throwaway):
docker compose run --rm --no-deps --entrypoint sh fwd -c \
  'python -c "import os,sys; f=os.open(\"/tmp/m\",os.O_WRONLY|os.O_CREAT|os.O_EXCL,0o600); os.write(f,os.urandom(32)); os.close(f)"; cat /tmp/m' \
  > ./config/master.key
chmod 600 ./config/master.key
# The container fwd user is uid 1000. The bind mount preserves host
# numeric ownership; SealedMaster checks st_uid == geteuid() (1000 in
# the container). Ensure the host file is uid 1000:
sudo chown 1000:1000 ./config/master.key   # skip if your host account is already uid 1000
ls -ln ./config/master.key                  # expect: -rw------- 1 1000 1000 32 ...
```

> Pass criterion 0: `./config/master.key` is exactly 32 bytes, mode
> `600`, numeric owner `1000`. (`SealedMaster.__init__` and `/healthz`
> enforce the same four checks; a mismatch is the #1 live-drill gotcha.)

### 0.5. Bring up the stack.

```sh
docker compose up -d --build fwd litestream
docker compose ps                 # fwd, fwd-litestream up; NO vault
curl -s http://127.0.0.1:8080/healthz | python3 -m json.tool
```

> Pass criterion 0.5: `/healthz` returns `{"master":"ok","rpc":...,
> "fwd":"ok"}`. **`master` MUST be `"ok"`** — `"unavailable"` means the
> key file failed one of the four checks (revisit Step 0). Note the
> field is `master`, not the retired `vault`.

### 0.6. Revoke stale callers (Phase-7 amendment, still binding).

D14 startup fail-fast checks every active DB caller against the loaded
policy. Revoke any active caller the gate policy below does not declare:

```sh
KEY=$(grep -E '^FWD_ADMIN_KEY=' .env | cut -d= -f2-)
curl -s -H "Authorization: Bearer $KEY" http://127.0.0.1:8080/v1/admin/callers | python3 -m json.tool
# For each with revoked_at == null that the gate policy does not name:
curl -s -X DELETE -H "Authorization: Bearer $KEY" http://127.0.0.1:8080/v1/admin/callers/<name>
```

### 1. Create the test wallet (sealed under the master).

```sh
curl -sf -X POST http://127.0.0.1:8080/v1/admin/wallets \
  -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"name":"sealed-verify","policy_path":"sealed-verify"}' | python3 -m json.tool
```

Capture `address` (call it `$ADDR`). Its privkey is now stored as a
`seal:v1:` ciphertext — confirm the format (no plaintext, no `vault:`):

```sh
docker exec fwd clifwd wallets list   # shows name/address/policy_path only (no secret — D16)
```

### 2. Write + mount the minimal gate policy, restart fwd.

`./config/policy.yaml` (gitignored, Core #12) — one caller, one wallet,
one permitted self-send. Substitute `$ADDR`:

```yaml
version: 1
callers:
  sealed-verify-caller:
    policy_path: sealed-verify
wallets:
  sealed-verify:
    policy_path: sealed-verify
permissions:
  sealed-verify:
    contracts:
      "ADDR_LOWER_HERE":            # $ADDR lowercased — the self-send target
        abi: erc20
        methods:
          "transfer(address,uint256)":   # the gate tx is a self-addressed transfer(amount=0); see the note below
            max_value_wei: "0"
            arg_predicates: {}
    wallet_allowlist: ["sealed-verify"]
    rate: { per_hour: 10, per_day: 50 }
wallet_constraints:
  sealed-verify:
    max_aggregate_value_wei_per_day: "1000000000000000000"
    rate: { per_hour: 10, per_day: 50 }
```

> Note (corrected v1.0.0a3 — the v1.0.0a2 live drill surfaced this):
> Core invariant #3 ("sign intent, never opaque bytes") means an
> empty-`data` value send is **denied at policy step 3** — no 4-byte
> selector ⇒ undecodeable ⇒ default-deny (`policy_denied step=3:
> calldata too short`). There is **no policy-passable bare value
> transfer** through `/v1/sign-and-send` by design. The gate tx is
> therefore a self-addressed ERC20 `transfer(address,uint256)` with
> `amount=0` — the proven shape from `phase-7-verification.md`. `$ADDR`
> is an EOA, accepted under the same operator-gated premise as phase-7:
> this gate verifies fwd's decode→policy→**sealed-master decrypt**→
> sign→broadcast→custody path, **not** token semantics (method-policy
> depth is already proven by `phase-7-verification.md`). The custody
> property under test — the point of THIS gate — is unchanged.

```sh
docker compose restart fwd
curl -s http://127.0.0.1:8080/healthz   # master:ok, fwd:ok after reload
```

### 3. Issue the caller token.

```sh
curl -sf -X POST http://127.0.0.1:8080/v1/admin/callers \
  -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"name":"sealed-verify-caller","policy_path":"sealed-verify"}' | python3 -m json.tool
```

Capture the `fwd_live_…` token as `$CALLER`.

### 4. Fund `$ADDR` from the Coston2 faucet.

Visit https://faucet.flare.network/coston2, submit `$ADDR`, wait ~10 s.
Confirm balance > 0 via `eth_getBalance` against `$RPC_URL_COSTON2`.

### 5. Sign + send a value-0 self-addressed `transfer` through the sealed master.

Build the calldata with the **same `eth-abi` codec fwd decodes with**
(an `amount=0` self-`transfer`; see the Step 2 note for why empty `data`
is denied by design):

```sh
CALLDATA=$(docker exec fwd python -c \
  "from eth_abi import encode; print('0xa9059cbb'+encode(['address','uint256'],['$ADDR',0]).hex())")
curl -sf -X POST http://127.0.0.1:8080/v1/sign-and-send \
  -H "Authorization: Bearer $CALLER" -H 'Content-Type: application/json' \
  -d "{\"wallet\":\"sealed-verify\",\"chain\":114,\"to\":\"$ADDR\",\"value\":\"0\",\"data\":\"$CALLDATA\"}" \
  | python3 -m json.tool
```

Capture `tx_id` and `hash`.

### 6. Poll until mined; verify on-chain `from` == `$ADDR`.

```sh
curl -s -X POST $RPC_URL_COSTON2 -H 'Content-Type: application/json' \
  -d "{\"jsonrpc\":\"2.0\",\"id\":1,\"method\":\"eth_getTransactionReceipt\",\"params\":[\"<hash>\"]}" \
  | python3 -m json.tool
```

Then fetch the tx and read its `from`:

```sh
curl -s -X POST $RPC_URL_COSTON2 -H 'Content-Type: application/json' \
  -d "{\"jsonrpc\":\"2.0\",\"id\":1,\"method\":\"eth_getTransactionByHash\",\"params\":[\"<hash>\"]}" \
  | python3 -c "import sys,json; t=json.load(sys.stdin)['result']; print('from=',t['from'])"
```

### 7. Chain integrity.

```sh
docker exec fwd clifwd audit verify     # expect: "chain intact: N rows", exit 0
```

## Pass / fail

| # | Check | Pass |
|---|---|---|
| 0 | `config/master.key` = 32 bytes, mode 600, owner uid 1000 | ☐ |
| 0.5 | `/healthz` → `master:"ok"` (field is `master`, not `vault`) | ☐ |
| 1 | Wallet created; privkey stored as `seal:v1:` (no `vault:`, no plaintext) | ☐ |
| 5 | `/v1/sign-and-send` → 200 with `tx_id` + `hash` | ☐ |
| 6 | Receipt `status=0x1`; **on-chain `from` (case-insensitive) == `$ADDR`** | ☐ |
| 7 | `clifwd audit verify` → chain intact, exit 0 | ☐ |

**Check 6 is the gate.** A matching `from` proves Coston2 recovered the
signing key via secp256k1, which is only possible if `SealedMaster`
correctly AES-256-GCM-decrypted the wallet's `seal:v1:` ciphertext
under the 0600 host-file master and `eth-account` signed with the exact
recovered privkey. The sealed-master custody chain is proven end-to-end
with no Vault anywhere in the path.
