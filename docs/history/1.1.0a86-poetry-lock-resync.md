# v1.1.0a86 — re-sync `poetry.lock` to the a84 custody pins (unbreak build-from-source)

**Type:** build fix — `poetry.lock` regeneration. No code/behaviour change.
**Date:** 2026-06-06.

## Why (the a84 regression, caught at install time)

v1.1.0a84 changed the custody package pins in `pyproject.toml` from carets (`^X`) to explicit ranges (`>=A,<B`) — semantically identical, same resolved versions — but **did not regenerate `poetry.lock`**. Poetry's `content-hash` is computed over the literal dependency strings, so any edit to them invalidates the lock even when the solution is unchanged. The fwd Dockerfile runs `poetry install --only main --no-root`, which **refuses** against a stale lock:

```
pyproject.toml changed significantly since poetry.lock was last generated.
Run `poetry lock [--no-update]` to fix the lock file.
```

The a84 verification ran `pytest` in an already-installed environment, which never executes `poetry install` from the lock — only the **build-from-source installer** does. So 783 green tests passed while `curl … | sudo bash` failed at the fwd build step. This is the Core invariant #14 boundary exactly: mocks/local envs lie; the validating boundary is the real build.

## What changed

- `poetry lock --no-update` regenerated `poetry.lock`. The **only** diff is the `[metadata] content-hash` line — no transitive version moved (the explicit ranges resolve identically to the prior carets).
- `poetry check --lock` → "All set!".

## Verification (real-infra, per the operator's "test everything")

- `poetry check --lock` passes.
- `git diff poetry.lock` = one line (content-hash), zero package changes.
- **`docker compose build fwd` succeeds** — the previously-failing `poetry install --only main --no-root` (build step 6/8) now completes and the image exports. This reproduces and closes the operator's install failure on the exact step.
- Full unit suite: 783 passed, 1 skipped (version-consistency green at a86).
- `clif`'s lock independently confirmed consistent (`poetry check --lock` "All set!") — only fwd was affected.

## Files

`poetry.lock`, version files.

## Lesson (defect class, Core invariant #19)

A `pyproject.toml` dependency-string edit — *even a semantically-identical reformat* — requires regenerating `poetry.lock` in the same ship, because Poetry hashes the literal strings. The class fix beyond this instance: any ship touching `[tool.poetry.dependencies]` must run `poetry lock --no-update` + `poetry check --lock`, and pin/dep changes are verified by a `docker compose build`, never by `pytest` alone (the unit suite runs post-install and is structurally blind to lock drift). Partners with Core #14.
