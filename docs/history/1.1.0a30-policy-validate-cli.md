# v1.1.0a30 — `clifwd policy validate` (pre-deploy policy gate)

**Type:** feature ship (operator tooling). First ship of the provider-distribution Phase 0.
**Date:** 2026-05-31.
**Authoring:** Reviewer (Opus) implemented directly under operator direction; operator-gated.

## Why

Policy is loaded only at startup, so a bad `policy.yaml` edit is caught only when
the daemon restarts — and a29 made the schema stricter (required `chains`,
`allow_unconstrained_args`, mandatory wallet bindings), so hand-editing is more
error-prone. There was no way to validate a policy *before* `docker compose up -d`
recreates the container. During the a29 cutover the Reviewer had to hand-roll a
`docker compose run` dry-run to confirm the edited policy was consistent. This
ship makes that a first-class command — the safety gate every operator (AP and,
per the approved provider-distribution plan, future third-party providers) needs.

## What changed

- **`clifwd policy validate [--policy PATH] [--schema-only]`** — runs the SAME
  checks the daemon runs at startup, without starting the daemon:
  - schema (`load_policy`) always — catches a29-schema errors (missing `chains`,
    bad types, unknown keys);
  - consistency (`check_consistency`) against the live DB + ABI registry unless
    `--schema-only` — callers/wallets/abis/methods/chains/wallet-bindings, i.e.
    the exact `main.py::_startup_policy_load` check (`include_revoked=False`).
  - Exit 0 = valid; 2 = schema error OR consistency error(s), each printed.
- New `src/fwd/cli/policy.py` (the command) + `src/fwd/app/policy_check.py` (the
  app-layer use case it calls). The CLI does NOT import infra directly — it goes
  through the app layer (`cli -> {app, domain}` boundary), mirroring
  `app/wallet_import.py`'s re-export pattern (`PolicyLoadError` re-exported).
- Wired `policy` into `src/fwd/cli/main.py`.

Read-only: never mutates `policy.yaml` (private config) or any state. **Reuses**
the existing `load_policy` + `check_consistency` in `infra/policy_loader.py` —
no new validation logic, just a CLI surface over the startup check.

## Verification
- `pytest`: **488 passed, 1 skipped** (+4 new). `ruff` clean; `mypy` clean (58 files).
  `test_layer_boundaries` passes (the cli->app indirection is why `policy_check.py`
  exists).
- Real-infra (Core #14): a throwaway image built from this tree, then
  `docker compose run --rm fwd clifwd policy validate` against the **live**
  `config/policy.yaml` + production DB → `schema OK — callers=9 permissions=6 …`
  then `VALID (schema + consistency)` (matches the a29 dry-run: 9 callers / 21
  wallets / 0 errors). The running container was NOT recreated (that is the
  operator-gated redeploy); this ship is verification + commit only.

## Not in this ship
`clifwd policy init` (the a29-schema template generator) is the next ship — it
needs a small networks data file (fwd is deliberately chain-agnostic and ships no
RewardManager/FSM/chain table), so it is split out to keep this ship surgical.
