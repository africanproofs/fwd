# v0.2.1 — pre-Phase-2 documentation fixes

> Doc-only ship landed 2026-05-01. Two gaps surfaced by the post-v0.2.0 CTO review, closed before Phase 2's project scaffold begins.

## Fixes

### Fix 1 — Failure modes in the signing flow

Under the v0.1.2 envelope-encryption design, `transit/decrypt/fwd-master` is a new failure point in the critical signing path. The original v0.1.0 design didn't have this dependency at signing time (Vault was supposed to *be* the signer); v0.1.2 introduces it (Vault is now in the critical path of every signature). The architecture document needed explicit guidance on what happens when decryption fails — particularly around nonce-release semantics, since a stuck nonce is the most severe consequence of a Vault hiccup.

`docs/architecture.md` § Signing flow gains a new sub-section `### Failure modes in the signing flow` documenting all six failure points in the critical path. The load-bearing rule: **if the failure occurs before broadcast (steps 1–12), the reserved nonce is RELEASED in the same SQLite transaction; if at or after broadcast (steps 13+), the nonce stays committed and the receipt watcher reconciles.** The Vault-decrypt failure case specifically is now 503 `vault_unavailable` with nonce release.

Implementation lands in Phase 3 (signing core) and Phase 5 (receipt watcher).

### Fix 2 — Implementation hazards (v0.1.2 envelope encryption)

Three implementation patterns specific to envelope encryption were documented only implicitly in Core invariant #16. The post-v0.2.0 review surfaced that they need explicit visibility before Phase 2's scaffold and Phase 3's signing-core implementation, so the patterns are correct from the start rather than surfaced post-hoc as bugs.

`docs/architecture.md` gains a new top-level section `## Implementation hazards (v0.1.2 envelope encryption)` documenting:

1. **No plaintext caching between requests.** Core invariant #16 forbids it. Phase 3 must implement decrypt → sign → zeroize on every signing call. Enforcement: unit test asserts `EnvelopeSigner` has no instance-level `bytes`/`bytearray` of length 32 between requests.
2. **`bytearray`, not `bytes`, for privkey buffers.** Python's `bytes` is immutable; you cannot zeroize it. The v0.2.0 spike's `zeroize()` helper is the canonical pattern. Enforcement: unit test asserts buffer is `bytearray` AND post-zeroize content is all zeros.
3. **Structlog scrubber redacts hex-shaped 32-byte values.** A logged privkey is a permanent leak. Enforcement: a custom structlog processor filters strings matching `^(0x)?[0-9a-fA-F]{64}$`; plus a fuzzer-style test that intentionally raises an exception inside the signing critical section and asserts no privkey hex appears in captured logs.

The v0.2.0 spike (`docs/history/0.2.0-spike-coston2.md`) already implements (1) and (2) correctly via its `zeroize()` helper. Phase 3 must copy this discipline. Item (3) is new in Phase 3 (the spike was throwaway and didn't configure structlog).

## What this ship deliberately does NOT include

- Code. No `pyproject.toml`, no `src/fwd/`, no Docker artifacts. Phase 2 ships those.
- The actual unit tests enforcing the three patterns. Phase 2 ships the test scaffold; Phase 3 ships the tests themselves.
- The actual structlog scrubber implementation. Phase 3 ships it.
- Updates to `threat-model.md`. The new failure-modes table is implementation guidance for the signing flow; the threat model already documents the underlying attacks (A3/A4) and is unchanged.
