# v1.1.0a66 — onboard loads the policy via `up -d --force-recreate` (a plain restart was an unreliable reload)

**Type:** onboarding reliability fix (`install/onboard`). No custody/signing semantics change. Operator-surfaced live: a clean install + onboard failed in FEE CLAIMING with `wallets create claimer-songbird … http 400 unknown_policy_path: 'wc/claimer-songbird' is not in the loaded policy`.
**Date:** 2026-06-03.

## Why (operator hit it live; root-caused on the host)

The generated policy file on disk was correct (host + container checksums matched, both had `wc/claimer-songbird`), and `policy_init` + onboard agreed on the path. But the **daemon's in-memory** policy was the inert startup one. The tell: the container's `StartedAt` (13:58:16) was *earlier* than the policy file's mtime (13:58:49) — onboard's Step 3 `docker compose restart fwd` had printed "loaded (fwd restarted, healthy)" but the container's `StartedAt` never advanced, i.e. the restart returned 0 **without actually restarting the container**. So the daemon kept serving its startup (inert) policy, and `wallets create` validated `wc/claimer-songbird` against it and 400'd. Running the identical command manually *did* restart it and the daemon then validated `wallet_constraints=3` — confirming a plain `docker compose restart` is not a dependable reload here (matches the banked operations lesson: force-recreate is the trusted reload, not a plain restart).

## What changed

Step 3 now reloads with `docker compose … up -d --force-recreate fwd` instead of `restart fwd`. force-recreate brings up a **new** container that re-reads the bind-mounted `config/policy.yaml`, so the load is guaranteed (the sealed master + the `fwd-state` volume persist across the recreate — no custody impact). Combined with a65 (always run Step 3, never skip on byte-identical), onboard now **reliably** loads the on-disk policy on every run and self-heals from any partial prior state — no manual `rm policy.yaml` or restart. Health-wait + `clifwd health` gate it as before; the subsequent `wallets create` is the end-to-end confirmation that the load took.

## Verification (Reviewer)

`sh -n` + `dash -n` clean. The exact `up -d --force-recreate fwd` command was run live on the host and DID advance `StartedAt` and load the policy (`clifwd policy validate` → `wallet_constraints=3`, VALID) where the plain `restart` had not. Live end-to-end validation is the operator's re-run of onboard past FEE CLAIMING (Core invariant #14). Class note (Core invariant #19): the defect class is "treating `docker compose restart` as a guaranteed config reload"; the fix asserts the reload by recreating the container that reads the artifact, and pairs with a65 (assert the loaded state every run, don't infer from file bytes).
