What happened instead: the live drill surfaced a critical concurrency
defect that all 215 unit tests had missed. Every `/v1/sign-and-send`
returned `(sqlite3.OperationalError) database is locked\n[SQL: BEGIN IMMEDIATE]`
— even with N=1, no concurrency.

v0.4.5 ships both the fix and the live verification evidence in one
combined ship.

## The bug

Two root causes acted together.

### Cause 1 — sqlite3's implicit BEGIN clashed with our explicit BEGIN IMMEDIATE

sqlite3's DB-API driver wraps every statement in an implicit `BEGIN (DEFERRED)`
by default. SQLAlchemy's `begin` event listener (registered in
`infra/db.py` at v0.4.0a5) then fired AFTER that implicit BEGIN had already
started a transaction. The listener called `conn.exec_driver_sql("BEGIN IMMEDIATE")`,
which failed with:

```
sqlite3.OperationalError: cannot start a transaction within a transaction
```

To other connections trying to acquire the writer lock, this surfaced as:

```
sqlite3.OperationalError: database is locked
[SQL: BEGIN IMMEDIATE]
```

### Cause 2 — multi-CM-per-request opened concurrent sessions in a single request

`app/dependencies.py` defined `SignerCM`, `TransactionRepoCM`, and `NonceRepoCM`,
each of which opened its own `session_scope()`. The pre-v0.4.5 `api/sign.py`
used all three concurrently:

```python
async with (
    signer_cm as signer,
    rpc_cm as rpc_mgr,
    tx_repo_cm as tx_repo,
    nonce_repo_cm as nonce_repo,
):
    ...
```

Three concurrent sessions per request. Each session's first execute fires
the `begin` event handler → tries to grab the SQLite writer lock via
BEGIN IMMEDIATE. With three concurrent writer-lock attempts in a single
request, in-request self-contention manifested as "database is locked".

The receipt watcher's `_tick()` had the same pattern.

### Why the unit tests missed it

`tests/unit/test_nonce_repo.py::test_concurrent_reservations_are_monotonic_no_gaps`
(shipped at v0.4.0a5) used `asyncio.gather` of 10 `reserve_next` calls,
each opening its OWN session. Two reasons it passed:

1. Each task uses one session — no per-task self-contention.
2. asyncio.gather schedules tasks serially enough that each BEGIN/COMMIT
   completes before the next task even tries.

The test built its own engine inline rather than going through
`fwd.infra.db.get_engine`, so it also didn't exercise the production
event-handler stack. Two layers of indirection from the real bug.

## The fix

### `src/fwd/infra/db.py`

```python
def _apply_sqlite_pragmas(dbapi_connection, _connection_record):
    # Disable sqlite3's implicit transaction wrap so SQLAlchemy's `begin`
    # event handler can issue an explicit BEGIN IMMEDIATE without colliding
    # with an already-open DEFERRED transaction.
    dbapi_connection.isolation_level = None

    cur = dbapi_connection.cursor()
    cur.execute("PRAGMA journal_mode=WAL")
    cur.execute("PRAGMA synchronous=NORMAL")
    # 30s absorbs concurrent-writer queueing during sign-and-send bursts.
    # Each request holds the writer lock for ~1s; 10 concurrent × 1s = 10s.
    cur.execute("PRAGMA busy_timeout=30000")
    cur.execute("PRAGMA foreign_keys=ON")
    cur.close()
```

Standard SQLAlchemy + SQLite pattern per the official docs:
https://docs.sqlalchemy.org/en/20/dialects/sqlite.html#serializable-isolation-savepoints-transactional-ddl

### `src/fwd/app/dependencies.py`

New `RequestScope` dataclass + `RequestScopeCM` context manager that share
ONE session across signer + tx_repo + nonce_repo. The old per-repo CMs
remain (used by `GET /v1/admin/wallets`), but signing-flow callers use
the consolidated scope.

### `src/fwd/api/sign.py` and `src/fwd/app/receipt_watcher.py`

Both refactored to use `RequestScopeCM`:

```python
async with scope_cm as scope:
    rpc = scope.rpc_mgr.for_chain(body.chain)
    result = await sign_and_send(
        request, scope.signer, rpc, scope.tx_repo, scope.nonce_repo
    )
```

### `tests/unit/test_db.py` (NEW)

Two regression tests exercising the production engine path:

- `test_session_scope_executes_write_without_implicit_begin_conflict` —
  single writer; pre-fix raises "cannot start a transaction within a
  transaction" on the first INSERT.
- `test_concurrent_session_scope_writes_through_real_infra` — 5 concurrent
  writers through `db_mod.session_scope`; pre-fix raises "database is
  locked" because the first writer's implicit-BEGIN-then-BEGIN-IMMEDIATE
  chain leaves the connection in a "in transaction" state.

These tests use `db_mod.get_engine()` directly with a tmp DATABASE_URL —
no inline engine, no bypassing the production event-handler stack. They
fail pre-fix and pass post-fix.

### `docs/architecture.md` § Signing flow step 6

Doctrine updated with the SQLAlchemy + SQLite isolation-level interaction,
the 30s busy_timeout rationale, and the single-session-per-request
requirement. Per Core invariant #18 (doctrine and code do not drift),
the new code constraints are documented inline.

## What v0.4.5 deliberately does NOT do

- **Refactor sign-and-send to split the writer-lock critical section.** The current shape holds the lock for ~1s (Vault decrypt + RPC + INSERT). A future ship could split into: reserve-then-commit (~ms) + work-outside-lock (~1s) + insert-then-commit (~ms), dropping writer-lock holding time from ~1s to ~ms and allowing much higher concurrency. Out of scope for v0.4.5; Phase 7 or a Phase 5 follow-up may pick it up.
- **Live low-gas replacement on Coston2 (Phase 5 Scenario 2).** Still deferred per the runbook — needs `_DEFAULT_TIP_WEI` env-configurable to exercise.
- **Phase 6 GA drill.** Operator-driven, against a fresh host with the `backup` volume pre-populated. Records its own verification-met addendum afterward.
- **Old per-repo CMs (`SignerCM`, `TransactionRepoCM`, `NonceRepoCM`).** Retained for other endpoints (`GET /v1/admin/wallets` etc). May be deprecated in a future cleanup; not in scope here.
