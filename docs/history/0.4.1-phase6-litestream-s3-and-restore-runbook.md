# v0.4.1 — Phase 6 ship 1: Litestream S3 replica + restore runbook skeleton

**Shipped**: 2026-05-13
**Authors**: Claude Sonnet 4.6 (implementer) + Claude Opus 4.7 (reviewer).
**Canonical prompt**: `~/.claude/plans/fwd-canonical-prompt-v0.4.1-phase6-litestream.md`

## Why this ship

Phase 5 closed v0.4.0 with substrate complete and a runbook waiting for live execution.
Phase 6 starts here: turn the Litestream placeholder shipped in v0.3.0-alpha into a real
S3 replica against Scaleway Object Storage, and publish the restore procedure.

The implementation-plan.md Phase 6 spec calls for four deliverables and one verification
gate (a clean-host drill with `litestream restore` → Vault restore → unseal → reconcile →
sign-and-send). This ship lands deliverables 1, 2, and 3 (Litestream S3, env-var contract,
`runbooks/restore.md`) and explicitly defers deliverable 4 (Vault Raft snapshot cron) to
the next Phase 6 sub-ship, with the restore runbook's Step 4 marking the deferral and the
operational consequence in-line.

The drill itself (verification gate) runs at Phase 6 GA against a freshly-provisioned
Docker host, when both halves (SQLite restore + Vault restore) are in place. This ship
is the foundation for that drill.

## What ships

- **`config/litestream/litestream.yml`** — replaced the v0.3.0-alpha file-replica
  placeholder with a real S3 replica. Uses `${VAR}` and `${VAR:-default}` env-var
  interpolation for the 5 required + 2 optional Scaleway variables. Snapshot
  interval 24h, sync interval 10s (~10s RPO), default retention 72h.
- **`.env.example`** — activated the `LITESTREAM_S3_*` block. Documents the
  Scaleway bucket provisioning ritual (region `fr-par`, visibility `PRIVATE`,
  IAM user with bucket-scoped write access). Includes the standard warning that
  these credentials are not in the public repo and must be populated locally.
- **`docs/runbooks/restore.md`** (NEW, 469 lines) — 8-step procedure with
  per-step pass criteria and a consolidated pass/fail table. Step 4 (Vault
  restore) is an explicit TODO block documenting both the planned next-ship
  procedure and the workaround for this drill (fresh `vault-init.md` run with
  OLD D6 shares), including the critical consequence: re-initializing Vault
  produces a new `fwd-master` Transit key, which makes OLD wallet ciphertexts
  in SQLite unreadable. That consequence is the entire reason Vault state
  backup is first-order, not an afterthought.

No code changes. No test changes. Cumulative test count stays at 213 + 3 skipped.

## What this ship does NOT cover

Per Core invariant #18, each deferral is explicit:

- **Vault Raft snapshot save + S3 upload (cron)** → next Phase 6 ship (planned
  v0.4.2 or later, depending on whether the Phase 5 verification-met addendum
  ships first).
- **Vault Raft snapshot restore in `restore.md` Step 4** → same ship as above;
  Step 4 is amended in-place when the Vault half lands.
- **`clifwd reconcile` CLI command** → Phase 7 or Phase 6 follow-up. Current
  drill leans on lifespan startup `nonce_reconcile` (shipped at v0.4.0a5), with
  log-grep as the pass criterion in Step 7.
- **F6.2 CI integration runner** → Phase 6; `docker compose up` + integration
  pytest in CI not yet wired.
- **Phase 6 GA drill execution + measured RTO** → Phase 6 GA, against a clean
  Docker host with the full Vault half in place.
