# v0.4.3 — Phase 6 ship 3: reversion of cloud-backup substrate to local-volume only

**Shipped**: 2026-05-13
**Author**: Opus 4.7 (Reviewer). No Sonnet involvement; mechanical surgery.
**Predecessor**: v0.4.2 (`1be6ffb` — Phase 6 ship 2 cloud-backup + vault-snapshot S3 upload)

## Why this ship

The operator challenged the cloud-backup substrate landed in v0.4.1 + v0.4.2:

> *"What is aws s3 doing in this project. I had specifically outlawed anything that cannot be run locally?"*

Clarification a few turns later:

> *"Give me choices that rely on no outside dependencies."*

Investigation confirmed the doctrinal basis:

- **Core invariant #10**: *"Host-agnostic deployment. `docker-compose.yml` + `.env.example` runs identically on any host with Docker + Docker Compose. No bake of Scaleway / ap-ftso-02 / IP-specific assumptions into the repo. Host-specific config flows through `.env`, period."*
- **D2** (decisions.md): *"The compose file makes no assumptions about the host (Scaleway, ap-ftso-02, a fresh VPS, khosi's laptop). Host-specific configuration flows through `.env`."*

The v0.4.1 + v0.4.2 ships satisfied the *letter* (every Scaleway endpoint was env-injected, not hardcoded) but violated the *spirit*: the stack did nothing useful without a Scaleway account on top. Per Core invariant #18 — when doctrine and code drift, fix the next ship.

After exploring four options (file replica, MinIO sidecar, hybrid file+S3 toggle, manual `clifwd backup export`), the operator chose Option A — local file replica only. Then ultrathink sharpened the shape further: don't gate the S3 path behind a flag (zombie code is exactly what Core invariant #18 forbids); strip it entirely. If a future deployment wants cloud backup, it adds it then — as an operator-side `restic`/`rclone` against the `backup` volume, NOT inside fwd.

## What ships

### 1. `aws-cli` removed entirely

- `config/vault-snapshot/Dockerfile` no longer installs `aws-cli`. Image now contains only `ca-certificates` + the vault binary copied from the multi-stage's vault-stage. Image shrinks ~170 MB.
- The verbatim verification: `docker run --rm --entrypoint sh fwd-vault-snapshot:latest -c 'vault version; command -v aws; echo aws_exit=$?'` → `Vault v1.18.2 (...) / aws_exit=127`.

### 2. `scripts/vault-snapshot.sh` rewritten for local-file mode

Each iteration:
1. `mkdir -p /backup/vault-snapshots` (idempotent)
2. AppRole login via `fwd-snapshot` role
3. `vault operator raft snapshot save /tmp/vault-<ts>.snap`
4. `cp /tmp/vault-<ts>.snap /backup/vault-snapshots/vault-<ts>.snap` (cross-fs safe; `cp` then `rm` rather than `mv` because the source is tmpfs)
5. Rotate: `ls` + `sort` + `head -n -KEEP` + `rm`
6. `vault token revoke -self`

Same `set -u` (not `set -e`) design — per-iteration failures log and the loop continues. Same `VAULT_SNAPSHOT_INTERVAL_SEC` (default 86400) + `VAULT_SNAPSHOT_RETENTION_COUNT` (default 7) tunables. No `AWS_*` env mappings, no `--endpoint-url`, no S3 anywhere.

### 3. Litestream switched to `type: file`

`config/litestream/litestream.yml` now replicates `/data/state.db` to `/backup/state.db`. Same `sync-interval: 10s` (~10s RPO), same `snapshot-interval: 24h`, same `retention: 72h`. No env-var interpolation block — there are no credentials to interpolate.

### 4. `docker-compose.yml` rewired

- `fwd-egress` network **DELETED**. Nothing now needs public egress.
- New `backup` Docker named volume.
- `litestream` service: mounts `backup:/backup`. `networks:` dropped entirely — Litestream needs no network at all (volume I/O only).
- `vault-snapshot` service: mounts `backup:/backup`. `networks:` reduced to `fwd-internal` (for the Vault API at `http://vault:8200`).

### 5. `.env.example` stripped

- `LITESTREAM_S3_*` block DELETED.
- `VAULT_SNAPSHOT_S3_PATH` DELETED.
- `FWD_VAULT_SNAPSHOT_ROLE_ID` + `_SECRET_ID` kept (mode-agnostic; vault-snapshot still needs AppRole login).
- `VAULT_SNAPSHOT_INTERVAL_SEC` + `_RETENTION_COUNT` kept (mode-agnostic tunables).
- New header explains backups go to the `backup` Docker volume and that off-host transport is the operator's responsibility.

### 6. `docs/runbooks/restore.md` rewritten in place

- Front-matter callout: v0.4.2 cloud framing → v0.4.3 local-volume framing. Explicit statement: *"This runbook assumes the operator has copied the `backup` volume contents to the new host using their preferred tool. fwd does not transport backups off-host."*
- Prerequisites: Scaleway bucket prerequisite REPLACED with "`backup` volume contents copied to the new host." Required env vars trimmed to FWD-only (no `LITESTREAM_S3_*`, no `AWS_*`).
- Step 1: `aws s3 ls` / `litestream snapshots` against a remote bucket REPLACED with `docker run --rm -v fwd_backup:/b alpine` listing both `/b/state.db.litestream/` and `/b/vault-snapshots/`.
- Step 2: `docker compose down --volumes` REPLACED with selective `docker volume rm fwd_vault-data fwd_fwd-state` — the `backup` volume is the restore source and MUST NOT be destroyed.
- Step 3: `docker exec fwd-litestream litestream restore … s3://…` REPLACED with a throwaway `litestream` container reading from `fwd_backup:/backup:ro` and writing into `fwd_fwd-state:/state/state.db` (`chown 1000:1000` to match fwd's non-root user).
- Step 4(a): `aws s3 ls` + `aws s3 cp` REPLACED with `docker run --rm -v fwd_backup:/b alpine cat` + `docker cp` into the vault container. Steps 4(b)–(f) — the throwaway-init → unseal-with-dummies → snapshot-restore → unseal-with-ORIGINAL-D6 dance — preserved verbatim.
- Pass/fail summary table row 1 rewritten.
- RTO timings rewritten: off-host transport excluded from the budget; "post-transport" RTO target tightened to 10–20 min.
- "What does not cover" / "When wrong" sections rewritten.

## What this ship does NOT cover

- **Off-host transport automation.** Explicitly operator-driven and out of scope for fwd, per the v0.4.3 framing.
- **Cloud-S3 backup re-introduction.** Reverted. If a future deployment wants it, the path is an operator-side `restic`/`rclone` against the `backup` volume — NOT modifying fwd.
- **F6.2 CI integration runner.** Re-numbered to v0.4.4. The canonical prompt at `~/.claude/plans/fwd-canonical-prompt-v0.4.3-f6.2-ci-integration.md` will be renamed and committed as part of v0.4.4. The 2-line pre-existing bug in `tests/integration/test_caller_auth_e2e.py` (missing `caller` arg + missing `tx_repo`/`nonce_repo` args, surfaced by Sonnet during its parallel F6.2 implementation) gets folded into v0.4.4 since that's the ship that makes the test newly relevant.
- **Phase 6 GA drill.** Operator-driven, against a fresh host with the `backup` volume pre-populated (simulating off-host transport). Records the verification-met addendum afterward.

## Why this is the right shape (the ultrathink synthesis)

1. **The operator's directive is doctrinally sharper as "no outside deps" than as "no AWS branding."** Swapping `aws-cli` for `mc` (MinIO client) doesn't help — `mc` against Scaleway is still an outside dep. The only honest "no outside deps" answer is to drop the cloud destination entirely.
2. **Separation of concerns is cleaner.** fwd's surface area shrinks; the operator's existing backup tooling expands to cover the off-host transport. Each tool does what it's best at.
3. **Reversal honesty.** v0.4.1 + v0.4.2 paragraphs stay in CLAUDE.md as honest history. v0.4.3's paragraph says "we reversed direction because Core invariant #10's spirit was being violated; here's the new shape." No revisionism. Per Core invariant #18, doctrine never silently retcons.
4. **Future flexibility preserved.** If the operator later wants cloud backup, the path is clear: introduce a separate sidecar (or operator-side `restic`/`rclone` against the `backup` volume) without modifying fwd itself. fwd stays the custody daemon; backup transport is plug-in.
5. **Minimum diff that's actually correct.** ~150 lines deleted, ~70 added across 8 files. No new dependencies introduced. Image shrinks ~170 MB.
