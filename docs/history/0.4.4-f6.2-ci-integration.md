## Why this ship

The v0.4.0a1 independent custody audit surfaced **F6.2 (Medium) — CI
integration runner**. The repo's 3 integration tests under
`tests/integration/` skipped in CI because the pipeline had no Vault. Per
Core invariant #14 (real-RPC verification is the validation), keeping the
integration tests permanently-skipping in CI defeats the value of the
test suite. F6.2 was deferred from Phase 4 to Phase 6 per the audit
deferral table; this ship closes it.

Per the operating rule under Core invariant #18, audit deferrals carry
explicit phase markers, and the audit ledger is updated when each one
closes. v0.4.4 ships:
- The CI plumbing to run integration tests against a real Vault.
- A bundled 4-line Reviewer correction to one of those tests, which had
  silently rotted across the Phase 4 + Phase 5 substrate adds (the test
  was written before v0.4.0a3 added the explicit `caller` field on
  `SignAndSendRequest` and before v0.4.0a3 / v0.4.0a5 added the
  `tx_repo` / `nonce_repo` args on the `sign_and_send()` call).

## What ships

### 1. `scripts/ci_vault_init.py` (NEW)

Pure-`httpx` Python utility — httpx is already a runtime dep so no new
package is added. Initializes a dev-mode Vault for CI use:

1. Wait-for-vault: polls `/v1/sys/health` until ready (60s timeout).
2. Enable Transit (idempotent: 400 "path is already in use" is success).
3. Create `transit/keys/fwd-master` with `type=aes256-gcm96`, `exportable=false`.
4. Write the `fwd-app` policy from `config/vault/policies/fwd-app.hcl` — single source of truth shared with the production `vault-init.sh`.
5. Enable AppRole (idempotent).
6. Create the `fwd` role: `token_policies=fwd-app`, `token_ttl=24h`, `token_max_ttl=72h`, `secret_id_ttl=0`, `secret_id_num_uses=0`. Same shape as `vault-init.sh`.
7. Read `role_id` (stable per role).
8. Generate `secret_id` (fresh each invocation).
9. Emit `FWD_VAULT_ROLE_ID=…` + `FWD_VAULT_SECRET_ID=…` + `VAULT_ADDR=…` on stdout as KEY=VALUE lines suitable for `set -a; . file; set +a` shell sourcing.

Resolves the policy HCL file via `pathlib.Path(__file__).parent.parent /
"config/vault/policies/fwd-app.hcl"` so CWD doesn't matter.

### 2. `.gitlab-ci.yml` `integration:` stage (NEW)

Inserted between `test:` and `build:` in the stage order:

```yaml
stages:
  - lint
  - typecheck
  - test
  - integration
  - build
```

The new job:

```yaml
integration:
  stage: integration
  needs:
    - job: test
      artifacts: false
  services:
    - name: hashicorp/vault:1.18.2
      alias: vault
      command:
        - "server"
        - "-dev"
        - "-dev-root-token-id=ci-root-token"
        - "-dev-listen-address=0.0.0.0:8200"
  variables:
    VAULT_ADDR: http://vault:8200
    VAULT_TOKEN: ci-root-token
  script:
    - poetry run python scripts/ci_vault_init.py > vault.env
    - set -a; . ./vault.env; set +a
    - poetry run pytest -v tests/integration/
```

GitLab spins the Vault container as a service alongside the job, with
the `vault` hostname resolving inside the job's network. Dev mode means
auto-unsealed + known root token + in-memory storage (lost on restart).
`needs: [test]` makes the integration job wait for unit tests to pass
before consuming a Vault service slot.

`VAULT_TOKEN` is a throwaway dev-mode root token, not a secret. The
`fwd` role's `secret_id` produced by `ci_vault_init.py` is the actual
credential pytest consumes; that's fresh per job and ephemeral.

### 3. `docs/runbooks/ci-integration.md` (NEW)

Operator-facing runbook documenting:
- What the `integration:` job does (start vault → init → run pytest).
- Pass criterion: 3 PASSED (not 3 skipped — a skip means the env wasn't exported).
- How to reproduce locally — `docker run hashicorp/vault:1.18.2 server -dev …` + same `ci_vault_init.py` + same pytest invocation.
- When the runbook is wrong (tests grow a dep on Litestream/vault-snapshot → re-scope; Vault major-version bump changes dev-mode CLI signature → update; `ci_vault_init.py` drifts from `vault-init.sh` → reconcile).

### 4. Bundled Reviewer correction — `tests/integration/test_caller_auth_e2e.py`

Sonnet's parallel pre-v0.4.3 implementation surfaced a BLOCKER: the test
was rotting across two Phase substrate adds:

- v0.4.0a3 (F8.1) added the explicit `caller: str` field to
  `SignAndSendRequest`. The test still constructed `SignAndSendRequest`
  without `caller=`.
- v0.4.0a3 + v0.4.0a5 added `tx_repo: TransactionRepo` and
  `nonce_repo: NonceRepo` as required positional args on
  `sign_and_send()`. The test still called `sign_and_send(request,
  signer, rpc)` with only 3 args.

Either gap produced `TypeError: missing required argument…` the moment
the integration job actually executed the test. Sonnet was prohibited
from modifying tests/ per the canonical-prompt operating rules. The
Reviewer applied the 4-edit correction at v0.4.4 commit time:

1. Added imports for `TransactionRepo`, `NonceRepo`, and their
   `metadata` symbols.
2. Added `nonce_metadata.create_all` + `transaction_metadata.create_all`
   to the test's tmp-SQLite schema setup.
3. Instantiated `tx_repo = TransactionRepo(session)` + `nonce_repo =
   NonceRepo(session)` alongside the existing wallet/caller repos.
4. Added `caller=resolved.name` to the `SignAndSendRequest`
   constructor; added `tx_repo, nonce_repo` to the `sign_and_send()`
   call (positional args 4 and 5).

Why fold into v0.4.4: the test was already broken in `main`; F6.2 is the
ship that makes it newly relevant (executable in CI). Splitting the fix
into its own patch would have been pure ceremony.
