# v1.1.0a46 — wizard: demarcate by function, emit wallet addresses, contract-accurate key language

**Type:** tooling/docs ship (`install/onboard` + docs; no daemon `src/` change).
**Date:** 2026-06-01. Reviewer (Opus); operator-gated. Verified under a pty harness.

## Why

The wizard (a44; default songbird a45) narrated by OPERATION, so its two functions
— **fee claiming** and **FSP reward signing** — were interleaved across the
wallet/token/nonce/gate steps and hard to tell apart; it printed wallet NAMES but
never ADDRESSES (so you couldn't confirm a pasted key derived the expected address,
and the on-chain step, which acts on an address, was unactionable); and it described
keys loosely. Three operator asks:
1. clearly demarcate the functions being onboarded;
2. emit the actual address of each (imported/generated) wallet;
3. describe the keys in the contract's own language, descriptively.

All presentation in `install/onboard` — no behavior change, no `src/` change.

## What changed

- **Function-grouped flow.** A header lists the enabled functions; a shared
  Foundation (health → build policy → load) runs once; then one banner'd section
  per function — `═══ Function 1/N — FEE CLAIMING ═══` and `═══ … — FSP REWARD
  SIGNING ═══` — each provisioning its own wallet(s), clif token(s), and nonce, with
  the key paste happening **in that function's context**. `--claim-only` /
  `--sign-only` show just one section; the design scales to a future validator
  function.
- **Wallet addresses emitted.** New `wallet_addr <name>` helper (`clifwd wallets
  list` lookup — the authoritative stored address). Every wallet line now shows
  `… @ 0x<addr>` (generate, paste-import, already-exists), the imported-key line
  adds "confirm this is the address you expect", and the on-chain step names the
  addresses it authorizes/registers.
- **Contract-accurate, descriptive key language** (from the shipped ABIs): the
  claim executor that calls `RewardManager.claim(_rewardOwner, _recipient, …)`; your
  **signing policy address** — the `_signature` signer `FlareSystemsManager.signUptimeVote`
  / `signRewards` recovers; the **`msg.sender`** that submits the FSM tx (gas; FSM
  checks the `_signature`, not the sender); the allowed claim `_recipient`. These
  appear in the function headers, section subtitles, paste prompts, per-wallet
  lines, and the on-chain step ("authorize … as a claim executor"; "register … as
  your signing policy address (voter)").

## Verification (Core #14 — isolated, prod untouched)

Isolated `fwd-test` from the `fwd:dev` image, wizard driven under a `pty.fork()`
harness:
- **generate mode** → header lists 2 functions; `FEE CLAIMING` section shows
  `claimer-songbird @ 0x… — the claim executor — RewardManager.claim caller …`;
  `FSP REWARD SIGNING` shows `fsp-sender @ 0x… — the msg.sender …` and the pasted
  `fsp-signing-songbird @ 0x… — your signing policy address …`; the on-chain step
  names both addresses with their roles.
- **import-existing mode** → 3 keys pasted in their sections (all hidden — none
  leaked), each echoing its address + role; CUTOVER step names addresses.
- **`--claim-only`** → one function (`Function 1/1 — FEE CLAIMING`), no FSP section;
  `clifwd policy validate` → VALID.
- Production `fwd` untouched.
