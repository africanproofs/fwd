# v1.1.0a75 — onboard preserves each network's own identity/recipient (multi-network fix)

**Type:** `install/onboard` correctness fix (2 lines in `env_write`). No custody/signing/policy/nonce change.
**Date:** 2026-06-04.

## Why

Adding a **second network with a different identity** (AP's Flare identity `0x26534a…` vs Songbird's `0xcf3A3e…`) exposed a latent bug. The onboard takes a single `--identity`/`--recipient` and `env_write` wrote `IDENTITY_ADDRESS=$IDENTITY` / `CLAIM_RECIPIENT_ADDRESS=$RECIP` **unconditionally** into every network's `.env.<net>`. So re-running `--networks songbird,flare --identity 0x26534a…` to add Flare would silently overwrite Songbird's `.env.songbird` `IDENTITY_ADDRESS` with the Flare identity, breaking Songbird claiming (it would claim for the wrong reward owner). The policy side is already safe — `generate_policy` (`app/policy_init.py`) builds rules per-network for every `--networks` entry, and the claim recipient is pinned identically (`0x7c3579…`) for both AP networks — so only the env writer was wrong.

## What changed (`install/onboard`, `env_write`)

`IDENTITY_ADDRESS` and `CLAIM_RECIPIENT_ADDRESS` now use `getval "$_ew_dst" <KEY> "$<flag>"` — **preserve the value already in `.env.<net>`, fall back to the `--identity`/`--recipient` flag only for a network that has no env yet.** This matches the existing pattern for `WRAP_REWARDS`, `FSP_AUTO_ENABLED`, and the RPC overrides. So re-running to add a network keeps each existing network's own identity and only sets the new one. It also fixes the general latent bug (a re-run with any changed `--identity` no longer clobbers an existing network's env; edit `.env.<net>` by hand to deliberately change it).

## Verification

`sh -n` + `dash -n` pass. `git diff` is the two `env_write` lines only — no control-flow/policy/wallet/nonce change. Traced: fresh network (no `.env.<net>`) → uses the flag (unchanged behaviour); existing network → preserves its stored identity/recipient.
