# v0.2.2 — wallet create + CLI-only import

> Doc-only ship landed 2026-05-01. Articulates the wallet-provisioning policy and corrects two stale Phase 3 references that were missed during the v0.1.2 envelope-encryption pivot.

## What this ship lands

### New decision: D9 (wallet provisioning)

`docs/decisions.md` gains D9 documenting three asymmetric paths:

- **Create — HTTP + CLI.** `POST /v1/admin/wallets` and `fwd-cli wallets create` generate a fresh secp256k1 privkey inside `fwd`, encrypt via `transit/encrypt/fwd-master`, persist ciphertext, zeroize. Plaintext never leaves `fwd`'s process.
- **Import — CLI only** (`fwd-cli wallets import --privkey-file <path>`). No HTTP endpoint by design — a privkey in HTTP traffic enters TLS termination logs, web access logs, and reverse-proxy memory (permanent leak surface). CLI-only forces a single, operator-controlled, file-based path with mode `0600` and ownership checks.
- **Export — not supported in v1.** Real-world export use cases are handled by Litestream restore (disaster recovery), on-chain rotation (HW-wallet migration), and audit-log walks (forensics). Re-introducing plaintext export requires explicit operator authorization tied to a real consumer, AND would probably argue for moving custody to YubiHSM 2 first.

The refusal table for `fwd-cli wallets import` enforces six conditions before accepting a privkey-file: existence, mode `0600`, owner UID match, exactly 32 hex bytes after decode, unique wallet name, and optional `--expected-address` match.

### New section: `architecture.md` § Wallet provisioning

Both flows fully documented with payload examples, refusal tables, and audit semantics. The import audit row records source-file metadata (`name`, `source_file_path`, `source_file_mode`, `source_file_owner`) — the privkey itself is NEVER recorded in the audit log.

### Phase 3 stale references corrected

Two lines in `implementation-plan.md` Phase 3 still described the pre-v0.1.2 architecture (per-wallet `transit/keys/<wallet>` and `transit/sign/+` Vault policy). Both were missed during the v0.1.2 ship's drift sweep. Corrected here:

- Vault policy: now `update` on `transit/encrypt/fwd-master` + `transit/decrypt/fwd-master`, `read` on `transit/keys/fwd-master`. No `transit/sign/*` capability anywhere.
- Wallet provisioning: now `fwd-cli wallets create register-coston2-test ...`, generating the privkey externally and storing the Vault-encrypted ciphertext in SQLite.

### Phase 4 deliverables extended

Phase 4 (caller authentication and admin CLI) was already going to ship `fwd-cli callers create|list|revoke`. Extended to also include `fwd-cli wallets create|import|list` and the matching `POST /v1/admin/wallets` HTTP endpoint. The admin CLI now manages two resource types (callers + wallets) with consistent ergonomics.

## What this ship deliberately does NOT include

- Code. No new Python, no Docker artifacts, no schema migrations. Phase 2 ships the scaffold; Phase 4 ships the actual `fwd-cli wallets` commands.
- Geth v3 keystore JSON support for import. Hex-only in v1; revisit if a real consumer requires it.
- Plaintext export. Deferred to Phase 10+ subject to a real consumer surfacing.
- HTTP import endpoint. Deferred to Phase 10+ if a bulk-migration automation use case surfaces and an explicit operator decision is recorded.
- Updates to `threat-model.md`. Import doesn't add a new attack class — it uses the same `transit/encrypt` round-trip as create, governed by the same A3/A4 envelope. The pre-import file handling is an operator concern, not a `fwd` threat surface.

## Provenance

Operator-driven design conversation post-v0.2.1: "lets support create and import now. we can revisit export later." Three design decisions confirmed: (1) HTTP+CLI for create; (2) CLI-only for import; (3) `--shred-source` off by default. The Reviewer flagged the stale Phase 3 references during pre-handoff verification and bundled the fix into v0.2.2 since both lines are wallet-provisioning-adjacent.
