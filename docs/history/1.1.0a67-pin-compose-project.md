# v1.1.0a67 — pin the compose project to the container name (the real root cause behind a65/a66)

**Type:** installer + wrapper fix (`install/install.sh`, `install/fwd`, `install/clifwd`, `install/clif`). No daemon/custody/signing semantics change. Operator-surfaced live + root-caused on the host.
**Date:** 2026-06-03.

## Why — the actual root cause (corrects a66's misdiagnosis)

A clean install + `fwd onboard` failed at Step 3 with `Conflict. The container name "/fwd" is already in use`, and the volume it tried to create was named **`fwdtest_fwd-state`** — not `src_fwd-state`. That exposed the real bug: the operator's shell had a **stale, session-only `COMPOSE_PROJECT_NAME=fwdtest`** (a leftover export from an old drill; confirmed *not* in any rc file). The installer runs under `sudo`, which **resets the environment** → it used the dir-derived project `src`. But the host wrappers (`fwd`, `clifwd`, `clif` → `onboard`) run **without** sudo and **inherited** `fwdtest`. So the install created `fwd` in project `src`, while onboard operated project `fwdtest` — a different project. The consequence chain:
- a65-era `docker compose restart fwd` (project `fwdtest`) matched **no** container → returned 0 having restarted nothing → the daemon kept its inert startup policy → `wallets create` 400'd `unknown_policy_path`.
- a66's `up -d --force-recreate fwd` (project `fwdtest`) tried to **create** a new `/fwd` → hard name-conflict with the real `fwd` (a global container name owned by project `src`).

**a66 was a misdiagnosis.** `restart` was never unreliable — verified on the host: in the *correct* project BOTH `restart` and `force-recreate` work and reload the policy (`wallet_constraints=3`). The fault was always the project mismatch, not the reload command.

## What changed

Pin the compose project to the container name everywhere, so the installer and every wrapper operate the **same** project regardless of any stale `COMPOSE_PROJECT_NAME` in the shell:

```sh
export COMPOSE_PROJECT_NAME="${FWD_CONTAINER:-fwd}"
```

added to `install/install.sh` (before the build/up — so the install's containers + volumes land in project `fwd`, or the custom `FWD_CONTAINER`), and to `install/fwd`, `install/clifwd`, `install/clif` (so `fwd start|stop|status|restart|logs`, `clifwd onboard`, the `onboard` wizard's compose calls, and the one-shot `clif` all target that same project). The `${FWD_CONTAINER:-fwd}` literal is baked to the install-time container name by the existing a59 wrapper-baking `sed`, so project always equals container — and a multi-instance host (custom `FWD_CONTAINER`) stays isolated. a66's force-recreate is retained (it works and is robust against inode-change reloads); the project pin is what actually closes the failure class.

## Verification (Reviewer)

`sh -n` + `dash -n` clean on all five install scripts; the pin is present in the installer + all three wrappers. Root cause was reproduced + isolated live: `restart`/`force-recreate` no-op'd/conflicted under the inherited `fwdtest` project but both succeeded under the correct project. Live end-to-end validation is the operator's next fresh install, which clones a67 → the wrappers override any stale `COMPOSE_PROJECT_NAME` → install and onboard share one project with no `unset` needed (Core invariant #14). Class note (Core invariant #19): "a sudo install (env-reset) and a no-sudo wrapper (env-inherited) can silently disagree on the compose project"; pin the project to a stable, install-time-baked identity rather than letting it derive from cwd/with an inheritable env var.
