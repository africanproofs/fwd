# v1.1.0a48 — wizard: retry on a bad key paste (instead of skipping) + host-side hex validation

**Type:** tooling ship (`install/onboard`; no daemon `src/` change).
**Date:** 2026-06-01. Reviewer (Opus); operator-gated. pty-verified.

## Why

In the wizard's key-import step, a bad paste (wrong format / length) printed a
warning and **moved on**, leaving the wallet unimported (the operator then saw the
token minted and "import deferred"). Operator: "why not a retry?" — exactly right.
The trigger was a paste that decoded to 91 bytes (not a raw 32-byte hex key); the
in-container importer rejected it, and the wizard gave up.

## What changed

`import_pasted` now **loops (up to 5 attempts)** instead of skipping on a bad key:
- **Host-side validation before staging** — the pasted value is stripped
  (whitespace + `0x`) and checked on the host: non-hex characters → "paste the RAW
  hex key (a keystore/base64/mnemonic must be converted first)"; not exactly 64 hex
  chars → "expected 64 hex chars (a 32-byte key); got N". Either way it **re-prompts**
  immediately (no doomed container round-trip).
- A failed in-container import (`clifwd wallets import` non-zero) also re-prompts
  ("import failed: …. Try again, or Enter to skip.").
- **Enter (blank) still skips** deliberately (deferred import); success or
  already-exists returns; after 5 failed attempts it gives up with the manual
  `clifwd wallets import …` command.

Custody unchanged: the normalized key lives only in a transient shell var (cleared
each iteration), is piped into the daemon container, and `--shred-source` wipes the
temp — never on host disk, never on the network.

## Verification

pty harness, `--import-existing`: pasting `zz` → "non-hex characters" + re-prompt;
`deadbeef` → "expected 64 hex chars; got 8" + re-prompt; a valid 64-hex →
`imported + sealed: claimer-songbird @ 0x…`. `dash -n` clean (the operator's shell
is dash).
