# v1.1.0a29 — policy fail-closed hardening

**Type:** feature ship (policy-engine hardening). Refines the D14 evaluation order via D22.
**Date:** 2026-05-28.
**Authoring:** Reviewer (Opus) implemented directly under the operator directive "implement recommended fixes"; operator-gated.

## Why

The whole-project external review that drove a28 left four fail-closed gaps explicitly deferred ("separate hardening ships"). A fresh project review re-verified all four against the code; the operator directed "implement recommended fixes". This ship closes them.

## What changed (the four fixes — D22)

1. **Chain-ID is policy-bound (step 2).** `ContractRule` gains a REQUIRED, non-empty `chains: list[int]`. The engine denies at step 2 unless `request.chain ∈ crule.chains`.
   - **Gap it closes:** a contract *address* is not chain-unique. Flare/Songbird/Coston2 system contracts (FlareSystemsManager, RewardManager) frequently share an address, so address-only matching let a Coston2-scoped caller obtain a **mainnet** signature for the same contract+method. The sharpest of the four given Phase 9 FSP targets mainnet.
   - **Fail mode:** no default → a contract rule omitting `chains` fails schema validation (startup fail-fast, D14), never signs on an unbound chain.

2. **Non-scalar args fail closed (step 4b).** `MethodRule` gains `allow_unconstrained_args: bool = False`; `domain/intent.py` gains `has_nonscalar_args()`. A method whose ABI carries a non-scalar (array/tuple) top-level arg is denied unless its rule opts in.
   - **Gap it closes:** non-scalar args are decoded but projected out of `DecodedIntent.args` (B1), so `arg_predicates` cannot constrain them — yet the tx signed anyway. `RewardManager.claim` (proofs `tuple[]`) and FSM `signUptimeVote`/`signRewards` (signature tuple) all carry such args.

3. **Wallet constraint is mandatory (step 9 + loader check 4b).** A wallet signable via the EVM path must have a `policy.wallets` binding. The engine denies at step 9 (releasing the step-8 caller increment first) when `policy.wallets.get(wallet.name)` is `None`; `check_consistency` check 4b flags the same at load time.
   - **Gap it closes:** a DB-or-allowlisted wallet with no binding had no aggregate-value cap (`check_and_increment_wallet(constraint=None)` returned `True`).

4. **Idempotency body-check (409).** Replay now compares the incoming canonical body to the stored `transactions.request_json`; a same-key/different-body reuse returns **409 `idempotency_conflict`** (a denied forensic row committed before raise, Core #19) instead of returning the wrong cached signed tx. No migration — `request_json` already persists the full body.

Plus the drift fix the review found: `docker-compose.yml`'s policy-volume comment said the ABI registry ships via `COPY config/` — corrected to `COPY config/abis/` (Core #18).

## Operator follow-ups (NOT in this ship — the live, gitignored `config/policy.yaml`)

This is a **breaking** schema/semantics change for any existing policy. Before the next gated redeploy, in the real `policy.yaml`:

1. Add `chains: [...]` to **every** contract rule — else the policy fails to load (startup fail-fast). 14 = Flare, 19 = Songbird, 114 = Coston2.
2. Add `allow_unconstrained_args: true` to every method rule whose ABI has array/tuple args — notably the FSP self-submit `signUptimeVote`/`signRewards` rules and any `RewardManager.claim` rule — else those sign requests deny at step 4b.
3. Ensure every EVM-allowlisted wallet has a `policy.wallets` binding (→ a `wallet_constraints` block) — else load-time error / step-9 deny.

The running container keeps its current behaviour until the operator rebuilds + recreates it (a gated redeploy); the policy edits above must land in the same redeploy.
