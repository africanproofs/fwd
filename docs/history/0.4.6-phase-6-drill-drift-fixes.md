## Bugs surfaced + fixed

### Bug 1 — Litestream replica volume mounted read-only (substrate)

`docker-compose.yml` mounted `fwd-state:/data:ro` for the litestream
service. Litestream 0.3.13 requires read-write access to the source DB
to create its `_litestream_seq` tracking table; with `:ro`, every sync
iteration logged:

```
sync error: create _litestream_seq table: attempt to write a readonly database
```

…and the `/backup` volume stayed empty indefinitely.

**Fix:** changed to `fwd-state:/data` (no `:ro`). Comment block in
`docker-compose.yml` documents the requirement with a doctrine link to
the Litestream config reference.

### Bug 2 — vault-snapshot sidecar cannot write to `/backup` (substrate)

The vault-snapshot Dockerfile dropped to `USER nobody` for defense-in-depth
per Core invariant #1. But the `/backup` Docker named volume is created
root-owned mode 755 at first mount, and `nobody` cannot mkdir into it:

```
mkdir: can't create directory '/backup/vault-snapshots': Permission denied
```

**Fix:** new `scripts/vault-snapshot-entrypoint.sh` wrapper runs as root,
creates `/backup/vault-snapshots/` and chowns it to `nobody:nobody`, then
drops privileges via `su-exec nobody:nobody /usr/local/bin/vault-snapshot.sh`.
The main snapshot loop continues to run as `nobody` — defense-in-depth
preserved. The chown step targets ONLY the `vault-snapshots/` subdir
(Litestream writes to `/backup/state.db/` and is unaffected).

### Bug 3 — `.env` missing `FWD_VAULT_SNAPSHOT_*_ID` credentials (operator-host)

The `vault-init.sh` script was last run on 2026-05-02 against the dev
Vault — pre-v0.4.2, before the `fwd-snapshot` AppRole existed. The script
was extended at v0.4.2 to also create the snapshot role + emit its
credentials, but the operator's local `.env` was never updated. The
vault-snapshot sidecar therefore had no `FWD_VAULT_SNAPSHOT_ROLE_ID` /
`FWD_VAULT_SNAPSHOT_SECRET_ID` to authenticate with.

**Fix:** re-ran `scripts/vault-init.sh` idempotently against the dev
Vault. The script's step 7 rotates the fwd `secret_id` on every run
(non-expiring per `secret_id_ttl=0`), and steps 11-12 create the
snapshot role + emit its credentials. The four-pair output was written
to `.env` (operator-host file, not in version control).

### Bug 4 — Restore runbook Step 2 / 3 order is fatally wrong (doc)

The runbook said "Step 2: `docker compose up -d` (start all four
services), then Step 3: `litestream restore ...`". Three failures
result:

1. fwd's entrypoint runs `alembic upgrade head` before `uvicorn`,
   creating a fresh empty `state.db` in the freshly-empty `fwd-state`
   volume.
2. The litestream service notices the new `state.db`, treats it as a
   NEW replication source, and creates a brand-new generation in
   `/backup/state.db/generations/` — sitting alongside the pre-disaster
   generation copied in from the off-host backup.
3. Step 3's `litestream restore` then picks the LATEST generation
   (which is the empty post-alembic one), silently overwriting the
   real backup.

The drill surfaced this immediately: my first restore attempt restored
generation `6b468de330d2716f` (empty schema, 2.5KB snapshot) instead of
`afdea5ed723aa224` (pre-disaster state, 17KB snapshot).

**Fix:** runbook Step 2 rewritten — bring up ONLY `vault` (and optionally
`vault-snapshot`) initially. The fwd and litestream services stay down
until Step 3 completes. The runbook now explicitly explains why and
links to the v0.4.6 drill.

### Bug 5 — Runbook drift in Step 1, 3, 4(d), 7 (doc)

Four smaller drifts between runbook prose and live behaviour:

| Drift | Reality |
|---|---|
| Step 1 / pass criterion checks `/b/state.db.litestream/` | Litestream 0.3.13 type:file writes to `/b/state.db/` (no `.litestream` suffix) |
| Step 3 throwaway-litestream command uses `sh -c '...'` | The litestream image has `ENTRYPOINT ["litestream"]`; must use `--entrypoint /bin/sh ... -c '...'` |
| Step 4(d) says "Vault becomes sealed after restore" | True on disk, but `vault status` shows cached in-memory seal config (the dummy 3/2 instead of the real 5/3) until the vault container is restarted |
| Step 7 says happy path emits `nonce_reconcile.complete` | No such event in `src/fwd/app/nonce_reconcile.py` — reconcile emits warnings ONLY on drift / orphan / RPC failure; silence is the happy-path signal |

**Fix:** all four corrected in `docs/runbooks/restore.md` per v0.4.6
runbook diff. Step 4 now includes an explicit `docker compose restart vault`
step after `snapshot restore` to refresh `vault status` from disk.

## What v0.4.6 deliberately does NOT do

- **Multi-host restore drill.** Phase 6 v1 scope is single-host
  (CLAUDE.md "What FWD Deliberately IS NOT" — single replica). Multi-host
  is a Phase 10 ops enhancement.
- **Production cut.** Core invariant #17 — the dev-mode `~/.fwd-dev/`
  shortcut is still in effect; the wipe-and-redo D6 distribution ritual
  is deferred to Phase 8 (first production migration: `ftso-fee-claimer`
  switching from `.env PRIVATE_KEY` to fwd-custodied wallet).
- **`clifwd reconcile` subcommand.** Currently only lifespan-startup
  reconcile exists. A dedicated CLI subcommand was flagged in the runbook
  as Phase 7 or a Phase 6 follow-up; not in v0.4.6 scope.
- **Off-host transport tooling.** Operator-driven per v0.4.3 reversion;
  out of fwd scope.
- **Defense-in-depth retreat in vault-snapshot.** The wrapper preserves
  `USER nobody` for the snapshot loop — root only runs for the one-shot
  chown. No reduction in container hardening.
