## Why this ship

Phase 5 alpha 2 closes the highest-stakes correctness gap in v0.4.0: concurrent `/v1/sign-and-send` calls against the same wallet must produce monotonically-increasing nonces with no gaps and no duplicates. Without the DB-side nonce manager, two near-simultaneous callers race the RPC `eth_getTransactionCount("pending")` and both build a tx at nonce N — one wins on broadcast, the other gets rejected by the chain. v0.4.0a5 makes this impossible by serializing nonce bookkeeping under SQLite's `BEGIN IMMEDIATE` writer lock.

## What ships

### Doctrine adherence

Sign-and-send now follows `docs/architecture.md` § Signing flow verbatim:

| Step | Code | Architecture.md ref |
|---|---|---|
| 6 — Reserve nonce | `BEGIN IMMEDIATE; SELECT next_nonce; UPDATE next_nonce+1; COMMIT;` returns N | `:122-127` |
| 7 — RPC fee fail → release | `release_if_unused(wallet, chain, N)` → 502 | `:187` |
| 10 — Vault decrypt fail → release | `release_if_unused(...)` → 503 | `:189` |
| 11 — eth-account malformed → release | wrapped in same try/except (ValueError catch) | `:190` |
| 13 — RPC broadcast fail → **stays committed** | no release in this path | `:191-192` |

Release uses the safe-conditional decrement per architecture.md:189 verbatim:
```sql
UPDATE nonces SET next_nonce = next_nonce - 1
  WHERE wallet = :w AND chain = :c AND next_nonce - 1 = :reserved
```
`rowcount == 1` → we were the most-recent reserver, decremented; `rowcount == 0` → someone else reserved after us, leave the gap as operator-visible drift.

## Deviations and Reviewer corrections

### Sonnet's deviation — SQL form for `reserve_next`

Sonnet implemented `reserve_next` as **two-step** (SELECT next_nonce, then UPDATE next_nonce+1) rather than the architecture.md:124-126 verbatim form (`UPDATE...RETURNING next_nonce`). Justification given: "SQLite 3.35+ supports RETURNING natively; this two-step form is compatible with SQLite 3.31+ (the version shipped in Ubuntu 20.04)."

**Reviewer initial response (Path c — inline tweak)**: rewrote to `UPDATE...RETURNING` per architecture.md verbatim, reasoning that Docker runtime ships SQLite 3.40+ so RETURNING should work, and Core invariant #18 demands doctrine-code alignment.

**Reviewer correction after running tests**: the dev host (`python -c "import sqlite3; print(sqlite3.sqlite_version)"`) returns 3.31.1 — same as Ubuntu 20.04. Local tests failed with `sqlite3.OperationalError: near "RETURNING": syntax error`. Sonnet's two-step was correct for both dev (3.31) and prod (3.40+); the verbatim form only worked in Docker.

**Final resolution**: reverted to Sonnet's two-step AND updated `architecture.md` § Signing flow step 6 to specify the two-step as canonical doctrine with the cross-environment rationale inline. This is **Core invariant #18 flowing both ways** — when reality and doctrine diverge, the right action depends on which one is wrong. Here doctrine was wrong (verbatim SQL didn't run on the dev host); doctrine got updated.

Lesson logged: Reviewer should grep the dev environment's tooling versions before insisting on verbatim doctrine where the doctrine encodes a specific dependency version assumption.

### Sonnet's deviation — `engine.sync_engine "begin"` event listener

Sonnet used the canonical prompt's primary recommendation (`event.listen(engine.sync_engine, "begin", _begin_immediate)`) rather than the fallback (`event.listens_for(Engine, "begin")`). Instance-scoped is the better choice — fires only on the fwd engine, not on every SQLAlchemy engine in the process. Accepted.

### Sonnet's deviation — integration test modified

Spec said "carry forward unchanged if the integration test works with first-call RPC init." Sonnet had to modify it because the call site requires the 5th positional arg. Mechanical adaptation; accepted.
