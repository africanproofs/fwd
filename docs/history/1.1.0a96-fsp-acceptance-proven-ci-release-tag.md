## Headline — FSP acceptance is no longer "deferred"; it is demonstrated

The dominant open item across two readiness audits was: *is our imported signing-policy key an
accepted on-chain registered voter?* It was inferred, never demonstrated — every prior live attempt
hit the FSM window guard (`signUptimeVote` reverts `'epoch not ended yet'` before the
signer-registration check). **For reward epoch 404 it is now proven end-to-end, unattended, on BOTH
chains:**

- **Songbird:** our signing-policy key's `RewardsSigned` event landed; the epoch finalized
  (`rewardsHash(404)` = `0x8eb571…eab5`, 50.43% signing weight; leading hash == on-chain
  `rewardsHash`); rewards claimed.
- **Flare:** same — `RewardsSigned` from our key, finalized (`rewardsHash(404)` =
  `0xff02f8…095dd`, 51.77%); rewards claimed.

All in one automated `clif epoch run` cycle (operator-confirmed). A successful `signRewards` passes
the same signer-registration check `signUptimeVote` does, so this proves the imported key is an
accepted registered voter. Evidence captured via `clif epoch signing-progress --epoch 404` (our_signed
= true both chains) + on-chain `rewardsHash(404)` (non-zero both chains) + the operator's
claim confirmation. (Note: `getVoterRewardsSignInfo(404, signingPolicyAddr)` returns 0 — a quirk of
that view; the `RewardsSigned` events are authoritative, which is exactly why clif 0.5.31 detects our
vote via the events, not the view.)

UPTIME signing uses the same signer-registration path (acceptance follows) and stays gated off by
default (`UPTIME_AUTO_ENABLED`).
