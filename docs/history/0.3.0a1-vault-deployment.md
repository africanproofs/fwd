# v0.3.0a1 — Phase 3a, Vault deployment

> Phase 3a sub-ship landed 2026-05-02. First half of "Vault deployment + signing core" (Phase 3 split into 3a/3b/3c per operator decision). This ship adds the Vault initialization machinery; no fwd code changes.

## What landed

- **`config/vault/policies/fwd-app.hcl`** — Vault policy verbatim from `architecture.md` § Vault configuration. `update` on `transit/encrypt/fwd-master` + `transit/decrypt/fwd-master`; `read` on `transit/keys/fwd-master`; explicit comment that `transit/sign/*` is NOT granted (per the v0.1.2 envelope-encryption architecture).
- **`scripts/vault-init.sh`** — POSIX `/bin/sh` script, idempotent, runs inside `fwd-vault` after the operator unseals Vault. Enables Transit, creates the `aes256-gcm96` master key, writes the policy, enables AppRole, creates the `fwd` role, prints `FWD_VAULT_ROLE_ID` + `FWD_VAULT_SECRET_ID` to stdout for the operator to paste into `.env`.
- **`docs/runbooks/vault-init.md`** — first runbook. Walks the operator through the full ritual: `vault operator init -key-shares=5 -key-threshold=3`, share distribution (per D6: 2 paper + 3 GPG-encrypted across 5 failure domains), `vault operator unseal × 3`, `vault-init.sh`, `.env` update, restart fwd, root token revocation as Phase 3.5.
- **`docker-compose.yml`** — vault service volumes updated. The previous single-file mount `./config/vault/config.hcl:/vault/config/config.hcl:ro` is replaced with a directory mount `./config/vault/:/vault/config/:ro` (so the policy file at `/vault/config/policies/fwd-app.hcl` is also visible inside the container) plus `./scripts/:/vault/scripts/:ro` (so the operator can run `docker exec ... /vault/scripts/vault-init.sh`).
- **`.env.example`** — `# VAULT_TOKEN=` placeholder replaced with `FWD_VAULT_ROLE_ID=` + `FWD_VAULT_SECRET_ID=` (uncommented; values blank for the operator to fill).
- **Version bump** — `pyproject.toml` and `src/fwd/version.py` both move from `0.3.0a0` to `0.3.0a1`.

## What this ship deliberately does NOT include

- **No Python code changes.** The Vault client wrapper (`infra/vault_client.py`) and the `EnvelopeSigner` implementation are Phase 3b's deliverables.
- **No new endpoints or CLI commands.** Phase 3b adds `clifwd wallets create` and `POST /v1/admin/wallets`.
- **No automated end-to-end test against a real running Vault.** The init ritual requires manual operator interaction (capturing root token, distributing shares, providing 3 unseal keys). The implementation gate is the operator-driven runbook walkthrough, not CI.
- **No TLS on the Vault listener.** Phase 2's `tls_disable = true` carries forward — the `fwd-internal` Docker network is the security boundary. TLS within the network is a defense-in-depth Phase 3b/c addition.
- **No auto-unseal.** Phase 10 deliverable.
- **No `/healthz` refinement to distinguish "uninitialized" vs "sealed".** Phase 3b ships that alongside the Vault client (when fwd actually starts using Vault for operations).

## Verification — manual operator gate

The CI gate is limited (file presence; version-consistency test). The real verification is operator-driven:

1. `docker compose up --build -d` — picks up the v0.3.0-alpha CMD change (`fwd.app:app` → `fwd.main:app`) AND the v0.3.0a1 volume mount changes for the vault service.
2. `docker exec fwd-vault vault status` — shows `Initialized: false, Sealed: true`.
3. Operator runs `docs/runbooks/vault-init.md` end-to-end.
4. After step 5 of the runbook, operator confirms the script's "fwd Vault initialization complete" output and captures the role_id + secret_id.
5. After step 7, operator runs the four `vault read/list/policy read` commands and confirms each returns data without errors.

If any step fails: STOP, surface the error to the Reviewer, do NOT improvise around it.
