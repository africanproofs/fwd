**Shipped**: 2026-05-12
**Author**: Sonnet 4.6 (implementation), Opus 4.7 (Reviewer, canonical prompt + review + commit + path-(c) bug fixes)

## Why this ship

After v0.4.0a5 (nonce manager), a tx broadcast by fwd had no automatic lifecycle. Status stayed `submitted` forever; stuck txs were never replaced; a wallet with the first tx in a sequence stuck at low fees would block every subsequent nonce indefinitely. `nonce_repo.last_confirmed` (added a5) was unused.

v0.4.0a6 closes that gap with an asyncio receipt watcher started in lifespan that polls every pending tx, transitions status on mining, and replaces stuck txs with bumped fees. This is the last substrate piece before the v0.4.0 GA verification gate (live 10-concurrent + low-gas-replacement on Coston2) can run.

## What ships

### Doctrine adherence

The watcher implements `docs/architecture.md` § Signing flow step 16 + § Failure modes:

| Architecture.md statement | Code |
|---|---|
| "Poll eth_getTransactionReceipt for each pending tx" | `_process_tx` walks `list_hashes_by_tx`, calls `rpc.transaction_receipt(h.hash_hex)` for each |
| "On confirmation: status='mined', call nonce_repo.mark_confirmed" *(updated this alpha — was 'confirmed' in the original text)* | `update_status("mined", ...)` + `nonce_repo.mark_confirmed(tx.wallet, tx.chain, tx.nonce)` |
| "On stuck (N blocks elapsed): replace with bumped tip" | `(now - submitted_at) > stuck_threshold_sec` → `_replace(...)` |
| "Replacement appends a new row to transaction_hashes (tx_id, sequence_num=N+1, hash_hex)" | `tx_repo.add_hash(tx_id, new_hash, sequence_num=len(hashes)+1)` |
| "On final failure (5 retries): status='failed', surface alert" | `if len(hashes) >= max_retries: update_status("failed", ...)` |

Replacement math (`implementation-plan.md:123` — "bumped tip × 1.125"):
- `new_tip = int(_DEFAULT_TIP_WEI * (config.tip_multiplier ** new_seq))` — bumps compound across retries (seq=2 → 1.27 gwei, seq=3 → 1.42, seq=4 → 1.6, seq=5 → 1.8).
- `new_max_fee = base_fee * 2 + new_tip` — basefee fetched fresh each replacement.

Status semantics: only `submitted → mined` and `submitted → failed`. The logical tx is one `tx_id` with multiple `transaction_hashes` rows; status stays `submitted` through ALL retries. `replaced` and `dropped` (external nonce consumption) defer to Phase 7.

### Bugs Sonnet missed (Reviewer-fixed during review, path-c inline tweaks)

Sonnet's deviation #5 and open-question #4 each flagged the SYMPTOM of a bug but did not fix the underlying production bug. Both surfaced during file-by-file review.

**Bug #1 — naive `submitted_at` from DB → TypeError on every production tick**

The schema declares `transactions.submitted_at` as `DateTime(timezone=True)`. We write `datetime.now(UTC)` (aware). But aiosqlite + SQLAlchemy 2.x strips tzinfo on round-trip: `repo.get_by_id(...).submitted_at` returns NAIVE. The watcher's stuck-check does:

```python
age_sec = (datetime.now(UTC) - tx.submitted_at).total_seconds()
```

`datetime.now(UTC)` is aware. `tx.submitted_at` is naive. Subtraction raises `TypeError: can't subtract offset-naive and offset-aware datetimes`. In production, EVERY tx that didn't immediately mine would trip this on every tick of every watcher pass. Forever. The watcher would never reach the stuck-replacement code.

Sonnet's unit tests passed because the test fixture builds `Transaction` dataclasses directly with `datetime.now(UTC)` (aware), bypassing the DB round-trip. Sonnet noted the round-trip symptom in deviation #5 and adapted the *test assertion* — but didn't fix the production path.

Reviewer fix (path-c inline tweak in `app/receipt_watcher.py`):
```python
submitted_at = tx.submitted_at
if submitted_at.tzinfo is None:
    submitted_at = submitted_at.replace(tzinfo=UTC)
age_sec = (datetime.now(UTC) - submitted_at).total_seconds()
```

Plus a NEW regression test `test_process_tx_handles_naive_submitted_at_from_db` that constructs a `Transaction` with `naive_submitted = datetime.now(UTC).replace(tzinfo=None)` to simulate the post-round-trip state and asserts the watcher does NOT raise + does attempt replacement.

Reviewer verification: `poetry run python -c "..."` round-trip experiment proved `repo.get_by_id` returns naive datetimes even for `DateTime(timezone=True)` columns. The fix is bounded to the comparison call site for v0.4.0a6; Phase 7 may centralize tzinfo normalization at the repo layer (`Transaction`, `Nonce`, `Wallet`, `Caller` all share this pattern).

**Bug #2 — `from` field in estimate_gas was the wallet name, not the address**

In replacement, Sonnet's code passed `tx.wallet` (e.g., `"primary"`) as the `from` field to `rpc.estimate_gas`. Geth and erigon expect a 0x-prefixed address there; passing a name causes either rejection or estimation against the zero address (silently wrong). The spec had a comment acknowledging this but Sonnet kept the verbatim code; Sonnet flagged it for GA validation rather than fixing.

Reviewer fix (path-c inline tweak in `app/receipt_watcher.py`):
```python
try:
    from_address = await signer.address(tx.wallet)
except Exception as exc:
    logger.warning("receipt_watcher.replace_address_failed", tx_id=tx.tx_id, error=str(exc))
    return
# ... use from_address in estimate_gas call_obj
```

Test update: `_signer()` helper gains `address = AsyncMock(return_value=...)`; `test_replace_estimates_gas_if_not_provided` now asserts `signer.address.assert_awaited_once_with(tx.wallet)` AND that the `estimate_gas` call object's `from` field is the resolved 0x address.

### Why these bugs slipped past Sonnet's tests

Both stem from the same pattern: **unit tests that mock infrastructure can pass on code that would fail in production**. The watcher's mocked `tx` dataclass never goes through a real DB; the mocked `_signer` never goes through `estimate_gas`. Sonnet had test coverage of the contract shapes but not of the DB-round-trip path or the real RPC contract.

Lesson: when an alpha's verification gate is deferred (live 10-concurrent is v0.4.0 GA, not a6), Reviewer must extra-carefully exercise the seams between mocked and real infrastructure during review. The "is anything truly aware vs naive after a DB read" question is the kind of seam that catches in production but slips through unit tests.
