# v1.1.0a40 — default reward policy ships visibly + names-pre-filled onboarding runbook

**Type:** docs ship (no daemon code change).
**Date:** 2026-05-31.
**Authoring:** Reviewer (Opus); operator-gated.

## Why

A provider bringing up the stack has to get the two revenue operations working —
**claiming FTSO rewards** (`RewardManager.claim`) and **signing FSP rewards**
(`signUptimeVote` / `signRewards`) — without learning the a29 policy schema. The
default-policy *substrate* already shipped (`clifwd policy init` defaults to
`--capabilities claim,fsp`, a31). The residual cognitive load is **sequencing the
~7 admin commands in the right order, with names pre-matched to the generator's
output, across a daemon restart** (`wallets`/`callers create` validate
`policy_path` against the *loaded* policy, so the policy must be loaded — restarted
— before any create). This ship makes the default reward policy visible and turns
the onboarding into a copy-paste runbook. (Operator-chosen phasing: ship the
visible default + runbook now; a one-command `fwd onboard rewards` orchestrator is
the next ship.)

## Correctness fix folded in

The prior banner's step 1 was `clifwd policy init … --out $SRC/config/policy.yaml`
— but `clifwd` runs **in-container** (`docker exec`), where that host path is not
the read-only-mounted policy file, so the generated policy would never reach the
host. Corrected to a host-shell **stdout redirect** (`clifwd policy init … >
config/policy.yaml`): the `>` runs in the host shell, capturing `docker exec`'s
stdout and writing the host file the container mounts read-only as the live
policy. `validate --schema-only` then reads that live mount with no daemon
running; `sudo fwd restart` loads it into memory before any `create`.

## Verification

- **Round-trip:** `clifwd policy init --networks coston2 --recipient
  0xYOUR_CLAIM_RECIPIENT_ADDRESS --capabilities claim,fsp` output is
  **semantically identical** (YAML-normalized) to the new `policy.example.yaml`;
  both pass `clifwd policy validate --schema-only` (3 callers / 2 permissions /
  3 wallet_constraints / 1 fsp_permissions).
- **Name consistency:** every caller / wallet / policy_path the generator emits
  (`claim-coston2`, `claimer-coston2`, `fsp-sender`, `fsp-sign-coston2`,
  `fsp-signing-coston2`, `fsp-submit-coston2`, `fsp/coston2`, `perm/claim-coston2`,
  `perm/fsp-submit-coston2`, `wc/claimer-coston2`, `wc/fsp-coston2`,
  `wc/fsp-sender`) appears verbatim in BOTH the doc runbook and the installer
  banner.
- `bash -n install/install.sh` clean; the banner heredoc has no unintended
  command-substitution (`$SRC` is the only expansion).
- Docs-only — no `src/` change; pytest/ruff/mypy unaffected.
