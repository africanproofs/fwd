# v1.1.0a94 — onboard writes FSP_AUTO_ENABLED=true by default (the onboard is the gate)

**Type:** onboarding UX. **No daemon/signing-path change** — only `install/onboard`
(+ version files). `src/` untouched.
**Date:** 2026-06-08. **Filed retroactively at a95** — this record was missing; the
deployment-readiness audit flagged a94 as shipped without its history file / index line
(tech-debt-02).

## Why

`fwd onboard` previously wrote `FSP_AUTO_ENABLED=false` into the clif `.env.<net>`, forcing
the operator to hand-edit it to `true` after rehearsal — making the env flag the gate. The
cleaner model: the **onboard itself** (and the `clifctl up <net>` bring-up) is the gate.
Onboarding a network is a deliberate act, so the daemon should default to enabled and the
operator simply chooses when to bring it up (after rehearsal). Set `=false` to keep a network
idle.

## What changed (`install/onboard`, 8 lines)

- The written default flipped: `getval "$_ew_dst" FSP_AUTO_ENABLED true` (was `false`) — onboard
  now writes `FSP_AUTO_ENABLED=true`.
- The post-onboard guidance changed from "set FSP_AUTO_ENABLED=true AFTER you rehearse" to
  "FSP_AUTO_ENABLED=true is written by default — the onboard is the gate; `clifctl up <net>`
  starts the daemon; set =false to keep it idle".

## Drift it introduced (reconciled at a95)

README + `docs/production-setup.md` + `docs/one-command-install.md` still instructed the operator
to set the flag manually ("hard-off by default / must be set"). a95 reconciles those to "onboard
writes it by default; the bring-up is the gate" (tech-debt-03). Scope (current-state) was
unaffected by a94.
