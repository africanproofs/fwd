# v1.1.0a59 — bake `FWD_CONTAINER` into installed wrappers; `fwd start <net> fsp` = FSP daemon ONLY

**Type:** installer + host-wrapper ship (`install/install.sh`, `install/fwd`, docs) + a bounded CLAUDE.md §Scope current-state correction. Reviewer-implemented. Verified by `sh -n` + `docker compose config` per profile. Operator-authorized ("go ahead" on their own reviewer's PART A — three MAJORs). Closes two non-default-mode gaps the third adversarial review surfaced; the operator's DEFAULT claim+FSP prod run (container `fwd`) was already safe.
**Date:** 2026-06-03.

## Why (third review — PART A, three MAJORs)

The operator's own reviewer found three issues against the a51–a58 redesign. None blocked the
default prod run (container literally named `fwd`, claim+FSP both wanted); all three gated
non-default modes or doc accuracy:

1. **`FWD_CONTAINER` not baked into the installed wrappers.** A host installed with a custom
   `FWD_CONTAINER` (e.g. running fwd beside an existing one) got wrappers whose `docker exec`
   target still defaulted to `fwd` — so `clifwd …` and `fwd onboard` would hit the wrong (or a
   non-existent) container. The default install (`FWD_CONTAINER` unset → `fwd`) was unaffected.
2. **`fwd start <net> fsp` started BOTH daemons.** a58 made `fwd start <net> fsp` bring up the
   claim daemon **and** the FSP auto-signer. On a `--sign-only` (FSP-only, no-claim) host there is
   no claim wallet / no claim caller token / `.env.<net>` has no claim keys (onboard gates them by
   `HAS_CLAIM`), and `clif auto` exits when no beneficiary is configured — so the claim daemon
   crash-loops under `restart: unless-stopped`. The FSP opt-in dragged in a claim daemon the host
   was never set up to run.
3. **CLAUDE.md §Scope overstated FSP verification.** The §Scope line claimed "the reward-claim +
   FSP signing paths are mainnet-verified", but Core invariant #17 and `docs/architecture.md`
   record that FSP *on-chain acceptance* is **deferred/unverified** (the fwd-generated signing key
   is not yet a registered voter — `signUptimeVote` reverts `'invalid signing policy address'`).
   fwd *signs* FSP messages and the clif↔fwd integration is verified; on-chain protocol acceptance
   is not. The doc conflated the two.

## What changed

- **`install/install.sh`:** after the `CLIF_SRC` bake loop, a third `sed` loop rewrites the
  `${FWD_CONTAINER:-fwd}` default inside the three installed wrappers (`fwd`, `clifwd`, `clif`) to
  `${FWD_CONTAINER:-$FWD_CONTAINER}` — i.e. the install-time container name becomes the baked
  default. Default install (`FWD_CONTAINER` unset → `fwd`) bakes `${FWD_CONTAINER:-fwd}` → identical
  no-op; a custom value persists into the wrappers so a runtime-unset `FWD_CONTAINER` still targets
  the container the operator installed against.
- **`install/fwd`:** `fwd start <net> fsp` now activates `--profile <net>-fsp` **ONLY** (the FSP
  auto-signer), not `--profile <net> --profile <net>-fsp`. `fwd start <net>` is unchanged
  (`--profile <net>` = claim daemon only). A claim+FSP provider runs **both** commands. Bare
  `fwd start fsp` (no network) is rejected with a clear message + exit 2. Header comment + help line
  + `docs/one-command-install.md` updated to the "claim and FSP are independent; run both for both"
  model. This keeps a sign-only host from ever launching a beneficiary-less claim daemon.
- **`CLAUDE.md` §Scope (current-state line, bounded correction):** "the reward-claim + FSP signing
  paths are mainnet-verified" → wording that distinguishes (a) the claim path + fwd's FSP *signing*
  + the clif↔fwd integration are mainnet-verified, from (b) FSP *on-chain acceptance* being deferred
  per Core invariant #17. This realigns §Scope with Core #17 / `docs/architecture.md`; no code claim
  is changed, only the doc is brought back to the present (Core invariant #18).
