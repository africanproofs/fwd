## What shipped — code only (the invariant *text* reconciliation is deferred)

The address-level key-domain segmentation invariant
(`policy_loader.check_consistency`) — the headline STOP-SHIP finding of the
three pre-FSP adversarial reviews — fail-fast refused to boot whenever one
wallet address was reachable from BOTH an EVM `permissions` allowlist AND an
`fsp_permissions` allowlist. That refusal stays exactly as-is for everyone
**not** explicitly opted in. A new, narrow, default-off opt-in admits the
specific "FSP signer self-submits its Leg-2 tx" pairing — the upstream
single-key mode — without widening the invariant for anything else:

- **`src/fwd/domain/policy.py`** — `Policy` gains
  `fsp_self_submit: list[str] = Field(default_factory=list)` (empty default
  → invariant unchanged for everyone not opting in). Backward-compatible.
- **`src/fwd/infra/policy_loader.py`** — a module-level frozenset
  `_FSP_SELF_SUBMIT_METHODS` pins the two canonical FlareSystemsManager
  signatures (`signUptimeVote(uint24,bytes32,(uint8,bytes32,bytes32))`,
  `signRewards(uint24,(uint256,uint256)[],bytes32,(uint8,bytes32,bytes32))`).
  `check_consistency` exempts an opted-in wallet's address from the
  `evm_addrs & fsp_addrs` violation **only** when every `permissions` block
  that allowlists it has contracts exclusively `flare_systems_manager` with
  methods ⊆ `_FSP_SELF_SUBMIT_METHODS` and every method's `max_value_wei ==
  "0"`. A declared-but-misused opt-in (unknown wallet name; not in any
  fsp_permissions allowlist; not in any permissions allowlist; or allowlisted
  in a non-conforming block) **fail-fasts** with a specific error — the
  carve-out only ever *removes* an address from the violation set; it never
  silently widens.
- **`src/fwd/app/fsp_policy.py`** — **no change** (the runtime belt is
  policy_path-level, not address-level; the FSP-sign caller binds
  `fsp_permissions`, the submit caller binds `permissions` — different
  callers/tokens, unaffected by a shared wallet, per the module's own
  docstring).
- **Tests** (`tests/unit/test_fsp_policy_loader.py`) — 7 new cases: happy
  carve-out; 3 negative-shape variants (extra method / non-FSM abi /
  nonzero `max_value_wei` each independently → "carve-out refused"); opt-in
  not in fsp allowlist → "meaningless carve-out"; opt-in not in any
  permissions allowlist → "carve-out declared but unused"; regression — a
  shared-address pair with `fsp_self_submit` empty/naming-a-different-wallet
  still fires the original violation exactly as before. The STOP-SHIP
  invariant is intact for everyone who hasn't explicitly opted in.

### Why this is safe (the bounded argument the operator authorized)

The segmentation invariant's threat is "a key authorized for opaque signing
also able to broadcast arbitrary EVM transactions." For this specific
pair both halves are already neutralised by other policy: Leg-1
(`/v1/sign-fsp-message`) is EIP-191 personal-sign of a fwd-**reconstructed**
typed messageHash — the caller never supplies a raw digest (Core #3
v1.1.0a5 reframe); Leg-2 is policy-pinned to exactly
`signUptimeVote`/`signRewards` on the FSM contract(s) with
`max_value_wei: 0`. A *bounded, policy-gated* same-address-self-submit
carve-out admits this case without reopening the general threat — and even
*with* the carve-out, fwd remains strictly safer than the upstream
`signing-tool` reference (which has zero policy gating and a fully hot
single key).
