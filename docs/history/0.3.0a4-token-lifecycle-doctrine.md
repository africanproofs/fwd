## What this ship adds

1. **`docs/decisions.md` D10** — *Token lifecycle: re-auth on 403 (v1), proactive renewal at Phase 7, periodic tokens at Phase 8*. Decision + alternatives considered (4) + reasoning (4 numbered points) + per-phase consequences + when-to-revisit triggers.
2. **`docs/architecture.md` § Auth lifecycle** — concrete v1 / Phase 7 / Phase 8 lifecycle table + migration procedure for the Phase 8 periodic-token cut.

## The decision in brief

| Phase | Token strategy | Code |
|---|---|---|
| **v1 (3b–6)** | Login on startup; cache `client_token`; **single-retry-on-403 fallback** in `_request()`. No background task. | ~50 lines |
| **Phase 7 (v0.5.0)** | Add asyncio background task: `auth/token/renew-self` every `lease_duration / 3`; full re-auth at `max_ttl` boundary. 403 fallback stays as defense-in-depth. | +80 lines |
| **Phase 8 (v1.0.0)** | If real high-frequency consumer materializes: re-run `vault-init.sh` with `token_period=24h, token_max_ttl=0`. Same client code; only role config changes. Operator-driven `secret_id` rotation replaces automatic re-auth. | 0 lines (operator-side flag change) |

## Why this staging

1. **v1 volumes are low.** Wallet creation is rare. Phase 3c's verification gate is one Coston2 tx. Phase 8's `ftso-fee-claimer` claims ~once per reward epoch (3.5 days, well below the 24h TTL). The 403 fallback is sufficient and exercises the re-auth path end-to-end.
2. **The 403 fallback is canonical defense-in-depth.** Clock skew, vault failover, manual revocation — all surface as 403. Building it first means the renewal task adds complexity *without changing the surface contract*.
3. **Real consumers drive design.** Designing a renewal protocol against a hypothetical every-minute workload is a Karpathy violation. Real consumer (`fics` write paths, AI-agent signing, market-making bot) shape informs the renewal interval and fallback cost when it lands.
4. **Periodic tokens are operator-side.** Switching from `token_ttl/token_max_ttl` to `token_period` is a flag change in `vault-init.sh`. Same client code on either side; decoupled migration aligns naturally with Core invariant #17's production wipe-and-redo.
