# v0.1.1 — pre-Phase-1 documentation fixes

> Doc-only ship landed 2026-04-30. CTO review of v0.1.0 surfaced three issues that block a clean Phase 1 / Phase 2 build. Fixed here as documentation revisions; implementation lands in the named phases.

## Fixes

### Fix 1 — Relational schema for decoded intent and hash history

`docs/architecture.md` § SQLite schema previously stored decoded transaction intent as `intent_json` (a JSON blob) and the replacement-hash list as `hashes_json` (a JSON array). Both violate the doctrine "no JSON blobs for core entities" — these are queryable domain data, not opaque archives.

Replaced with:

- Explicit columns on `transactions`: `contract_address`, `method_name`, `value_wei`, `idempotency_key`.
- New child table `transaction_args (tx_id, arg_name, arg_type, arg_value)` for decoded function arguments.
- New child table `transaction_hashes (tx_id, sequence_num, hash_hex, submitted_at)` for replacement history.
- `wallets.chains` (JSON array) replaced with new join table `wallet_chains (wallet, chain)`.

`request_json` and `receipt_json` remain as JSON — these are opaque forensic archives of caller-submitted payloads and RPC responses, not domain data we query against.

Implementation lands in Phase 5.

### Fix 2 — Idempotency-Key header contract, error envelope, versioning policy

`docs/architecture.md` § API surface lacked three contracts that external integrators (and AP backends acting as integrators) need:

- **`Idempotency-Key` header** for `POST /v1/sign-and-send`: caller-supplied UUIDv7, stored on the transaction row, duplicate detection per `(caller, key)`. Prevents duplicate on-chain transactions under retry storms.
- **Error envelope** with stable error codes: `{code, message, request_id}` shape; HTTP status mappings; explicit don't-leak rules (no SQL state, no tracebacks, no API keys).
- **Versioning policy**: path-prefix `/v1/*`, additive changes non-breaking, breaking changes ship as `/v2/*` with ≥6 months `/v1/*` overlap.

All three contracts are documented now; implementation lands in Phase 5 (idempotency) and Phase 3 (error envelope shape comes online with the first endpoint).

### Fix 3 — Layer boundaries section

`docs/architecture.md` previously implied a domain/application/infrastructure/interface separation through component descriptions but never named the layers or their prohibitions. For a Python service written under the Opus-prescribes / Sonnet-implements workflow, the boundary between "policy engine" (domain) and "FastAPI handler" (interface) will blur unless explicitly defended.

Added § Layer boundaries documenting:

- Per-layer responsibilities and "must NOT" lists
- Package layout (`src/fwd/{domain,app,infra,api}`) committed for Phase 2
- An import-graph test (`tests/unit/test_layer_boundaries.py`) committed as a Phase 2 deliverable that walks the import graph and fails on violations

## What this ship deliberately does NOT include

- Code. No `pyproject.toml`, no `src/fwd/`, no Docker artifacts. Phase 2 ships those.
- Schema migrations. Alembic ships in Phase 5; the schema documented here is the *target* for that migration.
- The actual import-graph test. Phase 2 ships it.
- The actual idempotency handler. Phase 5 ships it.
