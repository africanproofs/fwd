# v0.1.2 — Vault Transit pivot to envelope encryption

> Doc-only ship landed 2026-05-01. v0.2.0 (Phase 1 — Coston2 signing spike) attempt surfaced a foundational architectural blocker: Vault Transit does not support secp256k1 (Ethereum's curve). This ship revises D1 to use Vault as an encryption envelope rather than a signer, with signing in fwd's process post-decrypt.

## What v0.2.0's spike attempt found

A prior Sonnet session executed the v0.2.0 canonical prompt and STOPPED at key creation. Vault 1.18.2 OSS rejected `ecdsa-p256k1` as an unknown key type. Plausible alternative names (`secp256k1`, `ecdsa-secp256k1`, `ethereum`, `bitcoin`, `k256`, `p256k1`) all rejected. Verified independently against `developer.hashicorp.com/vault/docs/secrets/transit` (Vault OSS supports `ecdsa-p256`, `ecdsa-p384`, `ecdsa-p521` only) and `openbao.org/docs/secrets/transit/` (same three NIST curves; no secp256k1).

Per Core invariant #5 ("when the proposer doesn't have a path for an observed gap, STOP and surface to the operator"), the implementer correctly stopped and surfaced the blocker.

## Six secondary findings from the v0.2.0 attempt

The v0.2.0 spike's implementer also surfaced six minor deviations from the canonical prompt while exploring the architecture. These remain valid under the revised v0.1.2 architecture and inform Phase 3:

1. **Python 3.11 fallback.** `.python-version` says 3.12; pyenv had 3.11.4 available. 3.11.4 used; deviation noted. (Phase 2 should ensure Python 3.12 is installed before scaffolding.)
2. **`eth_account._utils.typed_transactions` moved.** In `eth-account` 0.13.x, the import path is `eth_account.typed_transactions` (no `_utils.` prefix). Fixed in script.
3. **`TypedTransaction.encode()` requires signature.** Calling `.encode()` on an unsigned transaction raises `ValueError`. The correct method for the signing-hash payload is `.hash()`, which returns `keccak256(0x02 || rlp(unsigned_fields))` directly. **Moot under the v0.1.2 revision** because we now sign with `Account.sign_transaction(tx_dict)` directly and don't manually compute digests.
4. **`to:` field requires EIP-55 checksum.** `TypedTransaction.from_dict` rejects lowercase hex addresses. Wrap with `eth_utils.to_checksum_address` before passing.
5. **`hvac` 2.3.0 client-side allowlist.** `hvac.create_key()` validates `key_type` against its own hardcoded list (which excluded `ecdsa-p256k1`). Direct `httpx` API calls bypass this — but in the v0.1.2 design we use `aes256-gcm96`, which `hvac` does support, so this is moot.
6. **`hash_algorithm: "none"` is invalid for Vault `transit/sign`.** Valid values are `sha1`, `sha2-*`, `sha3-*`. Omitting the field defaults to `sha2-256`. **Moot under v0.1.2** because we no longer call `transit/sign`.

## Pivot

The originally-intended D1 specified Vault Transit `ecdsa-p256k1` as the signing backend with `exportable=false`, giving "keys never leave Vault" as the load-bearing custody property. With secp256k1 unavailable, that property is unattainable through Vault Transit alone.

**Path 2 (chosen):** Vault Transit `aes256-gcm96` as an envelope encryption layer. Each wallet's secp256k1 privkey is generated externally, encrypted via `transit/encrypt/fwd-master`, and stored as ciphertext in SQLite. At signing time, fwd decrypts via `transit/decrypt/fwd-master`, signs in-process with `eth-account`, and zeroizes the plaintext buffer immediately. Vault's role narrows to encryption-at-rest envelope; the Shamir 3-of-5 unseal ritual remains.

Other paths considered (full table in `decisions.md` D1):
- Path 1 — AWS KMS (rejected: cloud jurisdiction)
- Path 3 — Encrypted file keystore (rejected: loses Shamir unseal recovery property)
- Path 4 — YubiHSM 2 + PKCS#11 (deferred to Phase 10 as originally planned)
- Vault Enterprise (rejected: ~$30k/yr, not AP-realistic)

## Trade-offs honestly recorded

**Preserved from v0.1.0:** Vault container topology. Shamir 3-of-5 unseal. AP sovereignty. D2 (Docker), D3 (SQLite + Litestream), D4 (Vault OSS), D6 (unseal custody) unchanged.

**Lost:** The two-process custody boundary. Plaintext privkeys exist in fwd's process memory during the bounded signing operation. The "non-exportable Vault Transit" property (which we never actually got because Vault can't sign with secp256k1) is replaced by "encrypted at rest + memory-only at signing."

**Simplified:** No DER → low-S → v-recovery dance — `eth-account.sign_transaction` returns Ethereum-shaped output directly. Phase 3's signing core is materially simpler than the original spec.

**Mitigated by Core invariant #16 (new):** decrypt-on-demand, no privkey caching between requests, zeroize-on-completion. Limits A3/A4 exposure window to microseconds per signing operation.

## Provenance

Phase 0 verification miss: the Reviewer did not independently verify Vault Transit's secp256k1 support before pinning D1 in v0.1.0. The v0.2.0 spike caught this; the doctrine worked. Future canonical prompts will explicitly verify substrate-level capability claims against upstream docs before pinning architectural decisions.
