# v0.3.0a2 — Reviewer-only fix-up to v0.3.0a1 (VAULT_ADDR in compose env)

> Reviewer-only ship landed 2026-05-02. Surgical defect fix surfaced during the v0.3.0a1 manual verification ritual. No Sonnet involvement.

## Defect

The `vault` CLI (inside the `hashicorp/vault:1.18.2` image) defaults to `https://127.0.0.1:8200` when `VAULT_ADDR` is unset. The `fwd-vault` listener is HTTP only (`config/vault/config.hcl` sets `tls_disable = true`; the `fwd-internal` Docker network is the security boundary per architecture.md § Vault configuration). Without `VAULT_ADDR` in the container env, every `docker exec fwd-vault vault <cmd>` fails with:

```
Error: Get "https://127.0.0.1:8200/v1/sys/seal-status": http: server gave HTTP response to HTTPS client
```

This breaks step 1 of `docs/runbooks/vault-init.md` (`vault operator init`) and every subsequent step that touches the vault CLI inside the container — including `scripts/vault-init.sh`.

The compose healthcheck (line 19) already inlined `VAULT_ADDR=http://127.0.0.1:8200 vault status -format=json`, which means v0.3.0-alpha's author hit the same default-HTTPS problem for the healthcheck only and worked around it inline. v0.3.0a1 added the operator-facing runbook + init script that *also* call the vault CLI but never generalized the workaround.

This is exactly the class of defect Core invariant #14 ("real-RPC verification is the validation; mocks lie") catches: v0.3.0a1's runbook was reviewed against the spec but never run end-to-end. The v0.3.0a1 verification gate (operator runs the runbook on a fresh Vault) caught it before push.

## Fix

Add a 2-line `environment:` block to the `vault` service in `docker-compose.yml`:

```yaml
    environment:
      VAULT_ADDR: http://127.0.0.1:8200
```

Plus a 5-line comment explaining the rationale. After this change, every `docker exec fwd-vault vault <cmd>` works as documented in the runbook with no per-command env passthrough.

## Out of scope

- The compose healthcheck's inline `VAULT_ADDR=http://127.0.0.1:8200` prefix (line 19) is now redundant but left intact. Cleanup is not a defect fix; it can ride alongside Phase 3b's TLS-within-`fwd-internal` work or a later compose tidy.
- Adding `VAULT_ADDR` to `.env.example` for *fwd's* outbound use to vault — `.env.example` already has `VAULT_ADDR=http://vault:8200` (line 11) for the fwd→vault path inside `fwd-internal`. Phase 3b's Vault client will read that as-is.
- Updating the runbook text — the runbook commands work as-shipped after this fix; no wording needs to change.
