# v1.1.0a43 — `clifwd onboard rewards --import-existing` for migrating providers

**Type:** tooling ship (`install/onboard` + docs; no daemon `src/` change).
**Date:** 2026-05-31.
**Authoring:** Reviewer (Opus); operator-gated. Verified on real (isolated) infra.

## Why

fwd is fundamentally a migration tool ("replace every `.env PRIVATE_KEY=`"), and a
provider who already operates is not greenfield — they already hold a funded,
on-chain-authorized **claim executor** and **FSP submit/sender** key (plus the
registered signing key). The a42 `onboard` *generated* the executor + sender,
forcing a migrating provider to re-run `ClaimSetupManager.setClaimExecutors` and
re-fund a new sender. This ship lets them import what they already have.

## What changed (operator decision: support both via a flag)

- **New `--import-existing` flag** on `clifwd onboard rewards`. Default is
  unchanged (generate fresh — greenfield; cleanest custody, keys born inside fwd's
  sealed master). `--import-existing` moves the executor (`claimer-<net>`) + sender
  (`fsp-sender`) from the GENERATE set into the IMPORT set; `fsp-signing-<net>` is
  imported in both modes.
- **Set-driven provisioning.** Each IMPORT-set wallet is existence-checked
  (`wallets list`); present → "already imported", missing → its exact `clifwd
  wallets import …` command is printed (GATE 1) and the gate pauses
  (`--skip-fsp-import` prints-and-continues; deferred wallets are skipped downstream
  with a warning).
- **Origin-aware nonce seeding.** Generated senders seed `0` (fresh). Imported
  senders **prompt the operator for the real on-chain nonce** — fwd is zero-egress
  and cannot read it; seeding `0` on a used key would `nonce too low`-wedge the
  first tx.
- **GATE 2 branches by mode.** Greenfield prints the authorize/register checklist
  (`setClaimExecutors` + allow recipient + register signer). `--import-existing`
  prints a **cutover** checklist instead: the imported keys are already authorized,
  so STOP the old claimer/submitter for those accounts (fwd is now their sole user —
  otherwise the two collide on nonces).
- Docs: `docs/one-command-install.md` documents `--import-existing` (the migration
  vs greenfield trade-off, the cutover, the nonce prompt); `install/install.sh`
  banner adds a one-line migration hint.

Honest trade-off (surfaced in the docs + GATE 2): an imported key carries its
pre-fwd plaintext exposure (old `.env`, backups, shell history) into fwd, and the
import requires the sole-submitter cutover (Core #15).

## Verification (Core #14 — isolated, production untouched)

Isolated instances from the `fwd:dev` image beside the untouched production `fwd`:
- **Generate regression:** `onboard rewards fsp` (no flag) → `claimer-coston2` +
  `fsp-sender` generated, fsp-signing import gate, nonce `0`, greenfield GATE 2 —
  unchanged from a42.
- **`--import-existing` Pass A** (no keys yet): prints the three `wallets import`
  commands, generates nothing, warns the deferred senders, prints the CUTOVER gate.
- **`--import-existing` Pass B** (keys imported): "already imported" ×3, nonce
  prompts seed the **operator-supplied** values (`claimer-coston2 = 5`,
  `fsp-sender = 7`), CUTOVER gate, exit 0. Idempotent re-run → "already imported" +
  "nonce exists (skip)".
- Torn down (`down -v`); production `fwd` healthy throughout.

The live-Coston2 reward drill via a clif client stays the operator gate (Core #15).
