# v1.1.0a108 — `fsp-register`: the keyless provider's one-time entity-registration capability

**Type:** feature. The first consumer to register a BRAND-NEW keyless provider (the new-Songbird-provider canary) surfaced a gap: a born-sealed keyless provider literally cannot register its own on-chain addresses, because the EntityManager `confirm*Registration` calls must be SENT BY the hot addresses fwd holds — and the fsp capability set had no permission for them.
**Date:** 2026-06-15.
**No signing-path change** — `policy_engine`, `sign_transaction`, the sealed master, the nonce manager are UNTOUCHED. This ship is policy GENERATION + one bounded carve-out shape; the daemon's authorization code is unchanged.

## Headline

A new, **revocable** `fsp-register` capability emits the 3 EntityManager confirm permissions a keyless provider needs to register its hot addresses **once**:

- `confirmSubmitAddressRegistration(_voter)` ← `fsp-submit`
- `confirmSubmitSignaturesAddressRegistration(_voter)` ← `fsp-sig-submit`
- `confirmSigningPolicyAddressRegistration(_voter)` ← `fsp-signing`

The matching `propose*Address` + `registerPublicKey` calls are signed by the **COLD identity key OFF fwd**, so they are deliberately NOT in the policy — fwd holds only the three hot addresses, so it only signs their three confirms. Granted at onboard, exercised once, then **revoked** — registration is bootstrap authority, not steady-state surface.

## What changed

- **`config/abis/entity_manager.json` (new)** + `config/abis/registry.yaml` — the `entity_manager` ABI (the 3 `confirm*Registration(address)` methods only; fwd signs nothing else on EntityManager). Required so fwd can intent-decode the confirm calldata (Core invariant #3).
- **`config/networks.yaml`** — `entity_manager` address per network (Flare `0x134b3311…fdC2`, Songbird `0x46C417…0049`, Coston2 `0xE62c…fDf1`).
- **`src/fwd/app/policy_init.py`** — new `FSP_REGISTER` capability + `identity` param (required for `fsp-register`; raises without it). Emits 3 confirm permission blocks; because `_voter` is a SCALAR address it is **pinned via `arg_predicates` to `--identity`** (NO `allow_unconstrained_args` — tighter than the non-scalar submit/sign methods), `max_value_wei="0"`. Reuses the fsp-voter wallets (defensive `setdefault`, so `--capabilities fsp-register --merge` into an existing fsp-voter policy is referentially valid).
- **`src/fwd/infra/policy_loader.py`** — widened the bounded cross-domain carve-out: `_FSP_SELF_SUBMIT_SHAPES["entity_manager"] = {confirmSigningPolicyAddressRegistration(address)}`. ONLY the signing-policy confirm is exempt (the submit / sig-submit confirms run on EVM-only wallets never in `fsp_self_submit`). The carve-out's value-bound + method-bound are unchanged in mechanism; this adds one abi+method to the allowlist, guarded by the negative tests.
- **`src/fwd/cli/policy.py`** — `policy init --identity`.
- **`src/fwd/app/capability_grant.py`** — the 3 `entity-confirm-*` roles in `_ROLE_CONVENTION`, so `fsp-register` is grantable via `fwdctl capability grant`.

## Why a carve-out widening is the load-bearing review point

`confirmSigningPolicyAddressRegistration` is sent by `fsp-signing`, which is a cross-domain `fsp_self_submit` wallet (it signs FSP messages AND self-submits relay/FSM/voter-registry EVM txs). fwd makes any new self-submit shape touch `_FSP_SELF_SUBMIT_SHAPES` ON PURPOSE — the negative test guards the bound. The widening admits exactly one new (abi, method): `entity_manager → confirmSigningPolicyAddressRegistration(address)`, value=0. The two negative tests prove the bound holds: a DIFFERENT entity_manager method (e.g. `confirmSubmitAddressRegistration`) on a self-submit wallet, or a non-zero value, is still refused.
