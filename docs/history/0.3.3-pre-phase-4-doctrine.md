# v0.3.3 — Pre-Phase-4 doctrine decisions (D11, D12, D13)

> Reviewer-only doctrine ship landed 2026-05-07. Closes the three "Phase 4 spec" findings from the v0.3.1 audit before Phase 4's canonical prompt is drafted, per Core invariant #18 (doctrine and code do not drift).

## What landed

Three new entries in `docs/decisions.md`:

### D11 — Admin auth and caller auth are distinct, never bridged

Closes audit finding F2.4. The two auth boundaries (admin via `FWD_ADMIN_KEY`, caller via argon2id-hashed bearer tokens) live in separate modules, share no fallback path, and never accept the other type's credential. An admin token presented to `/v1/sign-and-send` returns 401, exactly as a forged token would; a caller token presented to `/v1/admin/wallets` returns 401. Phase 4's `require_caller` is a new module (`api/caller_auth.py`), not a wrapper around `require_admin`. Tests verify the bright line as explicit unit cases.

### D12 — CLI in-process pattern for `clifwd wallets import`

Closes audit finding F3.2. Per D9, `clifwd wallets import` is CLI-only (no HTTP — privkeys never traverse HTTP). Phase 4 lands:

- `app/wallet_import.py` — new use case that reads the privkey file, validates against the D9 refusal table (mode 0600, owner UID, 32-byte hex content, name uniqueness, optional `--expected-address` match), and persists.
- `infra/envelope_signer.py::EnvelopeSigner.import_wallet(privkey_buf, ...)` — new method mirroring `create_wallet` but accepting an externally-provided privkey bytearray.
- `cli/wallets.py::import_` — opens `SignerCM` from `app.dependencies` and calls the use case in-process.

The CLI imports only from `fwd.app.*` and stdlib. Layer-boundary test stays unchanged (`cli: {app, domain}`); the in-process wiring lives in app's composition root.

### D13 — Policy ownership: caller-keyed, with wallet-level constraints reserved for Phase 7

Closes audit finding F7.4. Policy is **caller-keyed**: when caller X requests `/v1/sign-and-send` for wallet Y, `fwd` resolves caller.policy_path against `policy.yaml` permissions. The wallet's `policy_path` (already on the schema since v0.3.0a6) is reserved for Phase 7 per-wallet constraints (rate limits, daily-spend caps) under a `wallet_constraints` block.

The Phase 7 evaluation order (8 steps) is spec'd in D13's "Decision" section:
1. Resolve caller.policy_path → permissions block.
2. Check wallet_allowlist includes the requested wallet.
3. Check contract address in allowlist.
4. Check method in allowlist.
5. Check decoded args within bounds.
6. Check rate limit on (caller, wallet, contract, method) key.
7. Check `wallet_constraints[wallet.policy_path].max_daily_aggregate_wei` against pending+confirmed value sum.
8. Default-deny on any failure.

Phase 4 stores `policy_path` on the `callers` table without enforcement; Phase 7 lands the engine.

## Why this ships before Phase 4

Per Core invariant #18 (instated in v0.3.2): doctrine decides, code follows. Without these three decisions, Phase 4's canonical prompt would either:
- Bake in the wrong indirection (e.g., wallet-keyed policy, requiring rewrite at Phase 7), or
- Punt the decisions into Sonnet's deviation-license, which means the *implementer* makes architectural calls the *Reviewer* should make.

Both outcomes violate the Opus-prescribes / Sonnet-implements separation. v0.3.3 lands the prescriptions cleanly so v0.4.0-alpha's canonical prompt is unambiguous.
