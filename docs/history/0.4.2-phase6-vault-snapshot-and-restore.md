## Why this ship

Phase 6 ship 1 (v0.4.1) shipped Litestream S3 + a restore runbook with an
explicit TODO for Vault state recovery. The TODO was honest: without a Vault
Raft snapshot, the workaround (fresh `vault-init.sh` run with OLD D6 shares)
would regenerate the seal, which would in turn regenerate the `fwd-master`
Transit key, which would make every existing wallet ciphertext in SQLite
unreadable. Phase 6 ship 2 closes that gap.

It also folds in a Phase 0 finding the Reviewer surfaced while drafting:
`fwd-internal` is `internal: true` and has **no route to the public internet**
(verified empirically with `docker run --network fwd_fwd-internal alpine wget
s3.fr-par.scw.cloud` → `bad address`). Litestream was on `fwd-internal` only,
which would have silently failed once real Scaleway credentials were
provisioned. Per Core invariant #18 — when doctrine says replication works and
the code doesn't allow it, fix the code.

## What ships

Three changes form one logical unit:

### 1. vault-snapshot sidecar

- `config/vault-snapshot/Dockerfile` (NEW) — multi-stage:
  `hashicorp/vault:1.18.2` → `alpine:3.19` + `aws-cli` + `bash` +
  `ca-certificates`; vault binary copied from the vault stage; runs as
  `nobody`; entrypoint is the snapshot loop script.

- `scripts/vault-snapshot.sh` (NEW, 108 lines) — POSIX sh. Uses `set -u` (not
  `set -e`) so a per-iteration failure logs and continues. Each iteration:
  AppRole-login via the new `fwd-snapshot` role → `vault operator raft
  snapshot save` to `/tmp/vault-<UTC-ts>.snap` → `aws s3 cp` to
  `s3://${LITESTREAM_S3_BUCKET}/${VAULT_SNAPSHOT_S3_PATH:-vault-snapshots}/vault-<ts>.snap`
  → list bucket prefix, filter to `^vault-[0-9]{8}T[0-9]{6}Z\.snap$`, keep
  newest N (default 7), delete the rest → cleanup local + revoke token →
  sleep `VAULT_SNAPSHOT_INTERVAL_SEC` (default 86400). Credentials are reused
  from `LITESTREAM_S3_*` (mapped to `AWS_*` env vars at script start).

- `config/vault/policies/fwd-snapshot.hcl` (NEW) — single capability:
  `read` on `sys/storage/raft/snapshot`. No `transit/*`, no
  `snapshot-force`. Disjoint from `fwd-app` per D11-style isolation:
  compromise of the snapshot AppRole credentials does NOT grant the
  ability to decrypt wallet ciphertexts.

- `scripts/vault-init.sh` (EXTENDED) — steps 9-12 appended: write the
  fwd-snapshot policy, create the `fwd-snapshot` AppRole
  (`token_ttl=10m`, `secret_id_ttl=0`), read role_id, generate secret_id,
  validate. Closing operator-capture block extended to print all four
  credential pairs and instruct `docker compose restart fwd vault-snapshot`.

- `docker-compose.yml` (MODIFIED) — added `vault-snapshot` service on both
  `fwd-internal` (for Vault API at `http://vault:8200`) and `fwd-egress`
  (for S3); `depends_on: vault: service_started`.

- `.env.example` (EXTENDED) — vault-snapshot block: required
  `FWD_VAULT_SNAPSHOT_ROLE_ID` + `FWD_VAULT_SNAPSHOT_SECRET_ID` (empty,
  populated from vault-init.sh output) plus optional
  `VAULT_SNAPSHOT_S3_PATH`, `VAULT_SNAPSHOT_INTERVAL_SEC`,
  `VAULT_SNAPSHOT_RETENTION_COUNT` (commented with defaults).

### 2. restore.md Step 4 — real Vault Raft snapshot restore

`docs/runbooks/restore.md` Step 4 replaced in place. The procedure:

1. Locate the latest snapshot (`s3 ls` → regex filter → `sort | tail -1`),
   download via `aws s3 cp`, `docker cp` into `fwd-vault:/tmp/vault.snap`.
2. `vault operator init -key-shares=3 -key-threshold=2 -format=json` —
   throwaway Shamir; parse the dummy unseal keys + root token.
3. Unseal with the dummy keys; authenticate with the dummy root token.
4. `vault operator raft snapshot restore -force /tmp/vault.snap` —
   overwrites Vault state with the snapshot's state, including the
   ORIGINAL Shamir seal configuration. Vault becomes sealed.
5. Unseal with the **ORIGINAL D6 shares** (per `decisions.md` D6 + Core
   invariant #17). The dummy keys are now invalid; the original D6 shares
   are what unlocks the restored state.
6. Verify: `vault list transit/keys` returns `fwd-master`; `vault list
   auth/approle/role` returns `fwd, fwd-snapshot`. Wallet ciphertexts in
   SQLite decrypt unchanged because the original Transit key is restored.

Front-matter callout updated from "Phase 6 ship 1" to "Phase 6 ship 2 —
v0.4.2", and the Vault TODO bullet replaced with a "complete" bullet
documenting the preservation of `fwd-master` and AppRole credentials.

Pre-v0.4.2 fallback retired as broken: explicit note that running
`vault-init.sh` against a fresh Vault would regenerate the seal, making
OLD D6 shares useless and OLD wallet ciphertexts unreadable.

### 3. fwd-egress network

`docker-compose.yml` and `vault-init.md` updated:

- New top-level network `fwd-egress` (`driver: bridge`, default external
  connectivity). Comment explains the empirical Phase 0 finding.
- `litestream` service moved from `fwd-internal` → `fwd-egress` (it needs
  S3 but no Vault; reads SQLite via volume mount).
- `vault-snapshot` service on both `fwd-internal` (for Vault) and
  `fwd-egress` (for S3).
- `fwd-internal` remains `internal: true` — vault ↔ fwd ↔ vault-snapshot
  still resolve `vault` over it.
- `vault-init.md` Step 6 restart command changed from
  `docker compose restart fwd` to `docker compose restart fwd vault-snapshot`.
