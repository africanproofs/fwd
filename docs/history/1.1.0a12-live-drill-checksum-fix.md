# v1.1.0a12 — live drill + checksum / nonce-release fix

**Shipped 2026-05-27.** The end-to-end live drill of the zero-egress architecture
— and the latent bug it caught. This is the Core invariant #14 loop working as
designed: a defect invisible to mocked unit tests, surfaced only by signing on the
real path, then closed as a *class*, not just an instance.

## The drill (running service + client, end-to-end)

fwd was booted locally (sign-only, zero-egress) against a minimal demo policy
(`examples/demo-policy.yaml`: one caller `demo-client`, one wallet `demo-wallet`,
`erc20.transfer(address,uint256)` on a Coston2 token). A wallet + caller key were
provisioned and the nonce seeded via `clifwd nonce init`. A standalone demo client
(`examples/zero_egress_client.py`) then drove the full loop:

1. Built `transfer(...)` calldata client-side.
2. `POST /v1/sign-transaction` → fwd signed and returned `{tx_id, hash,
   signed_raw_tx, nonce}` **making no network call** (fwd log shows only
   `sign_transaction.ok`).
3. `eth_account.Account.recover_transaction(signed_raw_tx)` recovered the wallet
   address — the signed tx is cryptographically valid, proven with zero fwd
   involvement.
4. The **client** broadcast to **real Coston2** (`eth_sendRawTransaction`) — fwd
   never touches the RPC. The unfunded demo wallet got `insufficient funds`
   (the honest on-chain gate).
5. The client reported back: `POST /v1/transactions/{tx_id}/broadcast-result`
   `rejected_releaseable` → fwd released the nonce → status `failed`. The full
   sign → broadcast → report-back loop, end to end, against live infrastructure.

## The bug the drill caught (and the fix)

The client's **first** attempt sent a non-checksummed (lowercase) `to`. fwd's
`signer.sign_transaction` (eth_account) raises **`TypeError`** on a non-checksummed
address — and the pre-sign `except (VaultUnavailableError, ValueError)` did **not**
catch `TypeError`. Result: a leaked **500** AND, worse, **the reserved nonce was
never released — a permanent nonce-wedge** (every later nonce stuck behind the gap).
A mocked signer (which doesn't validate `to`) is structurally blind to this; only
signing on the real path exposed it.

**Fix (instance + class):**
- *Instance:* `sign_transaction` now normalizes `to` with
  `eth_utils.to_checksum_address` before building the tx — clients may send any
  valid-hex casing (the AP frontend standard is even lowercase). Live-verified: a
  lowercase `to` now returns 200 with a recoverable signed tx on the real daemon.
- *Class:* the pre-sign arm now catches `TypeError` too — **any** error between
  nonce reservation and a persisted signed tx MUST release the nonce, never wedge
  it (Core invariant #11 spirit; partners #14 real-RPC-verification and #19
  forensic-row durability). Regression tests assert both: the `to` reaching the
  signer is checksummed, and a signer `TypeError` releases the reserved nonce.

## Funded live-mine proof (real Coston2)

The on-chain mining leg was then proven with an existing fwd-custodied funded test
wallet (`phase3c-verify`, ~100 C2FLR) — no faucet needed. A harmless
`erc20.transfer(addr, 0)` to the Coston2 WNat token: fwd signed (zero egress) →
recovered signer == wallet → the **client** broadcast to real Coston2 →
**tx `0x14440b06e29c0e1a28563541ca8ef0c5a614d59be8401bb1644e8e4fe3395cbd` MINED at
block 31,028,196, status 1** → report-back drove fwd `pending → submitted → mined`.
Audit chain: `sign-transaction(approved) → tx-broadcast-result(approved) →
tx-receipt(approved, mined_success)`. The full zero-egress loop is proven on real
chain, effect-verified (receipt status), not just "submitted".

**Caveat (recorded honestly):** `phase3c-verify` is a pre-v1.0.0a1 wallet whose key
was sealed under the *retired* Vault Transit backend (`vault:v1:`), which the current
`SealedMaster` cannot decrypt. The drill ran on a *copy* of the state DB; the live
`fwd_fwd-state` volume was verified untouched. Reviving Vault to recover that key was
a custody-boundary action that should be operator-gated — a future drill must pick a
post-migration `seal:v1:` wallet (e.g. `sealed-verify`); see the memory
`spawned-agent-revived-vault-for-old-wallet`.
