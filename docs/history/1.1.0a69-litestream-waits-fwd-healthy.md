# v1.1.0a69 — litestream waits for fwd `service_healthy` (fixes the fresh-volume `readonly database` crash)

**Type:** compose fix (`docker-compose.yml`). No code change. Operator hit it on a from-scratch install — the fwd container crash-looped, masking a first-run migration failure.
**Date:** 2026-06-04.

## Why (operator hit it live)

A fresh `--with-clif` install crash-looped: `fwd` stuck `Restarting`, the installer's health-wait failed. The restart loop masked the real first error — the daemon's `alembic upgrade head` ran `0001 → 0002 → 0003` fine, then failed migration `0004` with **`sqlite3.OperationalError: attempt to write a readonly database`** (subsequent restarts then looped on `table wallet_chains already exists`, re-running the half-applied `0004`). The `/data` volume was correctly `1000:1000`-owned and `0001-0003` wrote fine, so it wasn't a static permission problem — it went readonly **mid-migration**, and `litestream` was active on the same `/data` at the same instant (`.state.db-litestream` created concurrently).

Root cause: `litestream` used the **short-form** `depends_on: [fwd]`, which waits only for the fwd container to **start**, not to be **healthy**. So litestream opened the source DB read-write (for its `_litestream_seq`/`_litestream_lock` tables) **while fwd's first-run alembic was still creating the schema** — the two collided on the fresh volume and fwd's migration write failed readonly. It's a fresh-DB-only race (whichever process opens the empty DB first wins), which is why prior installs intermittently succeeded.

## What changed

`docker-compose.yml`: litestream's `depends_on` switches from the short list form to the long form with `condition: service_healthy`:

```yaml
    depends_on:
      fwd:
        condition: service_healthy
```

fwd already defines a `HEALTHCHECK` (Dockerfile) that passes only after `alembic upgrade head` + uvicorn are up, so litestream now starts **after** the schema is fully created and the app is running — it can no longer touch the DB during the migration. The adjacent network comment was updated to match. No code, no behavior change beyond startup ordering; fwd has no dependency on litestream (one-directional).

## Verification (Reviewer)

`docker compose config` parses (exit 0) and renders litestream `depends_on: fwd: {condition: service_healthy}`; fwd's `HEALTHCHECK` is present (Dockerfile) so the condition is satisfiable. The operator's broken install was recovered without a reinstall by the manual analogue of this fix — wipe the half-built volume, start `fwd` ALONE (fresh alembic, no litestream) to healthy, then start `litestream` — which came up clean (`{"master":"ok","fwd":"ok"}`), confirming the race (not the schema) was the fault. `poetry run pytest` (version-consistency + suite). Class note (Core invariant #19): a replication sidecar sharing the state DB must wait for the primary's schema-creating startup to COMPLETE (`service_healthy`), never merely start — concurrent opens of a fresh SQLite DB race on writability.
