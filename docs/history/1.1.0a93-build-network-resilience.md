# v1.1.0a93 — build-from-source network resilience (Dockerfile retries)

**Type:** build-infra resilience. **No daemon/signing-path change** — only `Dockerfile`
(+ version files). `src/` untouched.
**Date:** 2026-06-08.

## Why

The operator's fresh `install.sh` failed the `docker compose build` twice, then a third time,
each at a *different* network step (`poetry install` wheel ReadTimeout; then `pip install
poetry` ReadTimeout; an `apt-get` "Network is unreachable" appeared in a parallel test). An
ultracode diagnostic workflow + host probes established what it is **not** and what it **is**:

- **NOT MTU** — docker0 bridge MTU is 1500, matching the host interfaces.
- **NOT a BuildKit-network bug** — a plain `docker run` (default bridge) AND `--network=host`
  both download large wheels fine *when the link is up*; the one build that succeeded (clif,
  `--network=host`) was simply in a good window.
- **NOT a deterministic config gap** — `POETRY_REQUESTS_TIMEOUT=120` + `pip --timeout 120
  --retries 5` were already present.
- **IT IS an intermittent/variable external link** (PyPI/Debian reachability swings between
  ~1 MB/s and read-timeout/unreachable within minutes). A build fails when it happens to hit a
  bad window at whatever network step is downloading then. Running fwd + clif builds **in
  parallel** (the diagnostic workflow) compounded it by saturating the constrained link.

A longer timeout alone can't fix dropped packets / a bad window — but **retrying** rides
through a transient dip, and **sequential** builds avoid self-inflicted contention.

## What changed (`Dockerfile`)

Every network step now retries; timeouts raised; sequential-build guidance documented:

- `POETRY_REQUESTS_TIMEOUT` 120 → **300**.
- `apt-get` (both stages): `-o Acquire::Retries=5`.
- `pip install poetry`: `--timeout 300` + **3× retry** (`|| sleep && retry`).
- `poetry install --only main [--no-root]` (both): **3× retry**.

Portable — helps any FTSO provider building from source on a variable link, not just this host.

## Validation (Core #14 — real build to exit-0, the operator's exact path)

`docker compose build` (default BuildKit, sequential) → **exit 0** for both, in a good window:
- fwd a93: built; `docker run … python -c "import fwd.version"` → `fwd 1.1.0a93`.
- clif 0.5.19 (companion ship): built; `clif version` → `clif 0.5.19`.

The built layers are cached on the host, so the operator's `install.sh` clone of a93 is a
cache hit (no re-download) unless the Dockerfile/lock content changes.

## Not the fix (recorded so it isn't re-tried)

`--network=host` was a red herring — it only "worked" for clif because that build caught a good
window. The default network is fine when the link is up. The real lever is retry-resilience +
not building in parallel + (operator infra) a stable link; this host has both wifi (`wlx…`) and
ethernet — a wired/stable connection during the source build is the most reliable path.
