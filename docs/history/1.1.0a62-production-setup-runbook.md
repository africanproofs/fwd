# v1.1.0a62 — codified full-production-setup runbook + onboard gas-funding reminder

**Type:** docs + a one-block install-script fix (`docs/production-setup.md`, `install/onboard`). Operator-directed: "a fresh full setup is more than the installer … review for correctness and codify this." Presentation/docs-only — no custody/signing/nonce/policy/daemon-profile semantics change.
**Date:** 2026-06-03.

## Why

The operator specified the canonical end-to-end production-setup sequence (install → onboard → custody gates → on-chain auth → rehearse → enable daemons → final checks) and asked to codify it as the authoritative meaning of "setup steps". Reviewing it against the code surfaced one real gap in the tool's own output: onboard's printed on-chain checklist listed `setClaimExecutors` / `setAllowedClaimRecipients` / register-voter but **never said to FUND the gas-paying wallets** — and `claimer-<net>` + `fsp-sender-<net>` are freshly-generated zero-balance wallets that pay their own gas, so an operator following onboard's output verbatim would have two wallets that silently can't transact.

## What changed

- **`install/onboard` — funding reminder added to the AUTHORIZE block** (the fresh-wallet / generate path). After the authorize/allow/register lines, per network: "fund gas: send native FLR/SGB to `claimer-<net>` (addr) — fresh wallet; it pays gas for RewardManager.claim" and the same for the FSP sender (`fsp-sender-<net>` / shared `fsp-sender`). The FSP **signing** key is deliberately excluded — it signs detached and needs no gas. Unconditional (prints in both compact and guided — funding is a next-action, not flavour). The import-existing CUTOVER path is unchanged (those wallets are the operator's existing, already-funded ones).
- **`docs/production-setup.md` (new)** — the canonical 7-step full-production runbook: install (inert) → onboard (canary-first; idempotent expand) → custody gates → on-chain authorization + gas funding → rehearse via the `clif` wrapper + verify the real `RewardClaimed` event → enable (`FSP_AUTO_ENABLED=true` then `fwd start <net> fsp`) → final checks. Honest where the code is: notes `get.proofs.africa` hosting is Phase-1-pending (clone-and-run fallback), recommends canary-first over passing all networks up front, and states the system is production-ready ONLY when every stage (incl. gas funding + a verified on-chain effect + green audit) is complete. References `one-command-install.md` for installer/onboarding internals (no duplication).
