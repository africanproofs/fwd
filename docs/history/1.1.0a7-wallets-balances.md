## What shipped

A read-only admin surface for verifying gas balances of every fwd-custodied
*transacting* wallet on each chain it is policy-authorized to transact on:

- **`src/fwd/infra/rpc.py`** — `RpcClient.get_balance(address) -> int`
  (Sonnet-implemented before the timeout; correct + clean).
- **`src/fwd/app/wallet_balances.py`** *(new)* — `list_balances()` use
  case: enumerates DB wallets, derives each wallet's *implied chain set*
  from `policy.permissions[*].contracts` via the module-level
  `_CONTRACT_CHAIN` table (Flare 14, Songbird 19, Coston2 114 — mirrors
  `clif/clif/config.py`'s `NetworkConfig` for RewardManager +
  FlareSystemsManager), calls `get_balance` per (wallet, chain), returns
  `BalancesResult(entries, warnings)`. RPC errors are per-entry, never
  abort the request. Unmapped contracts in policy surface explicit
  warnings (never silently dropped — operator notices stale tables).
- **`src/fwd/api/wallets.py`** — `GET /v1/admin/wallets/balances`
  (`admin_required`); query params `include_all=true|false` (default
  false = transacting wallets only) and `chain=14|19|114` (optional
  filter); returns `ListBalancesResponse(balances, warnings)`. `503
  policy_not_loaded` when `app.state.policy` is None. **Observational —
  no audit row** (the audit log stays focused on signing decisions, not
  read-only admin queries; mirrors `wallets list`).
- **`src/fwd/cli/wallets.py`** — `clifwd wallets balances` with
  `--chain`, `--all`, `--low-water FLOAT`, `--json`. Default output is
  an aligned table mapping `chain` → network name; `--low-water` adds
  a `⚠ low` marker on rows below the threshold; RPC errors render as
  `(rpc error: …)`.
- **`tests/unit/test_wallet_balances.py`** *(new)* — 13 cases covering
  the implied-chain derivation, `_format_native`, `list_balances`
  default-scope + include_all + chain_filter + per-call RPC error,
  endpoint admin-auth (401), policy_not_loaded (503), happy path, and
  `chain` query param. Plus an env-gated real-RPC smoke
  (`FWD_LIVE_RPC=1`) for Core #14 coverage.

## Why this scope (and not more)

The operator's directive was "funding status of all accounts we sign
transactions for". The scope is therefore fwd-custodied transacting
wallets — those reachable from any `permissions` allowlist. Three
deliberate exclusions:

1. **Non-custodied addresses** (e.g. AP's FTSO V2 provider Submit
   Address / Submit Signature Address / Delegation Address) are out of
   scope — fwd doesn't custody their keys, and a watch-list feature for
   them is a separate concern (any `eth_getBalance` script does the same
   job for non-custodied addresses; no need to bundle into fwd).
2. **No audit row** for balance queries — they're read-only observation,
   not signing decisions; the audit log stays focused on what was
   signed/refused/why.
3. **No caching** in v1 — interactive operator use; 6 wallets × 3 chains
   ≈ 18 cheap RPC calls; can add caching if hammering ever surfaces.

## Process honesty (Core #18) — Reviewer-implements vs Sonnet

This ship deviates from the standard
Reviewer-prescribes-Sonnet-implements-Reviewer-reviews flow: after the
second spawn attempt's stream timeout at ~10% completion, the Reviewer
implemented the remaining work directly. The fwd workflow's four-role
tension (Opus prescribes / Sonnet implements / Opus reviews / Operator
gates) is intentional — collapsing Reviewer + Implementer into one role
loses the binding-pass check. The operator's commit-gate review is the
load-bearing control here; the alternative (a third spawn attempt, also
at timeout risk) would have delayed the feature past its Ship-D
funding-verification window. Recorded as Reviewer-implements
documented honestly, not silently folded.
