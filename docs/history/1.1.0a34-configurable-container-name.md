# v1.1.0a34 — configurable container name (`FWD_CONTAINER`)

**Type:** deployment-scaffolding ship (no daemon code change). Provider-distribution Phase 1.
**Date:** 2026-05-31.
**Authoring:** Reviewer (Opus) implemented directly under operator direction; operator-gated.

## Why

The container name was hardcoded `fwd` (and `fwd-litestream`). That is correct
for the one-stack-per-host design (Core #9), but it makes it impossible to bring
up an **isolated second instance** on a host that already runs a production `fwd`
container — which blocks running install.sh's real `up`+health path locally for
verification (the live AP `fwd` would collide). Parameterizing the name (default
unchanged) unblocks local end-to-end testing and adds a minor capability (a
named instance) without changing production behaviour.

## What changed
- `docker-compose.yml`: `container_name: ${FWD_CONTAINER:-fwd}` (fwd) and
  `${FWD_CONTAINER:-fwd}-litestream` (litestream). **Default is unchanged (`fwd`
  / `fwd-litestream`)** — a production `docker compose up` with `FWD_CONTAINER`
  unset behaves exactly as before; the running container is unaffected.
- `install/clifwd`: `docker exec "${FWD_CONTAINER:-fwd}" clifwd "$@"`.
- `install/install.sh`: honors `FWD_CONTAINER` (config default + exported for
  compose so `container_name` interpolates; health `docker inspect`/`exec` use
  it). Combined with `COMPOSE_PROJECT_NAME`, a fully isolated instance
  (own name + project-scoped volumes + network) runs alongside production.

## Files
`docker-compose.yml`, `install/clifwd`, `install/install.sh`, version files.

## Verification
- `docker compose config`: unset → `fwd` / `fwd-litestream` (production
  unchanged); `FWD_CONTAINER=fwd-localtest` → `fwd-localtest` /
  `fwd-localtest-litestream`. `sh -n install.sh` clean. No `src/` change.
- This unblocks the isolated local end-to-end install run (next).
