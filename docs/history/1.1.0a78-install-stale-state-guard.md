# v1.1.0a78 — install refuses to start on a regenerated-master vs stale-state mismatch (+ `--reset-state`)

**Type:** `install/install.sh` custody-safety guard. No daemon change.
**Date:** 2026-06-05.

## Why (operator hit it live)

A fresh reinstall came up unhealthy and crash-looped on a cryptic `"caller 'claim-flare' policy_path 'perm/claim-flare' not in policy"` consistency error. Root cause: `sudo rm -rf /opt/fwd` removes the install dir (and the `master.key`) but **not** the docker volume `fwd_fwd-state`. So the reinstall regenerated a **new** master and reused the **old** state — whose 6 wallets were sealed under the now-deleted master and whose callers don't match the fresh inert policy. The wallets were undecryptable and the daemon refused to start, but the error gave the operator no idea why or what to do (and momentarily looked like key loss).

## What changed (`install/install.sh`)

Before bringing the stack up, if the installer **generated a new master this run** AND the state volume already holds **≥1 wallet**, it now **refuses** with a clear, custody-safe choice instead of letting the daemon crash-loop:
```
existing state volume '<proj>_fwd-state' holds N wallet(s) sealed under a PREVIOUS
master that this install just regenerated — they cannot be decrypted ... Choose one:
  - CLEAN install (discard that old state):  add --reset-state
  - RECOVER it:  restore its master.key + policy.yaml from backup into <src>/config/ first
```
- New `--reset-state` flag wipes `<proj>_fwd-state` + `<proj>_backup` before start, for an intentional clean reinstall.
- The wallet count is read with a stock `python:3.12-slim` throwaway container (`sqlite3` is stdlib) — **not** the locally-built fwd image (built-on-host, never referenced by registry name for a generic query).
- It never auto-wipes: a real prod's state is preserved; the operator explicitly chooses reset vs restore.

## Verification

`sh -n` + `dash -n` clean. Functional: the guard's wallet-count query returns **1** on a seeded (stale) volume → guard fires (`die`); **0** on a clean volume → guard skips. Reproduced against the exact failure (the stale 6-wallet songbird+flare volume), then recovered the operator's host by clearing the stale volume → fwd came up healthy + inert. (Pairs with the hand-off habit fix: a clean reinstall uses `--reset-state` or an explicit `docker volume rm`.)
