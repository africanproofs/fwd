# v1.1.0a20 — litestream egress lockdown

**Ship type:** config hardening (the second of the three a18-review-flagged code
gaps). Closes gap #2.

## The gap

The `litestream` sidecar in `docker-compose.yml` had no `networks:`/`network_mode:`
key, so it silently joined Compose's **default bridge** — which has internet egress.
The `fwd` daemon is on `internal: true` (no egress), but litestream was not, so the
*stack* was not strictly egress-free. litestream only ever replicates to the local
`backup` volume (Litestream `type: file`) over the shared `fwd-state` volume, so it
needs no network at all.

## The fix

Add **`network_mode: none`** to the `litestream` service. It replicates entirely over
shared Docker volumes (`fwd-state` → `backup`), so removing the network does not affect
replication; `depends_on: fwd` is startup ordering only. The whole stack is now
egress-free, not just the daemon.

(`network_mode` and `networks:` are mutually exclusive; litestream declares no
`networks:`, so this is consistent — `docker compose config` validates.)

## Verification

`docker compose config` validates and resolves `network_mode: none` on the litestream
service. Behavioural correctness is structural: replication is volume-based (no network
dependency — Litestream `type: file` to `/backup`), confirmed against
`config/litestream/litestream.yml`. The live "bring-up + write-tx + confirm-replica"
check lands at the operator's next prod redeploy (the running prod stack was not
restarted for a not-yet-deployed compose change — Core #15, operator-gated).
